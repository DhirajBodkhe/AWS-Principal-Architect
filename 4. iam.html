01 / CONCEPT

Concept & Mental Model #

What Problem Does IAM Solve?

Before AWS existed, controlling who could touch a server meant SSH keys on Linux boxes, Windows Active Directory group memberships, and a prayer that someone rotated credentials when an engineer left the team. Every tool had its own permission system, none of them talked to each other, and "least privilege" was a policy document nobody enforced.

AWS has thousands of API endpoints — S3:GetObject, EC2:TerminateInstances, RDS:DeleteDBCluster. Without a centralised, consistent enforcement mechanism, any IAM gap becomes an all-or-nothing failure: either you lock everything down and nothing works, or you open it up and accept the blast radius of a compromised credential. IAM is that centralised enforcement layer. Every single AWS API call — from your Console click to a Lambda function writing to DynamoDB — passes through IAM. There are no backdoors, no "local accounts" on the server, no root bypass. IAM is the only path.

What Did Engineers Do Before?

On-premises FSI environments used a combination of: Active Directory service accounts (one per application, rotated quarterly if you were lucky), static LDAP bind credentials stored in plaintext config files, per-host firewall rules to compensate for absent application-level auth, and manual ticket-based approvals for privileged access with no technical enforcement. The audit trail was a spreadsheet. Sound familiar? IAM replaces all of this with cryptographically signed, short-lived tokens, enforceable declarative policies, and a complete audit trail via CloudTrail.

Three Core Concepts to Internalize

1. Authentication vs. Authorisation are separate planes. Who you are (authentication — handled by the IAM principal model and STS token issuance) is evaluated separately from what you can do (authorisation — evaluated by policy evaluation logic on every API call). This separation is deliberate and powerful. You can federate authentication from your corporate AD while still controlling authorisation centrally in IAM.

2. IAM Roles, not Users, are the right primitive for workloads. IAM Users carry permanent credentials that can be exfiltrated and replayed indefinitely. IAM Roles issue temporary credentials via STS that expire in minutes to hours, are automatically rotated, and leave a complete trail. Every EC2 instance, Lambda function, ECS task, and CI/CD pipeline should run as a Role, never a User. If you have access keys for a workload in a config file, that is a security incident waiting to happen.

3. Policy evaluation is a multi-layer AND gate, not an OR gate. Access is only granted when every layer of the stack permits it: the Organization SCP must allow it, the resource-based policy (if present) must allow it, the permission boundary must allow it, and the identity-based policy must allow it. Any single explicit Deny anywhere in the chain overrides everything. This means "adding permissions" is additive but "restricting access" can be done at any layer.

Common Misconceptions

⚠️ Misconception: "The AWS root account is just the admin account"

AWS root is not an admin account — it is an account with no permission restrictions whatsoever, including ones set by SCPs. Root bypasses Permission Boundaries, bypasses SCPs, and can do things no IAM principal can (close the account, change the support plan, create certain service-linked roles). Root credentials must be locked in a vault, MFA-protected, and only used for the specific tasks that genuinely require it (there are about 12 of them — documented in AWS docs). Root is the nuclear option. Treat it like the safe combination, not the master password.

⚠️ Misconception: "I can use the same IAM user for everything"

This is how breaches happen. A single compromised IAM user credential with broad permissions = game over. Workloads get Roles. Humans get individual Users with MFA enforced. Break-glass access gets a separate Role that requires explicit assumption from a restricted bastion. Never share IAM users between people or between automated processes.

⚠️ Misconception: "Resource policies and identity policies are interchangeable"

They are not. Same-account access requires only one of them (either an identity policy or a resource policy). Cross-account access requires both — the resource policy must explicitly trust the external account, AND the external account's principal must have an identity policy permitting the call. If either is missing, access is denied.

The Post Office Analogy

Think of IAM as the post office that handles every parcel (API call) in the AWS world. When you send a parcel, the post office checks: (1) Do you have a valid sender ID? — Authentication. (2) Are you allowed to send to this destination? — SCPs check whether this delivery is legally permitted in your country. (3) Does the recipient accept packages from you? — Resource policy. (4) Do you personally have a delivery permit? — Identity policy. (5) Is there a court injunction blocking you? — Explicit Deny. Only when all five checks pass does the parcel get delivered. The post office keeps a complete manifest of every parcel attempted — CloudTrail.

🌉 Bridge from Storage/Virtualisation

IAM's multi-layer evaluation ≈ SAN zoning + LUN masking + host-level ACLs + iSCSI CHAP. In a well-designed SAN, access to a LUN requires: fabric zoning (the switch permits the WWN), LUN masking (the array permits the initiator), OS-level SCSI permissions, and potentially CHAP authentication. Any single layer can block access. IAM works identically: SCP (fabric zoning), resource policy (LUN masking), permission boundary (array quota), identity policy (host ACL), and MFA/Condition (CHAP). The mental model is not "add more permissions" but "all layers must simultaneously permit." IAM Roles ≈ vSphere service accounts — you don't give the VM a human login, you give it a machine identity with scoped permissions that rotates automatically.

💡 Why This Matters

IAM is not a service — it is the substrate. Every other guide in this learning path touches IAM. VPC Flow Logs need an IAM role to write to CloudWatch. Lambda needs a role to call DynamoDB. ECS tasks need task roles to pull from ECR. Transit Gateway needs service-linked roles. Bedrock agents need roles with Bedrock and S3 permissions. If you build nothing else well in AWS, build IAM well. A misdesigned VPC can be refactored. A misconfigured IAM policy can result in a data breach that ends careers and triggers MAS TRM breach notifications within 72 hours.

02 / ARCHITECTURE

Architecture Overview & Visual Model #

Control Plane vs Data Plane

Control plane: IAM API itself — CreateRole, AttachPolicy, AssumeRole. These calls hit the IAM service endpoints and are globally replicated. Changes here can take up to 60 seconds to propagate (eventual consistency). This matters for automated pipelines that create a role and immediately try to use it.

Data plane: Every other AWS API call (S3:GetObject, EC2:DescribeInstances, etc.) performs inline IAM evaluation. There is no separate "IAM enforcement server" — policy evaluation happens within each AWS service on the call path. This makes it extremely fast (microseconds) but also means you cannot centralise IAM enforcement outside the AWS control plane.

💡 The Critical Rule

An explicit Deny in any policy at any layer overrides any number of Allow statements everywhere else. A single SCP Deny on s3:DeleteBucket cannot be overridden by an IAM admin role, a resource policy, or even account root in a member account. This is how governance guardrails work — the Organisation layer is structurally higher than the account layer.

For cross-account access to succeed: the calling principal must have a policy permitting the sts:AssumeRole call, AND the target role's trust policy must include the caller as a trusted principal. Both must be present. Either alone is insufficient.

🌉 Bridge from Storage/Virtualisation

Cross-account IAM ≈ cross-fabric SAN zoning between two separate data centres. The host in DC-A (Account A) needs its own fabric zone allowing the connection, AND the target fabric in DC-B (Account B) must also have a zone permitting the DC-A initiator. One-sided zoning = no connectivity. Same mechanics in IAM — the caller's permission AND the target's trust must both exist.

3.3 Canonical Patterns & Pairings

Pattern 1: Role Chaining for Multi-Account Access

A CI/CD pipeline in a Dev account assumes a deployment role in a Staging account, which in turn assumes a readonly audit role in a Prod account. Each hop is a distinct sts:AssumeRole call with a maximum session duration that resets at each hop. Caution: role chaining caps sessions at 1 hour regardless of the individual role's maximum session duration. Use this for CI/CD deployment pipelines, cross-account monitoring, and centralised audit functions.

Pattern 2: ABAC for Dynamic Multi-Tenant Authorisation

Tag IAM principals with Project=payments and S3 buckets with the same tag. One policy with a condition StringEquals: {"aws:RequestedRegion": "${aws:PrincipalTag/Project}"} grants developers access to only their own project's resources. Scales to thousands of developers without changing policies. Requires disciplined tagging governance. Best fit: SaaS platforms, FSI sub-business-unit isolation, contractor access control.

Pattern 3: Permission Boundaries for Developer Self-Service

Platform team defines a Permission Boundary policy. Developers can create IAM roles themselves — but only within the boundary. Prevents privilege escalation (developers creating roles with more permissions than they personally have). Best fit: Internal developer platform (IDP) environments where teams need IAM autonomy without unlimited blast radius.

Pattern 4: OIDC Federation for CI/CD (GitHub Actions, GitLab, Jenkins)

CI/CD systems obtain short-lived AWS credentials via OIDC without any stored access keys. GitHub Actions presents a signed OIDC token; AWS STS validates it against the registered OIDC provider and issues a role session. Zero long-lived credentials in CI pipelines. Best fit: All modern CI/CD pipelines — this is the correct pattern, full stop. Storing access keys in GitHub Secrets is the wrong pattern.

Pattern 5: IAM Identity Centre + Permission Sets (SSO)

Corporate users authenticate via AD/Azure AD, federate into IAM Identity Centre via SAML, and receive Permission Sets mapped to IAM roles in specific accounts. No individual IAM Users required. Central onboarding/offboarding. Best fit: Any organisation with 10+ AWS accounts and an existing corporate identity provider.

🚫 Anti-Pattern: Long-Lived Access Keys for Workloads

Storing IAM access keys in application config files, Kubernetes secrets, environment variables, or EC2 userdata is a security incident waiting to happen. Every major cloud breach in the last five years has involved exfiltrated access keys. The fix: EC2 instance profiles, Lambda execution roles, ECS task roles, EKS IRSA, and OIDC federation for CI/CD. If you inherit an environment with access keys embedded in application code, treat it as an incident — rotate immediately and migrate to roles.

🤖 AI / Agentic Angle

Agentic AI architectures create a new IAM design challenge: the agent execution role. A Bedrock Agent needs bedrock:InvokeModel, bedrock:Retrieve (for Knowledge Bases), lambda:InvokeFunction (for action groups), and potentially s3:GetObject (for document retrieval). The principle of least privilege applies strictly — an agent that only summarises documents should not have s3:DeleteObject. As you build multi-agent architectures (supervisor agent invoking sub-agents), each agent gets its own Role with scoped permissions, and sub-agent roles trust the supervisor's role ARN in their trust policies. ABAC can help here: tag Bedrock agents with their function and write policies that dynamically scope access based on those tags.

04 / PREREQUISITES

Prerequisites & Environment Setup #

AWS Account & Access Requirements

  • Account type: Any AWS account. IAM is global — not region-specific — though this guide uses ap-southeast-1 for all regional services.
  • Starting credentials: Either AWS root (only for initial IAM user/role creation if no IAM admin exists yet) or an IAM principal with iam:* permissions and sts:AssumeRole.
  • MFA: Root MFA must be active before doing anything else. Non-negotiable. MAS TRM §7.3.2 requires MFA for privileged access.
  • Organizations: The SCP sections of this guide require AWS Organizations. If your account is standalone (not in an Org), you can still follow all non-SCP sections.
  • IAM Access Analyser: Must be explicitly enabled per-region. We'll enable it in Section 05.
💰 Cost Warning

IAM itself is free — no charge for users, roles, policies, or API calls to IAM. However:

  • CloudTrail management events (IAM API calls): Free for the first trail's management events. A second trail: ~$2/100k events.
  • IAM Access Analyser: Free for basic findings. Unused access analysis: $0.20 per IAM role analysed per month.
  • AWS Config (IAM rules): $0.003 per configuration item recorded, ~$2/month for a typical IAM baseline.

The lab in Section 16 costs <$1 total. The IAM service itself will not incur charges.

Browser & Console Setup

  • Chrome or Firefox, not Safari (Safari has issues with some IAM policy editor features).
  • Console region selector: IAM is displayed globally regardless of selected region — but keep your console region at ap-southeast-1 to ensure IAM Access Analyser and related Config rules deploy to the right region.
  • Enable the IAM console's "Visual editor" + "JSON" toggle — you'll use both throughout this guide.
🌉 Bridge from Storage/Virtualisation

Setting up IAM for the first time ≈ initial SAN fabric configuration before first LUN provisioning. You don't provision storage before you have zoning, initiator groups, and masking policies. Similarly: establish IAM baseline (admin role, CloudTrail, Access Analyser, MFA on root) before provisioning any other AWS services. Getting the foundation wrong here propagates through every subsequent deployment.

🔥 IMDSv1 — The Breach Pattern Nobody Fixes

IMDSv1 allows any HTTP request from within an EC2 instance to the metadata endpoint (http://169.254.169.254/latest/meta-data/iam/security-credentials/ROLE-NAME) to return the instance's role credentials. A Server-Side Request Forgery (SSRF) vulnerability in any application on that instance — a misconfigured URL redirect, an open proxy, an unvalidated URL parameter — allows an external attacker to exfiltrate those credentials over the internet. This is exactly how the Capital One breach occurred. IMDSv2 requires a PUT request with a TTL-limited session token before GET requests are honoured, blocking SSRF. Enable IMDSv2-only at account level via EC2 settings or enforce via Launch Template.

Top IAM Error Catalogue

Deny AccessDenied: User is not authorized to perform: ACTION on resource ARN ▼

Root cause: The most generic IAM error. Causes (in order of frequency): (1) Missing identity policy — the role/user simply doesn't have an Allow for this action. (2) SCP block — an Organizations SCP restricts this action. (3) Permission Boundary — the boundary doesn't include this action even though the identity policy does. (4) Resource policy — a bucket/KMS key policy doesn't grant access to this principal. (5) Condition block — the action is allowed but a Condition (e.g., requires MFA, requires specific IP) evaluates to false.

Fix: Run aws iam simulate-principal-policy first — it reveals exactly which layer caused the deny and which statement matched. CloudTrail will show the full error including errorCode and errorMessage.

Prevention: Use the IAM Policy Simulator in the Console before deploying roles. Test both happy path (actions that should work) and negative path (actions that should be blocked).

STS Not authorized to assume role — AssumeRole call fails ▼

Root cause: Two-sided problem. Either: (a) the calling principal's identity policy doesn't have sts:AssumeRole on the target role ARN, or (b) the target role's trust policy doesn't include the calling principal. Cross-account failures almost always involve one side being missing.

Fix: Check both the caller's identity policy (does it Allow sts:AssumeRole on the target ARN?) AND the target role's trust policy (does it trust the caller's ARN/account?). Both must be present for cross-account assumption.

Prevention: When creating cross-account roles, test immediately with aws sts assume-role from the caller's account before deploying dependent infrastructure.

STS AccessDenied: sts:AssumeRole — ExternalId mismatch ▼

Root cause: The role's trust policy requires an External ID via StringEquals sts:ExternalId but the caller didn't provide it (or provided the wrong value). Happens when: (a) the External ID was rotated but the caller's config wasn't updated, or (b) a new automation tool assumes the role without passing the External ID.

Fix: Confirm the External ID in the trust policy matches what the caller is sending. Check --external-id parameter in CLI calls or the equivalent SDK parameter. Never log External IDs — treat them as secrets.

IAM IAM role changes not taking effect immediately ▼

Root cause: IAM's control plane has eventual consistency. Changes to policies, trust policies, and role attachments can take up to 60 seconds to propagate globally. CI/CD pipelines that create a role in one step and immediately use it in the next step hit this frequently.

Fix: Add a sleep 10 or equivalent retry with backoff after IAM create/update operations in automation. Use the aws iam get-role response to confirm the policy attachment before proceeding.

Weird one: In Terraform, aws_iam_role_policy_attachment completing doesn't guarantee IAM propagation. Use time_sleep resource with a 15–30 second wait when a role is immediately used by Lambda, EC2, or ECS in the same plan.

KMS Access denied on KMS key despite IAM policy allowing kms:Decrypt ▼

Root cause: KMS is different from all other AWS services: the KMS key policy is the primary access control. If the key policy doesn't explicitly include the principal or doesn't delegate to IAM ("arn:aws:iam::ACCOUNT:root" in the key policy), no amount of IAM policy grants will work. IAM policies for KMS only work when the key policy explicitly delegates control to IAM.

Fix: Check the KMS key policy first — does it include the calling principal directly, OR does it include "arn:aws:iam::ACCOUNT:root" which delegates to IAM? If neither, add the appropriate statement to the key policy.

Prevention: Always include the IAM delegation statement in new KMS key policies: "Principal": {"AWS": "arn:aws:iam::ACCOUNT:root"}, "Action": "kms:*". This allows IAM policies to control KMS access for the account's principals.

SCP Action blocked even though IAM policy explicitly allows it ▼

Root cause: A Service Control Policy in AWS Organizations is blocking the action. SCPs operate above IAM — even an explicit Allow in an IAM policy cannot override an SCP Deny. This catches engineers off-guard who test permissions in one account (not in the Org, or in a different OU) and assume it will work everywhere.

Fix: Check the SCPs attached to the account's OU: aws organizations list-policies-for-target --target-id ACCOUNT-ID --filter SERVICE_CONTROL_POLICY. Review each SCP for Deny statements covering your action. Fix requires updating the SCP (platform team/Organization management account access required).

Prevention: Document SCP restrictions in a runbook accessible to all engineers. Use the Organizations Policy Simulator in the Console to test SCP impact before deploying.

EC2 EC2 instance cannot retrieve role credentials — 401 from IMDS ▼

Root cause: Either: (a) no instance profile was attached to the EC2 instance at launch, (b) IMDSv2 is required but the application code uses the IMDSv1 URL without the token header, or (c) IMDS was disabled entirely via instance metadata options.

Fix: Check aws ec2 describe-instances --instance-ids INSTANCE-ID --query 'Reservations[*].Instances[*].IamInstanceProfile' — should return an ARN. If null, no profile attached. Attach an instance profile via Console (EC2 → Instance → Actions → Security → Modify IAM role). For IMDSv2: applications must issue a PUT to get a session token first — update SDK/IMDS calls accordingly.

Escalation Privilege escalation via IAM — a developer created an admin role ▼

Root cause: A developer with iam:CreateRole and iam:AttachRolePolicy permissions created a new role with AdministratorAccess and then assumed it. This is a privilege escalation — the developer now has more permissions than their identity policy grants. IAM Access Analyser's unused access feature and AWS GuardDuty (PrivilegeEscalation findings) will flag this.

Fix (immediate): Revoke the role, rotate the developer's credentials, review CloudTrail for what actions were taken under the elevated role. Fix (structural): Deploy Permission Boundaries on all developer-created roles. The DenyBoundaryDeletion statement in the boundary prevents self-escape.

Prevention: Never grant iam:AttachRolePolicy without simultaneously requiring a Permission Boundary condition: "Condition": {"ArnEquals": {"iam:PermissionsBoundary": "arn:aws:iam::ACCOUNT:policy/DeveloperBoundary-Policy"}}.

Common Misconfigurations That Cause Breaches

🪣

Public S3 Bucket via Resource Policy

Principal: * in a bucket policy makes it world-readable regardless of Block Public Access settings if the setting is misconfigured. Always use Block Public Access at the account level as a final backstop.

🔑

Over-Permissive EC2 Instance Role

An EC2 instance with AdministratorAccess or PowerUserAccess — if the instance is compromised (IMDSv1 SSRF, code execution), the attacker gets those permissions. Scope instance roles to exactly what the application needs.

🏢

Trust Policy: Principal = Root ARN for Whole Account

arn:aws:iam::ACCOUNT:root in a trust policy grants every IAM principal in that account the ability to assume the role. Almost never intended. Scope to specific role ARNs.

⏳

Never-Rotated Access Keys

Access keys with creation dates from 2019 are still active in some accounts. Every such key is a ticking time bomb. The credential report surfaces them; AWS Config iam-user-access-key-age enforces rotation.

🚪

No Permission Boundaries on Developer Roles

Developers with iam:* permissions who can create roles without boundary constraints can escalate to any privilege level. The fix is trivially implementable and nearly universally skipped.

🔓

KMS Key Policy Delegates to IAM But IAM Has *

If you grant kms:* on * in an IAM policy and the key policy delegates to IAM, any principal with that IAM policy can decrypt any KMS-protected data in the account. Scope KMS IAM actions to specific key ARNs.

15 / DISASTER RECOVERY

Disaster Recovery & Multi-Region #

IAM is a global service — IAM users, roles, and policies are global and not region-specific. This changes the DR story significantly.

IAM Resilience Characteristics

  • IAM is globally replicated: IAM entities are stored and replicated across all AWS regions. An AWS region outage does not destroy IAM configuration — it may cause temporary eventual consistency delays but not data loss.
  • STS is region-aware: While the global STS endpoint (sts.amazonaws.com) resolves to us-east-1, regional STS endpoints exist for each region. If us-east-1 has an outage and you're using the global endpoint, AssumeRole calls fail. Configure regional STS endpoints.
  • IAM Access Analyser is per-region: You must create an analyser in each region you use. Findings from one region are not visible in another.
  • CloudTrail is per-region unless multi-region trail: Create a multi-region trail to capture IAM API calls from all regions in one S3 bucket.

🌉 Bridge from Storage/Virtualisation

IAM's global resilience ≈ your enterprise directory (Active Directory) replicated across multiple domain controllers in multiple data centres. AD replication means identity management survives a single DC failure. IAM's global replication means IAM configuration survives a regional failure. But just as AD replication lag can cause authentication failures during convergence, IAM eventual consistency (up to 60 seconds) can cause transient failures in automation that creates roles and immediately uses them. The STS regional endpoint issue ≈ having your authentication proxy in one DC — if that DC fails, authentication fails. Distributed the proxy (regional STS) to match your workload distribution.

Pattern 2: Zero-Standing-Privilege via Just-in-Time Access

Business scenario: FSI compliance requires that no human has standing access to production databases. All access must be just-in-time, approved, and logged.

Implementation: An approval workflow (ServiceNow ticket or PagerDuty) triggers a Lambda that calls iam:AttachRolePolicy to add a scoped policy to the requestor's role for a specific time window. A Step Functions state machine manages the countdown. When the time window expires, a second Lambda removes the policy. All IAM changes captured in CloudTrail with the approval ticket ID as a session tag (sts:TagSession). The session tag appears in CloudTrail for every action taken during that window — providing complete accountability without standing access.

🤖 AI / Agentic Angle

As agentic architectures grow (sub-agents, supervisor patterns, multi-tool agents), IAM design becomes the critical security control. The key principle: each agent gets its own execution role with the minimum permissions for its specific tools. Session tags (sts:TagSession) allow you to inject agent run IDs into CloudTrail — every action the agent takes is traceable to the specific invocation that caused it. Combined with Bedrock Guardrails (content policies), you get both an identity audit trail and a content safety layer for AI workflows in regulated environments.

Anti-Pattern: The Single Shared Role for Everything

A common pattern in smaller organisations: one IAM role, AppDeployRole, used by CI/CD, Lambda functions, EC2 instances, and the developer team for "convenience." The permissions accumulate over time as each new use case adds its requirements. Within a year, it has S3:*, EC2:*, RDS:*, IAM read access, and SNS:*. A single compromise of any consumer of that role gives an attacker full access to all data in all those services across all environments. The fix is role disaggregation: one role per workload, per environment, per function. Never share roles between security boundaries.

19 / FAQ

Regular FAQ — Beginner Focused #

Beginner Is IAM free? ▼

Yes — IAM itself (users, roles, policies, API calls) is completely free with no limits. CloudTrail management events (which capture IAM API calls) are free for the first trail. IAM Access Analyser for external access is free. The only IAM-adjacent costs are Access Analyser unused access analysis ($0.20/role/month) and AWS Config IAM compliance rules (~$3–5/month). For a production FSI baseline, budget $15–25/month for the full monitoring stack.

Beginner What's the difference between an IAM User and an IAM Role? ▼

An IAM User is a permanent identity with long-lived credentials (a password and/or access key) tied to a specific person or application. An IAM Role is a temporary identity — nothing holds it permanently. Things "assume" a role to get short-lived credentials (1–12 hours) that expire automatically. In storage/virtualisation terms: a user ≈ a local Unix account with a permanent SSH key; a role ≈ a vSphere service account that issues Kerberos tickets. The rule: humans can have IAM Users (though IAM Identity Centre is better for organisations); workloads (EC2, Lambda, ECS) must use IAM Roles, never Users with access keys.

Beginner What does "implicit deny" mean? ▼

In IAM, if there is no explicit Allow statement for an action, access is denied by default — this is the "implicit deny." You don't need a Deny statement for most things; you just need to not have an Allow. The only time you explicitly Deny is when you want to override an Allow that exists somewhere else in the policy stack (e.g., an SCP Deny that overrides an IAM policy Allow, or a Deny statement that restricts certain conditions even when a broad Allow exists). Think of it like a firewall's default-deny: if there's no rule permitting the traffic, it's dropped without needing an explicit drop rule.

Beginner Do I need a VPC for IAM? ▼

No — IAM and STS are global services accessible over the internet. However, if you have workloads in a private VPC with no internet access (which is the correct pattern for production FSI), you need VPC Interface Endpoints for IAM (com.amazonaws.ap-southeast-1.iam) and STS (com.amazonaws.ap-southeast-1.sts). These endpoints let your private VPC resources call IAM APIs without routing through an internet gateway or NAT gateway.

Beginner What's the difference between a managed policy and an inline policy? ▼

A managed policy is a standalone policy with its own ARN — it can be attached to multiple roles/users and has up to 5 versions. AWS provides AWS-managed policies (like AmazonS3ReadOnlyAccess). An inline policy is embedded directly into a single role or user and is deleted with it. Best practice: use customer-managed policies for anything reusable; inline policies for permissions unique to one specific role. Avoid AWS-managed policies in production (too broad).

Beginner Can I test what my IAM policy allows without actually making API calls? ▼

Yes — two tools: (1) IAM Policy Simulator in Console (IAM → Policy Simulator) — select a role/user and simulate actions against resources. It shows exactly which policy statement caused Allow or Deny. (2) CLI: aws iam simulate-principal-policy. Note: the simulator does not evaluate SCPs, so a "simulated allow" may still fail in production if an SCP blocks it.

Architect When do I need both a resource policy AND an identity policy? ▼

For cross-account access: always both. The resource in Account B needs a resource-based policy explicitly trusting the caller's account/role, AND the caller in Account A needs an identity policy allowing the action. Same-account access is more flexible — either an identity policy or a resource policy alone is sufficient. The exception is KMS: key policy is always primary; IAM policies only work for KMS if the key policy delegates to IAM root.

20 / INTERVIEW Q&A

Principal Architect Interview Q&A #

Principal "How would you design IAM governance for 50 AWS accounts and 500 engineers?" ▼

Strong answer: AWS Organizations with OU structure matching security/compliance boundaries. IAM Identity Centre with SAML federation to Azure AD — no individual IAM user management. Permission Sets map to job functions (Developer, Operator, ReadOnly, SecurityOps) assigned at OU level. SCPs enforce guardrails: deny creation outside approved regions, deny disabling CloudTrail, deny removing Permission Boundaries. ABAC via principal tags handles team resource ownership without policy proliferation. Centralised CloudTrail Lake in a security account, EventBridge routing critical IAM events to SIEM, Access Analyser in every active region. Full MAS TRM §7.3, §12, §11 mapping documented for the compliance team.

Principal "A developer committed AWS access keys to a public GitHub repo. Walk me through your response." ▼

Immediate (within 5 minutes): Disable/delete the exposed key — do not just rotate. aws iam delete-access-key --access-key-id AKIAXXXXXXXX --user-name NAME. Parallel investigation (30 min): pull CloudTrail for that key since last known-good commit. Look for: unexpected API calls, unusual IPs, iam:CreateUser, sts:AssumeRole, s3:GetObject on sensitive buckets. Check GuardDuty. If non-authorised calls found → full incident response + MAS TRM 72hr breach notification assessment. Structural fix: access keys for workloads should not exist. Migrate to OIDC federation for CI/CD. Deploy git pre-commit hooks (detect-secrets). Enable GitHub Secret Scanning org-wide.

Principal "Explain ABAC and when you'd use it instead of RBAC in IAM." ▼

ABAC uses tags on principals and resources as policy condition variables. Instead of listing ARNs, you write "allow access where caller's Project tag matches resource's Project tag" using aws:PrincipalTag/Project vs aws:ResourceTag/Project. Use ABAC when: many principals need access to many resources following a consistent tag-expressible pattern — multi-tenant SaaS, environment isolation, cost centre ownership. ABAC scales without policy changes. Don't use ABAC when the access pattern can't be expressed as tag equality, or when tag governance is immature (anyone retagging resources can escalate access). Combine ABAC with AWS Organizations tag policies to restrict who can set sensitive tag keys.

Principal "What's a confused deputy attack and how does External ID prevent it?" ▼

The confused deputy: a third-party SaaS tool (cloud scanner) can be tricked by an attacker into assuming your role ARN, using its own legitimate AWS identity as cover. External ID prevents this: your role's trust policy requires sts:ExternalId = "YourSecretValue". The attacker doesn't know your External ID, so the AssumeRole call fails. The External ID is a shared secret proving the call comes from the legitimate context. Every cross-account role shared with third parties should have an External ID, stored in Secrets Manager and rotated periodically.

Principal "How does KMS access control differ from standard IAM?" ▼

KMS is the exception: the key policy is required and is the primary control. For most services, same-account access only needs an identity policy. For KMS, if the key policy doesn't explicitly grant access (or include the IAM delegation statement "Principal": {"AWS": "arn:aws:iam::ACCOUNT:root"}, "Action": "kms:*"), no IAM policy works — even AdministratorAccess. The IAM delegation statement tells KMS to defer to IAM for that account's principals. Without it, only principals explicitly listed in the key policy can use the key. This is the top debugging scenario when kms:Decrypt is in the IAM policy but access is denied.

Key Terraform IAM Patterns

  • Data sources over hardcoded ARNs: Always use data.aws_caller_identity.current.account_id — never hardcode account IDs. Makes modules portable across environments.
  • IAM eventual consistency: Add a time_sleep resource between role creation and resources that immediately use the role (Lambda, ECS). 15–30 seconds is usually sufficient.
  • prevent_destroy on Permission Boundaries: Prevents accidental destruction of the guardrail via terraform destroy. Requires explicit lifecycle override to remove.
  • Policy files vs jsonencode: Use file() for complex policies — easier to review in PRs and test independently. Use jsonencode() for simple inline trust policies.
