00 / GLOSSARY

Glossary & Key Terms #

Every networking term used in this guide is defined here. If you've worked with VLANs, routing tables, and firewall ACLs in a data center, the analogies will land immediately.

VPC — Virtual Private Cloud
An isolated, software-defined network within an AWS region. The fundamental network boundary for all your AWS resources.
≈ A vSphere Distributed Switch (vDS) or an entire VLAN-segmented network in your data center, but software-defined and region-scoped.
CIDR — Classless Inter-Domain Routing
The notation for IP address ranges (e.g., 10.0.0.0/16). The number after the slash is the prefix length — smaller number = larger range.
≈ Subnet mask notation in any networking equipment — same math, just expressed differently.
Subnet
A range of IPs within a VPC, bound to a single Availability Zone. Resources you deploy live inside subnets, not directly in the VPC.
≈ A VLAN within a switched network — a Layer-2-ish broadcast scope, except AZ-scoped instead of switch-scoped.
Availability Zone (AZ)
A physically isolated data center (or campus of DCs) within a region. ap-southeast-1 has three: 1a, 1b, 1c.
≈ A separate building with independent power, cooling, and network — like geographically separated DC sites.
Route Table
A set of rules that determine where network traffic from a subnet is directed. Each subnet must be associated with exactly one route table at a time.
≈ The routing table on a Layer-3 switch or router — destination CIDR maps to a next hop.
Internet Gateway (IGW)
A horizontally-scaled, redundant VPC component that allows communication between VPC and the internet. One IGW per VPC.
≈ The internet edge router/firewall pair in your DC — except managed and unbreakable.
NAT Gateway
A managed service that allows resources in private subnets to initiate outbound traffic to the internet, while preventing inbound. Per-AZ resource — costs ~$32/month each plus data transfer.
≈ A SNAT pool on a perimeter firewall — outbound source NAT only, no inbound.
Security Group (SG)
A stateful virtual firewall at the ENI level. Default: deny all inbound, allow all outbound. Stateful = return traffic always allowed.
≈ A vSphere NSX distributed firewall rule — applied per-vNIC, stateful, allow-only.
NACL — Network ACL
A stateless packet filter at the subnet level. Both inbound and outbound rules required. Numbered priority, lowest first.
≈ A traditional ACL on a router or switch — stateless, numbered rules, evaluated in order.
ENI — Elastic Network Interface
A virtual network card that can be attached to an instance. Has a private IP, optional public IP, MAC address, and one or more SGs.
≈ A vNIC on a VM — same concept, but movable between instances.
VPC Endpoint
A private connection from your VPC to AWS services without traversing the public internet. Two types: Gateway (S3, DynamoDB only) and Interface (everything else).
≈ A direct fiber link to a service provider that bypasses the public internet — same data, lower latency, no NAT.
VPC Peering
A direct network connection between two VPCs. Non-transitive: A↔B and A↔C does not give B↔C.
≈ A point-to-point link between two networks — VPC peering is the cloud equivalent of patching two switch fabrics together with a single cable.
Transit Gateway (TGW)
A regional network hub connecting many VPCs and on-prem networks transitively. Replaces full-mesh VPC peering at scale.
≈ A core router in a hub-and-spoke WAN topology — every site connects once to the hub.
Elastic IP (EIP)
A static, public IPv4 address you allocate to your account and associate with an ENI/instance. Persists across stop/start.
≈ A statically assigned public IP from your ISP — except you "rent" it from AWS.
VPC Flow Logs
Captures metadata about IP traffic in/out of ENIs in your VPC. Logs the 5-tuple, action (ACCEPT/REJECT), and bytes/packets — not the payload.
≈ NetFlow/sFlow on a switch — flow records, not packet captures.
Route 53 Resolver
The DNS service inside every VPC, accessible at VPC_CIDR_BASE+2 (e.g., 10.0.0.2). Inbound/outbound endpoints enable hybrid DNS.
≈ The DNS forwarders in your DC — every VPC has its own resolver service.
PrivateLink
Mechanism behind Interface VPC Endpoints. Exposes a service in one VPC as a private endpoint in another VPC or account.
≈ A reverse proxy that lives inside your network and tunnels to a service — except managed by AWS.
Default VPC
An auto-created VPC in every region. Has IGW, public subnets in each AZ, default security group permissive enough to be dangerous.
≈ The default lab VLAN your DC team set up "for testing" that everyone keeps using in production.
01 / CONCEPT

Concept & Mental Model #

What Problem Does VPC Solve?

Before AWS introduced VPCs in 2009, EC2 instances launched into a flat shared network — every customer's instances on the same Layer 2 broadcast domain, distinguished only by security groups. There was no concept of network isolation, no way to use private IP ranges of your choosing, no way to extend an on-premise network into AWS. This was called EC2-Classic and was deprecated entirely in 2022. Every new account is VPC-only.

A VPC solves three problems simultaneously: (1) network isolation — your network is yours, no other customer can route packets into it; (2) addressing freedom — you choose your own private IP ranges, including overlapping ones across VPCs if you want; (3) hybrid connectivity — you can extend your on-premise network into AWS as if it were another data center site, with consistent IP space and routing. Everything you build in AWS lives inside a VPC. There are no exceptions for compute, databases, load balancers, ECS tasks, EKS pods, RDS instances, or any other VPC-native resource.

What Did Engineers Do Before VPCs Existed?

In on-premise data centers, the equivalent of a VPC is the combination of: a VLAN (Layer 2 isolation), a router with VRFs (Layer 3 isolation), an internal firewall (security boundary), and a routing protocol or static routes for inter-segment traffic. Building this out for a single environment took weeks — physical cabling, switch configuration, firewall rules, change requests through network operations. AWS VPCs collapse all of that into a single API call. The trade-off: you don't get to see the underlying physical topology, and you must trust AWS's implementation. For most workloads, that trade-off is fine. For ultra-low-latency or specialised hardware-dependent workloads (HPC, certain GPU clusters), bare-metal options (Outposts, Direct Connect to colo) still exist.

The Three Concepts You Must Internalise

Concept 1 — A VPC is regional, but subnets are zonal. The VPC itself spans an entire region, but every subnet belongs to exactly one Availability Zone. This is the most common point of confusion for new architects. When you "deploy a VPC across multiple AZs," what you're actually doing is creating multiple subnets in different AZs within the same VPC. The VPC has no AZ affinity — it's the subnets that do.

Concept 2 — Routing happens at the subnet level, not the instance level. A route table is associated with one or more subnets. Every packet leaving an instance in that subnet is evaluated against that subnet's route table. The most specific match wins (longest prefix match, just like any router). The default route (0.0.0.0/0) is the catch-all. This is why "public subnet" vs "private subnet" is purely a matter of routing — a subnet is "public" if its route table has 0.0.0.0/0 → IGW, and "private" if it has 0.0.0.0/0 → NAT GW (or no internet route at all).

Concept 3 — Security Groups and NACLs are different things solving different problems. Security groups are stateful, allow-only, applied at the ENI level — they're your primary firewall. NACLs are stateless, allow/deny, applied at the subnet level — they're a secondary, broader-stroke control. You'll use SGs for 95% of your rules. NACLs are reserved for blanket blocks (e.g., "block all traffic from this country's CIDR ranges at the subnet edge") or for compliance requirements that demand stateless filtering.

💡 Why This Matters
Mistakes in these three concepts are the source of 80% of VPC misconfigurations. Engineers who think "the VPC is in AZ-a" deploy single-AZ workloads thinking they're multi-AZ. Engineers who think "the instance has its own routing" troubleshoot by looking at route tables on the wrong layer. Engineers who treat NACLs and SGs as interchangeable end up with permissive NACLs covering for tight SGs, then loosen one and break the other. Get these three right and the rest of VPC follows logically.

Common Misconceptions

  • Misconception: "A VPC is a firewall." Reality: A VPC is a network. The firewall is the security group (and NACL, optionally). The VPC is the medium in which firewalled resources live.
  • Misconception: "Private subnets are unreachable from the internet." Reality: Private subnets cannot reach the internet directly, but they can be reached via load balancers in public subnets, VPC endpoints, or Transit Gateway connections. Privacy is about outbound, reachability is a separate question.
  • Misconception: "I can just use the default VPC for production." Reality: The default VPC has insecure defaults (every AZ has a public subnet, default SG allows all from itself across all default-VPC instances, default NACL allows all). For MAS TRM compliance and any production workload, never use the default VPC. Delete it from new accounts.
  • Misconception: "Bigger CIDR = better, just use /16 everywhere." Reality: Bigger CIDR means more wasted IP space and reduces the number of VPCs you can have without overlap when you connect them via TGW or Direct Connect. CIDR planning is a real skill — overprovisioning hurts you later when you can't connect to a vendor's network because their /16 overlaps yours.
  • Misconception: "VPC peering scales fine." Reality: VPC peering is non-transitive. With 5 VPCs, you need 10 peering connections. With 10 VPCs, 45. With 20 VPCs, 190. This is why TGW exists — it converts the mesh into a star topology.

The Apartment Building Analogy

Picture a large apartment building. The building itself is the VPC — a defined property, with its own address range. Each floor is an Availability Zone — physically separate, with independent power and water risers. Each apartment on a floor is a subnet — bound to that floor, has its own door (route table) determining which corridors residents can use. Residents are EC2 instances — they live in apartments, share the floor's infrastructure, and can be moved (re-attached ENIs). The lobby with the front door is the IGW — the way in and out of the building. The valet/concierge for outbound trips is the NAT Gateway — residents can ask the concierge to fetch something from the city (outbound), but the city can't walk in unannounced (no inbound). The apartment's keypad lock is the security group — stateful, lets in only authorised guests, remembers who you let in. The building's perimeter wall is the NACL — broader, simpler, doesn't remember anyone, just enforces the wall rules.

🌉 Bridge from Storage/Virtualization

If you've designed a multi-tier application network in a VMware environment, you already understand VPC mentally — you just don't know the AWS naming yet. A VMware vSwitch with VLANs is your VPC + subnets. A vSphere distributed firewall rule is your security group. A VLAN trunk to the core switch is your IGW. NAT on the edge firewall is your NAT Gateway. SRM-replicated networks across DC sites are your multi-AZ subnets. The conceptual gap closes quickly. Where AWS adds genuine new value is in the speed of provisioning (minutes vs weeks) and the API-first model (everything is an idempotent API call, nothing is "go to the wiring closet"). The discipline of CIDR planning, route hierarchy, and firewall depth is identical to what you've already done in a DC for a decade.

💡 Why This Matters
At Day-1 implementation work for FSI clients, the VPC design is the first artefact you produce. CIDR allocation, AZ distribution, subnet tier model, route table strategy, endpoint placement, and connectivity model — all decided in week one and difficult to change without a re-platform later. Getting this right separates Principal Architects from operators.

Packet Flow — How a Request Actually Travels

ASCII Flow — User → App → DB
  1. User in Singapore makes HTTPS request to api.example.com
  2. Route 53 resolves → ALB DNS name (alias record)
  3. Packet arrives at AWS edge → routed to ALB ENI in Public subnet 10.0.0.X (AZ-a)
     ├── Subnet route table: 0.0.0.0/0 → igw-xxx (IGW)
     └── Source IP preserved up to ALB; ALB terminates TLS, opens new connection to target

  4. ALB forwards to target IP in Private subnet 10.0.10.X (AZ-a)
     ├── Same VPC; no IGW/NAT involved
     ├── Target SG: allow port 8080 from ALB SG (SG reference, not CIDR)
     └── Local route: 10.0.0.0/16 → local (intra-VPC, free, no transfer charge intra-AZ)

  5. App on EC2 needs to call DynamoDB (over the internet, normally)
     ├── DynamoDB has a Gateway VPC Endpoint configured
     ├── Route table for Private subnet has: dynamodb-prefix-list → vpce-xxx
     └── Traffic goes via PrivateLink, never touches IGW or NAT — saves money and stays private

  6. App needs to query RDS in Isolated subnet 10.0.20.X (AZ-a)
     ├── RDS SG: allow 5432 from App SG (SG reference)
     ├── No internet route in Isolated subnet — RDS unreachable from outside VPC entirely
     └── Local route: same VPC, intra-AZ = free

  7. App needs to install OS patch (calls yum repo on internet)
     ├── Outbound 443 to repo
     ├── Subnet has: 0.0.0.0/0 → nat-xxx (NAT GW in same-AZ Public subnet)
     ├── NAT GW source-NATs to its EIP, packet exits via IGW
     ├── Response returns to NAT GW (stateful), then back to App instance
     └── BILLING: NAT GW data processing $0.045/GB + cross-AZ transfer if NAT in different AZ

Control Plane vs Data Plane

PlaneWhat It IsFailure Impact
Control PlaneVPC API: CreateSubnet, CreateRoute, AuthorizeSecurityGroupIngress. Runs in AWS-managed regional control plane.Cannot make config changes. Existing data plane keeps running. Rare outages (look for AWS Health Dashboard alerts).
Data PlaneThe actual packet forwarding inside your VPC. Implemented in Hyperplane (AWS's distributed network virtualisation layer).Packets stop flowing. Extremely rare; AZ-isolated. Even during control plane outages, existing routes continue to function.
💡 Why This Matters
The control plane / data plane split explains why "I made a route table change and it took effect immediately for new connections, but my existing SSH session was unaffected" — the data plane evaluates the route table per-flow, not per-packet. It also explains why you can't rely on the control plane during a regional incident, but you can rely on the data plane: existing config keeps working, you just can't change it. This is structurally identical to how Cisco N7K supervisors work — control plane on the supervisor, data plane in the linecards. If the supervisor restarts (NSF), forwarding continues.

3.3 Canonical Patterns & Pairings

🏛️
Three-Tier Web Application
Public (ALB) → Private (App tier) → Isolated (RDS). Standard for any web app/API. Each tier in 3 AZs. Pair: VPC + ALB + ECS/EC2 + RDS Aurora.
🔄
Hub-and-Spoke (Multi-VPC)
TGW as hub; one VPC per environment/team/workload. Centralised egress and DX. Pair: TGW + multiple VPCs + Network Firewall in egress VPC. The standard for any organisation with 5+ VPCs.
🛡️
Inspection VPC Pattern
All inter-VPC and egress traffic routed through a dedicated Inspection VPC running AWS Network Firewall or 3rd-party (Palo Alto, Fortinet). Mandatory for FSI compliance.
🌐
Hybrid Connectivity
On-premise → DX → DX Gateway → TGW → VPCs. Consistent IP space, no NAT, BGP route exchange. Pair: VPC + DX + TGW + Route 53 Resolver inbound endpoints for DNS.
📡
Centralised VPC Endpoints
One VPC hosts all Interface Endpoints (KMS, SSM, ECR, etc.); spokes access via TGW. Reduces $7.50/AZ × N-services × N-VPCs to a single set. Pair: TGW + endpoint VPC + private hosted zone for endpoint DNS.
⚠️
Anti-Pattern: Single-AZ "for cost"
Teams sometimes deploy production in a single AZ "to save on NAT/cross-AZ costs." This is broken architecture — one AZ failure = full outage. The savings are pennies; the outage is career-ending.

  • Avoid multi-cloud VPCs as a default — managing two cloud network models doubles operational burden. Use only when business mandates.

Prerequisites & Environment Setup #

⚠️ Cost Warning — VPC Components That Bill From Creation

The VPC itself is free. What costs money:

  • NAT Gateway: ~$32/month per NAT GW (24/7) + $0.045/GB processed. Three AZs = $96/month base + data charges. This is by far the dominant cost in most VPCs.
  • Interface VPC Endpoints: $0.014/hour per endpoint per AZ = ~$10/month per endpoint per AZ. Three AZs × 5 endpoints = $150/month.
  • Elastic IP: Free if attached to a running resource; $0.005/hour (~$3.65/month) if unattached.
  • VPN Site-to-Site: $0.05/hour per connection ≈ $36/month + data charges.
  • Direct Connect: Port hour cost ($0.30–$2.25/hr depending on speed) + data transfer.
  • Transit Gateway: $0.05/hour per VPC attachment ($36/month each) + $0.02/GB processed.
  • VPC Flow Logs to CloudWatch: $0.50/GB ingestion (expensive); S3 destination is much cheaper at $0.023/GB storage.

The CIDR Planning Discipline — Most Important Prerequisite

Before you create your first VPC at scale, you need a documented IP allocation plan that anticipates:

  • How many VPCs you'll eventually have (count environments × workloads × accounts; double it)
  • Whether they'll all need to talk to each other or to on-premise (if yes, no overlap allowed)
  • Whether you'll connect to vendor/partner networks (avoid common ranges like 10.0.0.0/16, 172.31.0.0/16)

🌉 Bridge from Storage/Virtualization

Insecure Defaults AWS Ships

🚨 What AWS Ships That You Must Fix on Day 1
  • Default VPC in every region: Has IGW, public subnets in every AZ, default SG that allows all from itself. Used "for testing" then production resources accidentally land there. Delete it from every account on day 1.
  • Default Security Group allows itself: Anything in default SG can talk to anything else in default SG on any port. Sneaky. Remove all inbound rules from default SG and tag it "DO NOT USE".
  • Flow Logs disabled: Indefensible from a compliance standpoint. Always enable on creation. Use S3 destination — CloudWatch Logs is 20× the cost.
  • NAT Gateway billing trap: Default cost is ~$32/month base, BUT data processing at $0.045/GB. A single chatty app can rack up $1000s/month. Always set Cost Explorer alerts for NAT GW data processing.
  • Open egress on default SG: Default SG allows all outbound to 0.0.0.0/0. For zero-trust egress, custom SGs should restrict outbound to only required destinations (e.g., port 443 to specific endpoints, not all internet).
  • VPC Endpoint default policy = full access: Means anyone with API permissions in your VPC can use the endpoint to access ANY S3 bucket in ANY account globally. Always scope endpoint policies.

The Session

You log into the AWS Console, switch to ap-southeast-1. You navigate to VPC service. You create the VPC vpc-prod-sg-1 with CIDR 10.65.0.0/16. You create 9 subnets across 3 AZs. You create the IGW and attach it. You allocate 3 EIPs and create 3 NAT Gateways. So far, smooth.

You create rt-public, add the 0.0.0.0/0 → IGW route, and associate the 3 public subnets. You create rt-private-1a with route 0.0.0.0/0 → natgw-1a, associate sn-private-1a. You move quickly through 1b and 1c. You create rt-isolated with no internet route, associate the 3 isolated subnets.

You launch a test EC2 instance into sn-private-1a with a security group that allows SSH from your bastion. You SSH in via Session Manager. You try:

$ curl -v https://www.example.com
* Could not resolve host: www.example.com
curl: (6) Could not resolve host: www.example.com

The Misconfiguration Surfaces

🔴 DNS resolution failed — but is the issue DNS or routing?
Your first instinct might be to check DNS. But the symptom on a private instance with no internet route is identical whether the issue is DNS, NAT GW, or route table. Always systematically check from the bottom of the stack up.

You start at the route table:

bash
$ aws ec2 describe-route-tables \
    --filters "Name=association.subnet-id,Values=subnet-xxx" \
    --query 'RouteTables[0].{Name:Tags[?Key==`Name`]|[0].Value,Routes:Routes}'

{
  "Name": "rt-private-1a",

    { "DestinationCidrBlock": "10.65.0.0/16", "GatewayId": "local", "State": "active" }

}

You forgot to add the 0.0.0.0/0 route to rt-private-1a. The instance has no path to the internet. You go back to the Console:

Console fix
VPC → Route Tables → rt-private-1a → Routes tab → Edit routes → Add route:
  Destination: 0.0.0.0/0
  Target: NAT Gateway → natgw-1a
  Save

Back in the test instance:

bash

The Lesson

This is the most common "first VPC" mistake — creating route tables but forgetting the 0.0.0.0/0 entry. The resource works (LB-style health checks pass for intra-VPC), but anything that needs internet (yum updates, calls to third-party APIs, even DNS to public servers) fails silently. Symptoms vary: hung connections, DNS timeouts, package manager errors. The root cause is always the same: missing route. Symptom-driven debugging will lead you astray; systematic stack-walk debugging finds it in 30 seconds.

Troubleshooting & Failure Modes #

Debug Runbook — First 5 Checks

🔍 The Diagnostic Stack-Walk
Always check in this order. Skipping a layer is how you waste hours.
  1. Subnet route table — Does the subnet's RT have the right routes? (Most common issue.)
  2. Security Group on the source ENI — Outbound rules allow the destination?
  3. Security Group on the destination ENI — Inbound rules allow the source?
  4. NACL on source AND destination subnets — Both directions allowed (NACLs are stateless)?
  5. NAT Gateway / IGW health — State = "available"?

Top Errors

No internet from private subnet

Symptom: Instance in private subnet — curl times out, DNS fails, yum can't reach repos.

Root cause: Three possibilities, in order of likelihood: (1) route table missing 0.0.0.0/0 → NAT GW, (2) NAT GW in different AZ that's down, (3) instance SG egress doesn't allow 443 to 0.0.0.0/0.

Fix: Verify route table has 0.0.0.0/0 → nat-xxx; verify NAT GW state = available; verify SG allows outbound 443.

Prevention: Use Terraform with explicit route resources — the missing route surfaces in plan output before apply.

CIDR overlap on VPC peering / TGW attachment

Symptom: CreateVpcPeeringConnection or CreateTransitGatewayVpcAttachment fails with InvalidVpcConfiguration.

Root cause: Two VPCs with overlapping CIDRs (e.g., both have 10.0.0.0/16). Cannot route between them — destination is ambiguous.

Fix: Re-IP one of the VPCs (painful — requires migrating all resources) OR use PrivateLink instead of routing (preserves VPC isolation).

Prevention: Org-wide CIDR allocation document maintained centrally. Every new VPC's CIDR is approved against the document before creation.

⚠️ Subnet too small — running out of IPs

Symptom: EC2 launch fails with InsufficientFreeAddressesInSubnet. ENI creation fails for new ECS tasks/Lambda functions.

Root cause: Subnet CIDR too narrow. Common when /28 or /27 subnets are used for app tier (only 11 or 27 usable IPs).

Fix: Cannot resize a subnet. Either add a new larger subnet to the same RT in the same AZ, or migrate workloads to a new VPC with bigger subnets.

Prevention: /24 minimum for any subnet hosting compute. /28 acceptable only for TGW attachment subnets where only TGW ENIs live.

⚠️ NAT Gateway data charges exploded — Cost Explorer shock

Symptom: NAT GW data processing charge of $5,000+/month appears unexpectedly.

Root cause: An app is making large data transfers through the NAT GW. Common culprits: (1) container images pulled from public registries instead of ECR via VPC endpoint, (2) S3 access via NAT instead of S3 Gateway endpoint, (3) chatty third-party API integrations, (4) cross-region replication going via NAT.

Fix: Enable Flow Logs analysis to identify top destinations. Add VPC endpoints for high-traffic AWS services (S3, ECR, CloudWatch). For non-AWS destinations, evaluate if traffic can be reduced or routed via DX/peering.

Prevention: Cost Explorer alarm on EC2-Other → NAT Gateway data processing > $X/day. Tag NAT GW to track ownership.

⚠️ Instances in private subnet can't reach RDS in isolated subnet

Symptom: App connection to RDS times out. App is in private tier, RDS in isolated tier, both in same VPC.

Root cause: Almost always SG, not routing. Intra-VPC traffic always works at the routing layer (local route is automatic). The issue is the RDS SG doesn't allow 5432 from the App SG.

Fix: RDS SG inbound rule: TCP 5432, source = sg-app (SG reference, not CIDR).

Prevention: Always use SG-to-SG references for intra-VPC. CIDR-based rules in the same VPC are an anti-pattern.

⚠️ NACL blocking ephemeral return traffic (the classic NACL gotcha)

Symptom: Outbound connections initiated from instance fail. Inbound TCP handshakes fail mid-handshake. SG looks correct.

Root cause: NACL is stateless. Outbound rule allows port 443; inbound rule must explicitly allow ephemeral return traffic on ports 1024-65535. Many people forget this and only set inbound for 80/443.

Fix: NACL inbound rule: allow TCP 1024-65535 from 0.0.0.0/0.

Prevention: If unsure, leave NACLs at default (allow all) and rely on SGs (stateful). NACLs are an advanced control — only use them when you understand stateless filtering.

⚠️ The Weird One: VPC Endpoint Private DNS not resolving

Symptom: Created Interface VPC Endpoint for KMS. Application still hits public KMS endpoint. nslookup returns public IP.

Root cause: One of three things: (1) VPC enableDnsHostnames or enableDnsSupport is OFF, (2) endpoint's "Enable Private DNS" checkbox not ticked at creation, (3) custom Route 53 DHCP option set overrides AmazonProvidedDNS — instance is using on-prem DNS that doesn't know about VPC endpoint.

Fix: Verify VPC DNS settings ON; verify endpoint Private DNS enabled; check DHCP option set — if custom, ensure AmazonProvidedDNS or VPC's resolver IP (CIDR_BASE+2) is in the list.

Prevention: Standard checklist for new VPCs always includes verifying DNS settings before adding endpoints.

⚠️ The Weird One: TGW route propagation vs static route

Symptom: VPC attached to TGW. Route table shows the route. Traffic still doesn't reach the destination VPC.

Root cause: TGW route tables have two routing mechanisms: static routes (manually added) and route propagations (auto-learned from attachments). If the propagation is enabled but the TGW route table you're using doesn't have an association to your VPC's attachment, you don't see the route.

Fix: TGW → Route Tables → check Associations tab AND Propagations tab. Both must include the relevant attachment.

Prevention: Document your TGW route table strategy — which attachments associate with which RT, which propagate to which RT — before building. TGW is unforgiving when this gets complicated.

-- Top 20 source IPs sending REJECTED traffic in the last 24 hours
SELECT srcaddr, SUM(CAST(packets AS bigint)) AS total_packets,
       COUNT(DISTINCT dstaddr) AS unique_dst
FROM vpc_flow_logs
WHERE action = 'REJECT'
  AND FROM_UNIXTIME(start) > CURRENT_TIMESTAMP - INTERVAL '1' DAY
GROUP BY srcaddr
ORDER BY total_packets DESC
LIMIT 20;

-- Suspicious: any internal IP scanning many destination ports
SELECT srcaddr, COUNT(DISTINCT dstport) AS unique_ports_targeted
FROM vpc_flow_logs
WHERE srcaddr LIKE '10.65.%'

HAVING COUNT(DISTINCT dstport) > 50
ORDER BY unique_ports_targeted DESC;

  AND FROM_UNIXTIME(start) > CURRENT_TIMESTAMP - INTERVAL '7' DAY
GROUP BY dstaddr
ORDER BY gb_transferred DESC
LIMIT 20;

Cost Traps

⚠️ The Cross-AZ Tax

$0.01/GB each direction means a single ALB → cross-AZ target generates $0.02/GB total. At 1 TB/day, that's $20/day = $600/month JUST for cross-AZ traffic that adds zero value over same-AZ. Always: NAT GW per AZ, ALB target groups with same-AZ preference where supported, RDS reads from same-AZ replica when possible.

⚠️ NAT GW Without S3 Gateway Endpoint

If your private instances pull from S3 via NAT GW (because you forgot the Gateway Endpoint), you pay $0.045/GB for NAT processing. With a free Gateway Endpoint, that traffic is $0. Apps that ship multi-GB ML models or container images can save hundreds/month with this single change.

⚠️ Flow Logs to CloudWatch Logs

The Console wizard often defaults to CloudWatch Logs. Ingestion is $0.50/GB. For a busy VPC processing 10 TB/month of traffic, that's $5,000/month of LOG INGEST charges. To S3: same data costs ~$235/month. 21× cheaper. Always S3.

At What Scale Does VPC Break?

VPC itself doesn't break — it's effectively unlimited for most practical purposes. What hits scale issues:

  • NAT GW connection ceiling: 55k concurrent connections to a single destination. A microservice fleet calling one third-party API can hit this and get timeouts. Solution: spread across multiple NAT GWs, use VPC endpoints where possible, or use Network Firewall.
  • Route table size: 50–1000 routes. TGW route propagation from many VPCs can blow this. Solution: route summarisation (use /16 in route table instead of dozens of /24s).
  • VPC peering at >10 VPCs: Mesh becomes operationally infeasible. Solution: TGW (it's why TGW exists).

Common Misconfigurations That Cause Breaches

🚨 Hall of Shame
  1. Database in public subnet: Sometimes happens when a developer launches RDS using "default subnet group" which includes public subnets. RDS becomes internet-reachable. Fix: dedicate "isolated" subnet group to RDS only.
  2. Security group with 0.0.0.0/0 on database port: "Just for testing" left in production. Common breach vector. Use SG-to-SG references always.
  3. NACL "allow all" combined with SG misconfiguration: Default NACL allows all; SG misconfig has no second line of defence. Either tighten NACL or always defend in depth at multiple layers.
  4. VPC peering with overly permissive routes: "10.0.0.0/8" routes added to peering accidentally allowing access to every VPC. Use specific /16 or /24 in peering routes.
  5. VPC endpoint with default policy: Allows access to ANY S3 bucket in ANY account. Attacker exfiltrates data through your endpoint to their bucket. Always scope policies.
  6. Flow Logs disabled: Breach happens. No forensic data. Six-figure incident response bill that could have been a post-mortem report.
💼 Career Application
Security architecture interviews: "Walk me through your defence in depth model for a financial services VPC." Strong answer: "Account boundary via SCPs, network perimeter via Network Firewall in Inspection VPC, subnet boundary via NACLs for known-bad blocking, ENI level via Security Groups (the primary control), application level via WAF on ALB, data level via KMS+IAM, audit via Flow Logs + GuardDuty + Security Hub mapped to MAS TRM controls." That's the layered story interviewers want — generic answers stay at "Security Groups."

Disaster Recovery & Multi-Region #

VPC Itself Has No Backup

A VPC is not a stateful resource — there's no "backup VPC" concept. What you back up is the VPC configuration as code (Terraform state in S3 + Git). Recovery from a region-wide disaster means re-applying your IaC to a different region, not "restoring" a VPC.

DR Runbook Outline

  1. Detection: CloudWatch + Route 53 health checks identify region-level failure (multi-AZ VPC unreachable).
  2. Decision: Incident commander declares failover; runbook executed.
  3. Activation: If pilot light: scale up DR ASGs; if cold: terraform apply to DR region.
  4. Data: Verify RDS read replica promoted; S3 cross-region replication caught up.
  5. DNS: Update Route 53 to point to DR ALB.
  6. Validation: Synthetic monitoring confirms DR region serving traffic.
  7. Communication: Stakeholders notified; status page updated.
  8. Failback: When primary recovers, gradual traffic shift back; data resync; documented.
🌉 Bridge from Storage/Virtualization
VPC DR is conceptually identical to VMware SRM cross-site failover, except your recovery plan is Terraform code, not SRM Recovery Plans. The discipline is the same: maintain accurate documentation of what's in production, replicate state (storage replication ≈ Terraform state in S3 + RDS replication), test regularly via DR drills, document failback procedure. The big difference: AWS regions are far more autonomous than VMware sites — there's no shared dependency that can fail and take both sites with it. That's a feature.

Architectural Patterns & Real-World Designs #

Pattern 1: FSI Production VPC (MAS TRM Compliant)

The reference architecture for any MAS TRM-regulated workload at Netrust scale. Three AZs, three tiers, full audit logging, Inspection VPC for egress, TGW connectivity to other accounts.

  • VPC: /16 in production OU CIDR allocation (e.g., 10.65.0.0/16)
  • Subnets: 3 public, 3 private, 3 isolated, 3 TGW-attachment (/28)
  • NAT Gateways: 3 (one per AZ); routes to Inspection VPC for L7 inspection (centralised egress pattern)
  • VPC Endpoints: S3, DynamoDB Gateway; KMS, SSM, ECR, SecretsManager Interface
  • Flow Logs: All traffic, S3 destination, custom format, KMS-CMK encrypted
  • Connectivity: Attached to org TGW for cross-account; DX gateway for on-prem
  • Compliance: AWS Config rules enforce subnet tiering tags, Flow Logs enabled, default SG locked

Pattern 2: Hub-and-Spoke with Inspection VPC

The standard for any multi-VPC organisation with compliance requirements. All inter-VPC and egress traffic flows through a central Inspection VPC running AWS Network Firewall.

  • Inspection VPC: Hosts AWS Network Firewall endpoints; receives all routes via TGW
  • Egress VPC: Centralised NAT Gateways; one per AZ; all spokes route 0.0.0.0/0 here
  • Endpoint VPC: Hosts shared Interface VPC Endpoints; spokes resolve service DNS to endpoints here
  • Spoke VPCs: Workload VPCs with no NAT GW or endpoints of their own (cost saving)
  • Trade-off: Significant cost saving on duplicate endpoints/NAT GWs vs added complexity and TGW data charges

Pattern 3: AI/Agentic Workload VPC

VPC layout for self-hosted LLM inference fleet (Ollama, vLLM) plus agentic orchestration:

  • Public: ALB only — single entry point
  • Private (GPU): g5/g6 instances running inference; large CIDR (/22) — GPU clusters can scale to dozens of nodes
  • Private (Orchestration): ECS/EKS running LangChain/CrewAI; small fleet
  • Isolated: Aurora for agent memory/state; OpenSearch for vector embeddings
  • VPC Endpoints: Bedrock (Interface), S3 (Gateway for embedding storage), KMS
  • NAT GW: minimal — most AWS service traffic goes via endpoints; only reaches NAT for HuggingFace/external LLM API calls
  • Why this matters: AI workloads have very different traffic patterns — large outbound to model repos, large internal east-west between inference nodes and vector stores. CIDR planning must accommodate both.
🤖 AI/Agentic Angle
VPC design for AI workloads is increasingly distinct from traditional web app VPCs. Inference traffic patterns are bursty (large model loads on cold start, then sustained chat sessions). Vector DB traffic is east-west heavy (every query reads thousands of embeddings). Placement matters: GPU instances and vector DBs should be same-AZ to avoid cross-AZ data transfer charges that compound at every embedding lookup. As Netrust's AI initiatives grow, expect VPC patterns to evolve — what works for traditional app VPCs needs adjustment for AI fleets.

Anti-Pattern: The Single Mega-VPC

⚠️ "We'll just put everything in one big VPC"
Tempting because it avoids TGW complexity. The problem: blast radius. One misconfiguration affects all workloads. One DDoS exhausts NAT GW capacity for everyone. Compliance auditors hate it because tier separation by tags is much weaker than tier separation by VPC. Limit each VPC to one workload + environment combination.

Interview & Architect-Caliber Q&A #

Claim: CIDR planning is a one-time decision that locks in your scaling and connectivity options for years. Get it right on day 1.

Reasoning: Allocate a single supernet to the organisation (e.g., 10.64.0.0/10) — this gives you 4 million IPs to subdivide. Reserve sub-supernets per environment: prod /12, non-prod /12, sandbox /12, DR /12. Within each /12, allocate /16 per VPC (256 VPCs possible per /12). Within each /16 VPC, /24 subnets per tier per AZ. Avoid common ranges: 10.0/16, 172.31/16, 192.168/16 — these collide with default VPCs, vendor networks, and home routers. Document the allocation centrally; treat it as immutable.

Trade-off: Generous allocation wastes IP space; tight allocation creates collisions later. The cost of wasted IPs in private space is zero — you have 16M+ private IPs available. The cost of a CIDR collision is a re-IP project.

Conclusion: Always over-allocate. The 30-minute planning meeting saves you from a multi-week migration three years later.
Claim: Transit Gateway when you have more than ~5 VPCs needing connectivity, or when you need transitive routing.

Reasoning: VPC peering is non-transitive and full-mesh: N VPCs need N(N-1)/2 peerings — 5 VPCs = 10, 10 VPCs = 45, 20 VPCs = 190. Each peering is a manual config. TGW is a hub: each VPC attaches once. TGW also enables transitive routing — Spoke A → TGW → Spoke B is one logical path. Peering does not transit: A↔B and A↔C does not give B↔C.

Trade-off: TGW costs $36/month per attachment + $0.02/GB processed. VPC peering is free per connection (only data transfer charges). At very small scale (2-3 VPCs), peering wins on cost; at any scale, TGW wins on operational simplicity.

Conclusion: Default to TGW for any organisation that will grow beyond 5 VPCs. The cost is paid back in operational time saved on day 1.
Claim: Centralised egress through a dedicated Inspection VPC running AWS Network Firewall, with all 20 VPCs routing 0.0.0.0/0 via TGW to the Inspection VPC.

Reasoning: §11.2 of MAS TRM 2021 requires inspection of internet-bound traffic. Per-VPC NAT Gateways alone don't provide deep packet inspection. Centralised inspection: (1) Inspection VPC contains Network Firewall endpoints — stateful L3-L7 with Suricata-compatible rules, (2) Egress VPC has NAT GWs for source-NAT to internet, (3) all spoke VPCs route 0.0.0.0/0 via TGW to Inspection VPC. TGW route tables enforce all egress flows through inspection.

Trade-off: Network Firewall adds ~$400/month base + $0.065/GB processed. At 50 TB/month that's $3,650/month — substantial. Inspection VPC also adds latency (additional hop). Required for compliance; cost is non-negotiable.

Conclusion: Document the design with traffic flow diagrams showing inspection points; map specifically to MAS TRM §11.2 controls; provide auditor evidence via Flow Logs at Inspection VPC and Network Firewall logs.
Claim: Flow Logs delivery failures almost always come down to IAM, S3 bucket policy, or KMS key access — not the VPC config itself.

Reasoning: Investigation order: (1) describe-flow-logs — check DeliverLogsStatus and ErrorMessage, (2) if "Access Denied," check the IAM role's trust policy and permissions, (3) check S3 bucket policy — does it allow the delivery service principal (delivery.logs.amazonaws.com), (4) if bucket has KMS-CMK encryption, check the key policy allows the same principal, (5) check S3 bucket exists and isn't deleted, (6) check S3 lifecycle hasn't somehow blocked writes.

Trade-off: Stop-gap is to switch destination to CloudWatch Logs, but this is 20× more expensive — unsustainable.

Conclusion: Add CloudWatch alarm on DeliverLogsStatus = FAILED — should be a P2 incident because it's a compliance gap. Test Flow Logs delivery in non-prod after any IAM, S3, or KMS policy change.
Claim: Conceptually similar but the "regional vs global" model is the most consequential difference.

Reasoning: AWS VPCs are regional — one VPC per region; multi-region requires peering or TGW peering. Azure VNets are similarly regional. GCP VPCs are global by default — a single VPC spans all regions, with subnets per region. This matters when designing global apps: GCP simplifies "one network, multiple regions" while AWS requires explicit cross-region connectivity. CIDR planning differs too — GCP's auto-mode VPCs assign subnets automatically (avoid for production); AWS requires explicit subnet creation. Security models differ: AWS Security Groups are stateful and ENI-level; Azure NSGs are similar but rule precedence is different; GCP firewall rules are network-wide, target by tags or service accounts.

Trade-off: Multi-cloud architectures must account for these model differences. AWS VPC's regional model is more isolation by default — a failure mode you have to design around in GCP.

Conclusion: For Singapore FSI work, AWS VPC is the right tool. The model differences matter when designing multi-cloud DR or partner integrations.
Claim: Sudden NAT GW data spikes have a finite list of causes — investigate by elimination.

Reasoning: (1) Cost Explorer → group by usage type → confirm it's NAT data processing not data transfer out. (2) Flow Logs Athena query — top destinations from private subnets. Common findings: (a) container image pulls from public Docker Hub instead of ECR via VPC endpoint, (b) S3 access without Gateway endpoint going through NAT, (c) cross-region replication going via NAT instead of VPC peering, (d) malware/cryptominer C2 traffic, (e) misconfigured app pulling unbounded data from a third party. (3) For each top destination, check if there's an AWS endpoint that would bypass NAT.

Trade-off: Investigation can take hours of Athena queries. Worth it — the savings often pay for an entire engineer's time.

Conclusion: Set up automated Cost Anomaly Detection on NAT data; weekly Athena reports of top NAT destinations as part of FinOps cadence.
Claim: PrivateLink exposes a single service endpoint without sharing networks; VPC peering shares the entire network. Different tools for different needs.

Reasoning: VPC peering connects two networks with bidirectional routing — both sides can reach each other on any port (subject to SG/NACL). PrivateLink exposes one specific service in the provider VPC as a private endpoint in the consumer VPC — only that service is reachable, only the configured port. Network isolation is preserved. CIDR overlap is allowed (PrivateLink uses NAT-like mechanism). Common use case: SaaS providers (Snowflake, MongoDB Atlas, Datadog) offer PrivateLink so you don't need internet egress to reach them.

Trade-off: PrivateLink costs $0.014/hr per endpoint per AZ + $0.01/GB. VPC peering is free per connection (only data charges). PrivateLink scales to many consumers without configuration overhead per-consumer.

Conclusion: Use PrivateLink when: vendor offers it (default choice), you want isolation, you have CIDR overlap. Use peering when: you control both sides, full network access is needed, cost is the priority.
Claim: Same-AZ placement, cluster placement group, ENA with SR-IOV, jumbo frames, instance types with high network performance.

Reasoning: Cross-AZ adds 1-2ms — too much for sub-ms requirement. Cluster placement group ensures instances are physically close in the same AZ. Use instance types like c6gn, c6i with up to 100 Gbps networking. Enable Elastic Network Adapter (ENA) and Enhanced Networking. Enable jumbo frames (MTU 9001) within the placement group — but cap at 1500 if traffic leaves the AZ via NAT or transit gateway. Avoid intermediate hops: VPC endpoints, NAT GWs, ALBs all add latency. For absolute lowest latency: instance-to-instance direct, same-AZ, same placement group.

Trade-off: Single-AZ violates HA. Acceptable only if the workload is itself multi-region active-active so AZ failure is handled at the application layer, not the network layer.

Conclusion: Document the latency budget end-to-end. Test with iperf and tcpdump from day 1. Reserve cluster capacity ahead of demand.

Common HCL Pitfalls Specific to VPC

  • map_public_ip_on_launch on the wrong subnets: easy to leave default false everywhere and wonder why public subnet instances don't get IPs. Conditional based on tier.
  • Implicit dependency on IGW: NAT GW resource needs depends_on = [aws_internet_gateway.main] — NAT GW creation can race ahead of IGW attachment.
  • Route table loops: Adding NAT GW route to public RT (which has IGW route) creates a loop. NAT GW routes go in private RTs only.
  • Default NACL/SG management: these auto-exist. Use aws_default_* resources to control them rather than letting them sit untouched.
  • VPC endpoint route table associations: Gateway endpoints need route_table_ids list — easy to forget one and get half-functioning routing.
  • Implicit cycles via security groups: SG-A references SG-B references SG-A. Terraform will plan but apply may fail. Use aws_security_group_rule resources separately to break cycles.
