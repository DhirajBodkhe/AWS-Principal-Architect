00 / GLOSSARY

Glossary & Key Terms #

Read this once now, then come back whenever a term feels slippery. The storage/virtualization analogs are deliberate — they're how a 10-year storage engineer onboards DNS thinking in under an hour. Tooltips on these terms work anywhere in the document.

TermPlain-English definition (with on-prem analog)
Authoritative DNSThe DNS server that is the source of truth for a zone — when asked "what is the IP for api.example.com?" it answers from its own database, not by asking another server. Storage analog: like the array controller that owns a LUN; queries about that LUN go to it, not to a replicated copy.
Recursive ResolverThe DNS server your client talks to. It does the legwork: asks the root, then the TLD, then the authoritative server, caches each answer, and returns the final IP. On-prem: your 10.0.0.2 Active Directory DNS that recursively forwards queries you can't answer locally.
Hosted ZoneA Route 53 container holding all DNS records for one domain (e.g., example.com). Two kinds: public (answers internet queries) and private (answers only inside associated VPCs). Roughly equivalent to a forward lookup zone in Windows DNS Manager.
Record (RR)A single entry in a zone. Common types: A (IPv4), AAAA (IPv6), CNAME (alias to another name), MX (mail), TXT (free text), NS (delegation), SOA (zone metadata), ALIAS (AWS-specific zero-charge alias to AWS resources).
TTLTime-To-Live. How long a resolver may cache an answer before re-asking. Lower = faster failover, higher cost; higher = cheaper, slower failover. Mental model: snapshot retention window. Network analog: ARP cache timeout.
Alias RecordAWS-only record type. Looks like a CNAME but resolves to AWS resources (ALB, CloudFront, S3, API GW). Three superpowers: (1) free to query, (2) works at zone apex (CNAMEs cannot), (3) integrates with health checks.
NS DelegationThe mechanism by which one zone says "for queries under this sub-name, ask these other servers." When you buy example.com at GoDaddy and want AWS to host DNS, you put 4 Route 53 NS records at the registrar. This is the delegation.
Private Hosted Zone (PHZ)A hosted zone associated with one or more VPCs. Queries only resolve from inside those VPCs (when VPC DNS settings enable it). The cloud-native replacement for split-horizon DNS.
Resolver EndpointAn ENI-backed gateway that connects your VPC's recursive resolver to networks outside AWS. Inbound: on-prem queries can reach AWS-side zones. Outbound: AWS workloads can reach on-prem DNS servers. The hybrid-DNS bridge.
Resolver RuleA forwarding rule: "for queries matching *.corp.netrust.com, forward to 10.5.0.10:53 via an outbound endpoint." Without this, on-prem domain queries fail from inside VPC.
Health CheckA periodic probe (HTTP/HTTPS/TCP) from AWS edge locations to verify an endpoint is alive. Failure marks the record unhealthy and Route 53 stops returning it. Mental model: like vSphere HA's heartbeat for VMs.
Routing PolicyThe algorithm Route 53 uses to choose which IP to return when multiple records share a name. Eight types: simple, weighted, latency, failover, geolocation, geoproximity, multivalue, IP-based.
DNSSECDNS Security Extensions. Cryptographic signing of DNS responses so resolvers can verify the answer wasn't tampered with. Route 53 supports DNSSEC signing on public hosted zones since 2020. MAS TRM §11 calls for this on internet-facing zones.
Resolver Query LoggingCaptures every DNS query made from a VPC, including the source ENI. Lands in CloudWatch Logs, S3, or Kinesis Firehose. Mandatory for MAS TRM §12 audit trail.
Apex / Naked DomainThe bare domain with no subdomain (example.com not www.example.com). Per RFC 1912, you cannot put a CNAME at the apex — which is why AWS invented ALIAS records.
Negative Cache (NXDOMAIN cache)Resolvers cache not-found answers too, for the duration of the SOA minimum TTL. If you create a record after a resolver cached its absence, that record stays invisible until the negative TTL expires.
Split-Horizon DNSSame name returns different answers depending on where the query came from. api.netrust.com resolves to a private IP from inside the VPC, public IP from the internet. Implemented in Route 53 via public + private hosted zones sharing the same name.
VPC DNS Resolver (.2 resolver)The implicit recursive resolver at VPC-CIDR-base + 2 (e.g., 10.0.0.2 for 10.0.0.0/16). Every ENI uses it by default. Caches aggressively. Throttles at ~1024 queries/sec/ENI.
💡 Why This Matters

DNS sits below every other service. When DNS breaks, applications appear to break in baffling, plausible-but-wrong ways: timeouts, "host unreachable," intermittent failures. The engineer who can read DNS first and code second is the one who closes incidents in minutes instead of hours.

01 / CONCEPT

Concept & Mental Model #

What problem does Route 53 solve?

Computers talk to each other using IP addresses. Humans cannot remember IP addresses. DNS is the translation layer between human-readable names and machine-readable addresses. Every web request, API call, database connection, and email delivery starts with a DNS lookup. If DNS is slow, your application is slow. If DNS lies, your application is compromised.

Route 53 is AWS's fully managed implementation of three distinct DNS functions glued together:

  1. Authoritative DNS — hosts zones for domains you own. This is the "I am the source of truth for netrust.com" role.
  2. Domain registration — actually buys and renews the domain from ICANN-accredited registries. A bolt-on service, not the core.
  3. Resolver — recursive DNS service used by every VPC. This includes Resolver Endpoints and Resolver Rules for hybrid DNS.

These three are commonly conflated. They are billed separately, scaled separately, and fail separately. A Principal Architect treats them as three services in one wrapper.

What did engineers do before Route 53?

Run their own DNS. Specifically: pairs of BIND9 servers on hardened Linux boxes, replicated via AXFR/IXFR, behind anycast load balancing if you were sophisticated. Internally, Active Directory–integrated Windows DNS handled the corporate .local zone. The operational pain points were always the same:

  • BIND zone files edited by hand with named.conf typos taking the entire company offline
  • Replication lag between primary and secondary causing inconsistent answers
  • DDoS amplification attacks against your authoritative servers
  • Capacity planning: how many QPS does your resolver handle before melting?
  • Renewing the TLS certs on your DoT/DoH endpoints, if you were modern enough to run them

Route 53 collapses all of this. It is a 100% SLA, anycast-distributed, globally replicated authoritative DNS that you interact with via API. You do not size it. You do not patch it. You do not pay for capacity you aren't using.

The 2–3 core concepts

  1. A hosted zone is a container for records about one domain. If you own netrust.com, you create one hosted zone and put all records in it. Subdomains live in the same zone unless you explicitly delegate them with NS records.
  2. Authoritative ≠ Resolver. Route 53 the authoritative service answers from your hosted zones. The VPC .2 resolver recursively asks the internet for everything else. Resolver Endpoints bridge the two when you need on-prem traffic to flow.
  3. Records have TTLs. Resolvers cache. Therefore changes propagate eventually. If you set TTL=300, the longest a stale answer can live is 5 minutes anywhere in the world. If you set TTL=86400 (1 day), expect that long. Choose TTLs as a deliberate availability decision, not a default.

Common misconceptions

⚠ What Route 53 is NOT

Not a load balancer. Route 53 routing policies return different IPs to different queries, but it does not terminate TCP, inspect HTTP, or distribute requests across backends in real time. Use ALB/NLB for that.

Not a CDN. CloudFront caches content at edges. Route 53 only resolves names. They pair beautifully (your ALIAS record points at a CloudFront distribution), but they are different things.

Not "free because it's AWS." Hosted zones bill monthly. Queries bill per million. Health checks bill per check. Resolver Endpoints bill per ENI-hour. Plan for it.

Not a firewall. Route 53 Resolver DNS Firewall is a separate add-on feature for blocking known-bad domains. The base Resolver answers any question that resolves.

One concrete analogy

Imagine Route 53 as the global telephone directory operator from the 1950s — except the operator is reachable from anywhere on Earth simultaneously, responds in single-digit milliseconds, never sleeps, and can give different answers to different callers based on where they're calling from, what time it is, and whether the person they're calling has picked up recently. The "phone book" itself (your hosted zone) is what you maintain. The "operator" (Route 53) handles delivery, redundancy, and routing logic.

🌉 Bridge from Storage/Virtualization

If you've ever configured iSCSI, you know that initiators connect to iqn.example.com:target-name — a name that must resolve to an IP via DNS before the SCSI session can even start. Route 53 is the iSCSI portal lookup of the entire internet. A more direct analog: vSphere's reliance on DNS for vMotion, vCenter HA, and host certificate validation. When vSphere DNS breaks, your cluster doesn't fail gracefully — it cascades. Same here. DNS is a foundation, not a feature.

💡 Why This Matters

Architects who treat DNS as "just records" build systems that fail in DNS-shaped ways. Architects who treat DNS as a control plane — with TTLs as RTO levers, health checks as failover triggers, and zone delegation as a multi-team isolation boundary — build systems that recover gracefully. The mental shift from "set it and forget it" to "DNS is part of my architecture" is the single biggest leap from Cloud Engineer to Cloud Architect.

🔑 Pro-tip

The fact that Route 53's control plane is in us-east-1 only is a real architectural fact with real consequences. Time-based sequence: a health-check-driven failover

  T+0s     Primary ALB in ap-southeast-1 goes down
  T+0-30s  Health check probes (3 of 3 from different regions) fail
  T+30s    Route 53 marks primary record unhealthy
  T+30s    Failover routing policy switches to secondary record
  T+30-X   Resolvers worldwide return secondary IP as cached TTLs expire
           (X depends on the record's TTL — e.g., TTL=60 means ≤60s)
  T+60-90s Vast majority of new clients hit secondary
  T+300s   Stragglers with longer-cached records finally fail over

  RTO = health-check interval (10s/30s) × failure threshold (default 3)
      + your record TTL
      + a few seconds of edge propagation
💡 Why This Matters

That arithmetic — health check interval × threshold + TTL — is your DNS-driven RTO floor. If a Principal Architect asks "what's our RTO for this multi-region pattern?", you derive it from this formula. Set health checks to 10s with 3 failures and TTL to 60s, and your floor is ~90 seconds. Set them at the defaults (30s, 3, TTL 300), and you're at ~390 seconds — three times worse, with users seeing errors the whole time.

3.3 Canonical Patterns & Pairings

① Public domain → CloudFront → ALB

When: Standard web app, global users.

Pairing: Public HZ ALIAS → CloudFront → custom origin (ALB) in VPC. ACM cert at CloudFront (us-east-1).

The single most common AWS web architecture. Route 53 ALIAS makes it free at the apex.

② Multi-region active/passive failover

When: Strict RTO/RPO with cost discipline.

Pairing: Public HZ with two failover records, each pointing at a regional ALB, each with a health check.

Survives regional failure. Test the failover quarterly or it doesn't work.

③ Latency-based multi-region active/active

When: Global low-latency reads.

Pairing: One record name with multiple regional records keyed by latency policy + health check on each.

Each user gets the closest healthy region.

④ Split-horizon DNS for internal APIs

When: Same domain name used internally and externally.

Pairing: Public HZ api.netrust.com → CloudFront. Private HZ api.netrust.com associated with internal VPCs → internal ALB.

Inside the VPC, requests skip the internet entirely.

⑤ Hybrid DNS (on-prem ↔ AWS)

When: Bidirectional resolution required.

Pairing: Inbound + Outbound Resolver Endpoints, Resolver Rules forwarding *.corp.netrust.com to on-prem; on-prem forwarders pointing zones for *.aws.netrust.com at the Inbound endpoint IPs.

The reference architecture for every regulated hybrid environment.

⑥ Service discovery for microservices

When: ECS or EKS services need to discover each other.

Pairing: Cloud Map + Private HZ. ECS Service Connect or EKS ExternalDNS writes records as tasks come up.

DNS becomes the service registry — no Consul, no etcd, no extra ops.

🚨 Anti-pattern: using Route 53 as a load balancer

Multivalue and weighted routing tempt new architects to "load balance" across IPs by returning multiple A records. But clients cache aggressively, don't reliably round-robin, and won't retry on connection failure. The result: hot-spotting, slow failover, and a load balancer-shaped problem with no load balancer's instrumentation. Use ALB/NLB for load balancing, Route 53 for steering traffic between regions or to alternate stacks.

🎯 Decision rubric

Use Route 53 when AWS is your primary cloud, you want ALIAS records, and you value tight integration over absolute resolution speed.
Use Cloudflare when you're multi-cloud, you already pay them for CDN/WAF, or your CFO is allergic to per-query AWS billing.
Use NS1 when DNS is a product surface, not a substrate — i.e., you need to make routing decisions based on real-time user telemetry.

💼 Career Application

Ecosystem fluency is what interviewers test when they ask "walk me through how a request reaches your service". Junior answers stop at "DNS resolves it." Senior answers cover the full chain: registrar → NS → Route 53 authoritative → cached or recursive → ALIAS → CloudFront → ALB → target. Principal answers also explain what fails where and which dependencies create cross-region blast radii.

🤖 AI/Agentic Angle

In agentic architectures, every Bedrock endpoint, Lambda inference function, and EKS-hosted vLLM cluster needs a stable, low-latency name. Private Hosted Zones plus PrivateLink let agents call llm.internal.netrust.com from anywhere in your VPC mesh without any internet traversal — important for both latency and data sovereignty (MAS TRM §11). When an agent loop calls a tool, DNS is the first hop. Slow DNS = slow agent.

04 / SETUP

Prerequisites & Environment Setup #

Before you click anything in the Console, the following must already be true. Skipping any one of these costs you 30 minutes of confusion later.

  1. AWS account active in ap-southeast-1. Route 53 is a global service (no region selector at the top of the Console for hosted zones), but the resources you'll point at — VPCs, ALBs, Resolver Endpoints — are regional. We default to Singapore for MAS TRM data residency.
  2. An IAM principal with Route 53 + Resolver permissions. Either an admin role or, for cleaner hygiene, an attached policy with route53:* + route53resolver:* + ec2:*VpcEndpoint* + logs:*. Do not use the root user. MFA required.
  3. A domain name you actually control. Either registered at Route 53 Domains (easiest — NS auto-points correctly) or at an external registrar (you'll edit NS records there). For learning, a $1/year .click or .link domain is plenty.
  4. A VPC from Guide 01 deployed in ap-southeast-1. 3-AZ, with at least one private subnet per AZ. We'll use this for the Private Hosted Zone and Resolver Endpoints later.
  5. Browser: latest Chrome / Firefox / Edge. The Route 53 Console has historically been one of the older AWS UIs — the modern redesign rolled out late 2023. Use private/incognito if you've experienced stale-cache layout glitches.
  6. AWS CLI v2 installed locally for verification. aws --version should return ≥ 2.15. If not, upgrade.
  7. (Optional) Terraform ≥ 1.6 for the Rosetta Stone blocks to be runnable.
💰 Cost warning — read before proceeding

The moment you create a hosted zone you start being billed $0.50/month, pro-rated to the hour. Resolver Endpoints bill $0.125/ENI/hour — that's ~$1.50/day for a two-ENI inbound endpoint, ~$3/day for both directions. Health checks bill $0.50/month each. If you're following this guide as a learning lab, complete the cleanup at the end of Section 16 or expect a $5–10 surprise.

  • Type: Public hosted zone
  • Tags: Environment=prod, Owner=platform-team

Why these values: Production zones must be tagged for cost allocation. The description is invaluable when you have 50+ zones and need to know which is which without opening each one.

Visual cue: Click Create hosted zone. A green banner appears top-right. You land on the zone detail page showing four NS records and one SOA. The NS records will look like ns-1234.awsdns-12.org, ns-567.awsdns-34.co.uk, etc. Copy them — you'll need them next.

✓ Checkpoint At this point you should see exactly two record sets in the zone: one NS (4 values) and one SOA. If the zone shows 0 records, something failed silently — refresh, or check CloudTrail for an error. If you don't see this, jump to Section 09 (Troubleshooting).
STEP 03

Where: Your registrar's control panel (NOT the AWS Console). For Route 53 Domains, this is Route 53 → Domains → registered domains → click your domain → Actions → Edit name servers. For external registrars (Cloudflare, GoDaddy, Namecheap), it's their UI.

What to fill: Replace the existing nameservers with the four from your new Route 53 hosted zone.

Why: This is the delegation. Until the registrar tells the world "for queries about netrust.click, ask these four AWS servers," your zone is invisible.

Visual cue: The change can take from minutes to 48 hours to propagate globally. Test with dig +trace netrust.click NS from any terminal. When you see the four awsdns servers in the response, delegation is live.

Part B — Add records (A, AAAA, ALIAS, TXT)

STEP 04

Where: Hosted zone detail page → button Create record (right side)

What to fill: Choose Quick create record (left toggle at top). Fields:

  • Record name: www (the form auto-suffixes .netrust.click)
  • Record type: A — Routes traffic to an IPv4 address
  • Alias: Toggle ON
  • Route traffic to: Alias to Application and Classic Load Balancer → Region: Asia Pacific (Singapore) [ap-southeast-1] → pick your ALB from the dropdown
  • Routing policy: Simple routing
  • Evaluate target health: Yes

Why these values: ALIAS is free at query time (vs CNAME which would bill per query) and works at the zone apex (try doing example.com = CNAME — RFC violation, won't work). Evaluate target health means Route 53 won't return this record if the ALB itself has no healthy targets. This is the single most underused feature in Route 53.

Visual cue: Click Create records. The new record appears in the table with type A and value showing dualstack.netrust-prod-alb-...elb.amazonaws.com.

STEP 05

Where: Same page → Create record again

What to fill: Another record — apex this time:

  • Record name: leave blank (this means the apex, netrust.click itself)
  • Record type: A · Alias ON · same ALB target
  • Routing policy: Simple

Why: This is the apex ALIAS — the trick CNAMEs cannot do. Now netrust.click AND www.netrust.click both resolve to your ALB.

STEP 06

Where: Same page → Create record → for a TXT record (for SPF/domain verification)

What to fill:

  • Record name: blank (apex)
  • Record type: TXT
  • Value: "v=spf1 include:_spf.google.com -all" — the quotes matter
  • TTL: 300 (5 minutes)
  • Routing policy: Simple

Why this TTL: SPF/DKIM are read-mostly. 300s balances "fast to change if we add a new mail vendor" vs "don't pound the resolvers." For internal IP records you change weekly, use 60s. For NS / SOA records, use 86400s.

✓ Checkpoint Open a terminal: dig +short www.netrust.click. You should get back the public IP of your ALB. If you get NXDOMAIN, NS delegation hasn't propagated (wait 5–60 minutes). If you get an empty answer, the ALB has no healthy targets and Evaluate target health is correctly suppressing it.

Part C — Create a Private Hosted Zone

STEP 07

Where: Hosted zones → Create hosted zone

What to fill:

  • Domain name: internal.netrust.click (or whatever your internal namespace is — we'll use a sub-zone to avoid split-horizon confusion in this lab)
  • Type: Private hosted zone
  • VPCs to associate: Region ap-southeast-1 → select your prod VPC from Guide 01

Why a sub-zone instead of split-horizon: Split-horizon (same name, public + private) is powerful but confusing. We're keeping public and private as distinct names so failures are obvious. You can switch to split-horizon later.

Visual cue: Created zone shows just NS + SOA. The NS records are NOT internet-resolvable — they're cosmetic for Private zones. The actual resolution happens via the VPC's .2 resolver.

STEP 08

Where: Inside the private zone → Create record

What to fill:

  • Record name: db
  • Record type: A
  • Value: 10.0.10.42 (the private IP of your RDS-equivalent)
  • TTL: 60
  • Routing policy: Simple

Why TTL=60: Internal IPs change more often than public ones (subnet migrations, RDS failovers if you don't use the RDS endpoint). 60 seconds means clients converge within a minute of any change.

⚠ Common gotcha

If dig db.internal.netrust.click from inside an EC2 in your VPC returns SERVFAIL, check the VPC's DNS attributes. Both enableDnsSupport and enableDnsHostnames must be true for Private Hosted Zones to resolve. Go to VPC → Your VPCs → select VPC → Actions → Edit DNS hostnames / DNS resolution → enable both.

Part D — Resolver Endpoints (hybrid DNS)

STEP 09

Where: Route 53 left nav → Resolver → Inbound endpoints → Create inbound endpoint

What to fill:

  • Endpoint name: netrust-r53-inbound-apse1
  • VPC: your prod VPC
  • Security group: a new SG allowing TCP+UDP 53 from your on-prem CIDR (e.g., 10.5.0.0/16)
  • IP addresses: 2 entries — one private subnet in ap-southeast-1a, one in ap-southeast-1b — let AWS pick the IPs

Why two AZs: Resolver endpoints require minimum 2 ENIs in 2 AZs. This is the regional HA guarantee for the endpoint itself. Always add the third AZ in production for true regional resilience.

Visual cue: Creation takes 2–3 minutes. When done, the detail page shows two ENI IPs like 10.0.10.55 and 10.0.20.74. These are the IPs your on-prem DNS forwarders will target.

STEP 10

Where: Resolver → Outbound endpoints → Create outbound endpoint

What to fill: Mirror image of Step 09. Same VPC, same 2-AZ topology, SG egress to 0.0.0.0/0:53 (or more tightly: to your on-prem DNS CIDR only).

Why the egress rule: The outbound endpoint needs to reach your on-prem DNS server IPs. Tighten the SG to those specific IPs in production.

STEP 11

Where: Resolver → Rules → Create rule

What to fill:

  • Rule name: forward-corp-to-onprem
  • Rule type: Forward
  • Domain name: corp.netrust.com
  • VPCs that use this rule: your prod VPC
  • Outbound endpoint: the one from Step 10
  • Target IP addresses: 10.5.0.10:53 and 10.5.0.11:53 (your on-prem DNS pair)

Why two target IPs: Resolver Rules retry against each target IP in order if the first times out. Always pair your on-prem DNS for resilience.

Visual cue: Rule created. From any EC2 in the VPC, dig anything.corp.netrust.com now forwards to your on-prem DNS instead of trying to resolve via internet root servers.

Part E — Health-checked failover record

STEP 12

Where: Route 53 → Health checks → Create health check

What to fill:

  • Name: hc-www-apse1-primary
  • What to monitor: Endpoint
  • Specify endpoint by: Domain name → www.netrust.click
  • Protocol: HTTPS · Port 443 · Path /health
  • Request interval: Fast (10 seconds)
  • Failure threshold: 3
  • String matching: OK (verify body content)

Why "Fast" + 3 failures: Detection time = 10 × 3 = 30 seconds. Standard interval (30s × 3) gives you 90 seconds. The cost difference is real ($1/check/month for Fast vs $0.50 for Standard) but for primary failover it's worth it.

Visual cue: Health check status will show "Unknown" for the first minute or two, then transition to "Healthy" (green) or "Unhealthy" (red). Click the row to see per-region status from each of AWS's checker locations — invaluable when debugging "but it works for me!" issues.

STEP 13

Where: Back in your public hosted zone → click the existing www A record → Edit record

What to fill:

  • Routing policy: change from Simple to Failover
  • Failover record type: Primary
  • Health check ID: select hc-www-apse1-primary
  • Record ID: www-primary-apse1 (an arbitrary identifier — must be unique among records sharing the same name)

Visual cue: The record now shows routing policy "Failover" and the linked health check. Create a second www record marked Secondary, pointing at your DR region's ALB.

✓ Final checkpoint dig +short www.netrust.click returns your primary ALB. Now aws elbv2 modify-target-group --health-check-path /broken-on-purpose ... to fail the health check on purpose. Wait 60 seconds. dig again — you should see your secondary IP return.

🚨 Insecure defaults the vendor ships

1. DNSSEC off by default. AWS will let you launch a public zone with no signing. In 2026 there's no excuse. Turn it on.
2. Resolver Query Logging off. A VPC with no DNS query log is an audit black hole. Turn it on for every VPC, period.
3. DNS Firewall off. The default allow-anything stance means your workloads can resolve C2 servers freely. Apply at least the AWS-managed botnet rule group.
4. NS TTL=172800s (48 hours). If you ever migrate registrars or change name servers, you're committed to a 48-hour propagation window. Lower it to 3600 a week before any migration.

Live Session Walkthrough #

This section is a simulated narrative: you sit down, log in, and build the full setup including a deliberate mistake so you experience the failure mode and the fix. Follow it as a story, not a recipe.

Scene: 09:30 Monday — you've been asked to set up DNS for a new internal API

You open Chrome, navigate to signin.aws.amazon.com, punch in your IAM user, complete MFA, and land in the Console. Region selector top-right shows Asia Pacific (Singapore) ap-southeast-1. You search for "Route 53" — and notice the region indicator greys out as you arrive on the page. Right, global service.

You click Hosted zones → Create hosted zone. You type api.netrust.internal, set type to Private, and… you forget to associate any VPC. The form lets you submit anyway with a warning banner. The zone is created but un-associated. This is mistake #1, deliberately preserved.

You add an A record: v1 pointing to 10.0.10.42, TTL 60. The zone now shows NS, SOA, and your one A record. Looks fine.

You SSH to your test EC2 instance in the same VPC (using SSM Session Manager because in this environment public SSH is forbidden by SCP). You run:

bash · the moment of truth
$ dig +short v1.api.netrust.internal
$
# Empty output. The query returned, but no answer.

$ dig v1.api.netrust.internal

; <<>> DiG 9.18.x <<>> v1.api.netrust.internal
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 12345
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 0, AUTHORITY: 1, ADDITIONAL: 1

;; AUTHORITY SECTION:
.    10800 IN SOA a.root-servers.net. nstld.verisign-grs.com. ...

NXDOMAIN. Coming from the root servers. That tells you the VPC .2 resolver didn't find the name in any local source (no Private HZ associated, no Resolver Rule matched) and went out to the public internet. Where, of course, netrust.internal doesn't exist.

⚠ Diagnostic moment

The lesson here is to read the AUTHORITY section. When you see root servers there, your private zone isn't reachable from this VPC. When you see your AWS NS servers, the zone is found but the record isn't.

You fix it: back in the Console, click your private zone → Hosted zone details tab → scroll to Associated VPCs → Associate VPC. Pick ap-southeast-1, your prod VPC. Click Save. Wait 30 seconds (association propagation isn't instant).

09 / TROUBLESHOOTING

Troubleshooting & Failure Modes #

DNS failures fall into a small set of patterns. Learn these ten and you'll diagnose 95% of incidents in under five minutes.

Debug runbook — the first five things to run

  1. dig +short <name> — am I getting any answer?
  2. dig +trace <name> — where in the delegation chain does it break?
  3. dig @8.8.8.8 <name> vs dig @VPC.2 <name> — public vs private resolver disagreement?
  4. aws route53 list-resource-record-sets --hosted-zone-id <id> — does the record even exist in the zone?
  5. aws route53 get-change --id <changeid> — is my recent change still PENDING?

The top ten failures

① "Created the zone, set the record, still NXDOMAIN from the internet"

Symptom: dig www.example.com from any external network returns NXDOMAIN.
Root cause: NS delegation at the registrar still points at the previous DNS provider (or never pointed at Route 53).
Fix: Go to your registrar's control panel. Replace the NS records with the four Route 53 NS values from your hosted zone. Run dig +trace yourdomain.com NS — when the trace shows AWS NS servers, you're done. Allow up to 48 hours globally, though usually it's 5–60 minutes.
Prevention: Always set NS records at the registrar first, then create AWS records. Document the registrar location in your zone description.

② "Private Hosted Zone records don't resolve from inside the VPC"

Symptom: dig db.internal.netrust.click from an EC2 returns NXDOMAIN with root-server AUTHORITY.
Root cause: Three possible: (a) zone not associated with the VPC; (b) VPC's enableDnsSupport or enableDnsHostnames disabled; (c) the EC2 is using a custom DNS server in DHCP options that isn't the VPC .2 resolver.
Fix: Confirm association: aws route53 list-hosted-zones-by-vpc --vpc-id vpc-xxx --vpc-region ap-southeast-1. Confirm VPC DNS attributes: aws ec2 describe-vpc-attribute --vpc-id vpc-xxx --attribute enableDnsSupport. Confirm DHCP options: cat /etc/resolv.conf should show the .2 IP.
Prevention: Codify zone↔VPC associations in Terraform, never click them.

③ "Updated a record but old IP keeps resolving"

Symptom: Made a change in the Console, still seeing old answer from clients.
Root cause: Resolver caching, governed by the record's TTL. Plus possible negative caching if the record was previously NXDOMAIN.
Fix: Wait for TTL to expire (max time). On Linux, systemd-resolve --flush-caches. On Mac, sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder. On a Windows client, ipconfig /flushdns. Direct verification: dig @8.8.8.8 <name> bypasses local caches.
Prevention: Lower TTLs before planned changes, raise them back after. Many teams keep TTL=60 permanently on records they iterate on.

④ "ALIAS record won't save — 'cannot create CNAME at zone apex'"

Symptom: Trying to create example.com → cloudfront.net; Console rejects it.
Root cause: You're using CNAME type. RFC 1912 forbids CNAMEs at the zone apex (which must hold SOA and NS).
Fix: Use record type A with Alias=ON. ALIAS records sidestep the RFC by resolving to AWS targets at query time.
Prevention: Always prefer ALIAS over CNAME when the target is an AWS resource. ALIAS is free at query time; CNAME is billed.

⑤ "Resolver endpoint creation fails: 'must have at least 2 IP addresses in 2 Availability Zones'"

Symptom: Endpoint creation API returns this exact message.
Root cause: You selected only one subnet, or two subnets both in the same AZ.
Fix: Pick subnets explicitly from different AZs. In Terraform, parameterize private_subnet_az1 and private_subnet_az2 and assert they're different.
Prevention: Tag subnets with az and assert AZ diversity at IaC validation time.

⑥ "Health check reports Unhealthy but the endpoint works fine for me"

Symptom: Console shows health check failing red, but curl https://www.example.com/health from your laptop works.
Root cause: Three common: (a) endpoint blocks Route 53's checker IP ranges via Security Group; (b) endpoint requires SNI but the health check doesn't set it; (c) endpoint returns 200 but the body doesn't contain the configured string match.
Fix: (a) Allow ingress from Route 53 health checker CIDRs (download the JSON, filter by service ROUTE53_HEALTHCHECKS). (b) Enable SNI in the health check config — checkbox in the Console. (c) Verify body content matches exactly, including whitespace.
Prevention: When creating an ALB / EC2-fronted health check, immediately use get-health-check-last-failure-reason to see why it's failing in each region.

⑦ "Throttled: too many requests"

Symptom: Bulk creating thousands of records, API returns Throttling errors.
Root cause: Route 53 control plane has a per-account API rate limit (5 requests/second for most APIs). You're going faster than that.
Fix: Batch records into change-resource-record-sets calls — each batch can carry up to 1000 changes. Use exponential backoff (AWS SDK does this for you). For mass migrations, use traffic policies to deploy hundreds of records in one batch.
Prevention: Never loop one-record-per-call. Always batch.

⑧ "On-prem can resolve some AWS names but not others"

Symptom: nslookup v1.api.netrust.internal works from on-prem; nslookup db.internal.netrust.click fails — both are in PHZs.
Root cause: On-prem AD DNS forwarder is configured to forward netrust.internal to the Inbound Endpoint but not internal.netrust.click.
Fix: Add a conditional forwarder on AD DNS for each PHZ namespace. Or, consolidate PHZs under a single parent zone so one forwarder covers all.
Prevention: Standardize on one internal-namespace convention (e.g., *.aws.netrust.com) so one conditional forwarder rule covers everything.

⑨ "DNSSEC validation broke after enabling signing"

Symptom: After enabling DNSSEC, some resolvers (especially corporate ones) return SERVFAIL.
Root cause: You enabled signing but forgot to publish the DS (Delegation Signer) record at the registrar / parent zone.
Fix: In the Route 53 Console, after enabling signing, the page shows the DS record values you must add at your registrar. Copy them. Add them at the registrar. Then resolvers that validate DNSSEC can verify the chain of trust.
Prevention: Always treat DNSSEC enablement as a two-step deploy: enable signing → confirm via DNSViz → publish DS at parent. Test with dig +dnssec +cd before flipping for production.

⑩ "Random intermittent SERVFAILs from inside the VPC"

Symptom: Sporadic resolution failures, especially under load.
Root cause: The VPC .2 resolver throttles at ~1024 queries/sec per ENI. High-traffic Lambda or container workloads can hit this. Visible as packets-per-second drops on the ENI.
Fix: (a) Reduce DNS query rate by enabling client-side caching (Lambda nscd, JVM networkaddress.cache.ttl); (b) For very high-throughput workloads, dedicate Outbound Resolver Endpoints which scale beyond the .2 resolver limit; (c) Spread the workload across more ENIs.
Prevention: Watch aws/route53resolver CloudWatch metrics for query rate. Alert at 75% of the throttle ceiling. This is a real production problem and is rarely caught in dev environments.

The weird ones — non-obvious failures

⚠ Eventual consistency across the 4 AWS NS servers

Route 53 propagates record changes to its 4 NS replicas independently. A query might hit any one. For ~60 seconds after a change, different resolvers may get different answers depending on which NS they happened to query. Critical changes (failover decisions especially) should be designed around this — pre-create both records, then flip the health check, rather than create-on-failure.

⚠ Negative caching (NXDOMAIN cache) burns for hours

When a resolver gets NXDOMAIN, it caches the absence using the zone's SOA minimum field (default 900s, often higher). If you create a record after some resolver cached its absence, that resolver will continue to return NXDOMAIN until the negative cache expires. The fix: set SOA minimum low (60-300s) on zones where you frequently add new records. Cost: slightly more queries.

⚠ ALB DNS name changes

If you delete and recreate an ALB, its DNS name (used as the ALIAS target) changes. CNAMEs would break; ALIAS records track the new ALB only if you update the alias target. Terraform handles this automatically because it tracks the resource. Manual Console edits often miss it. Symptom: yesterday it worked, today it doesn't, and nothing in Route 53 has changed.

10 — Day-2 Operations

Living with Route 53 in production #

Building a zone is one hour. Living with it for three years is everything. Day-2 is where most mistakes get made — and where most outages originate.

The golden rule of record changes

⚠ Never edit production records by hand in the Console

Every record change in a production hosted zone is a potential outage. There is no "edit" button that performs a safe rolling update — a record is either correct or it's wrong, and 100% of traffic relying on it is affected. The single biggest source of DNS-induced outages is a typo'd manual edit. Treat every production record change as a code change: propose in Terraform, review in PR, plan, apply.

The TTL-lowering ritual

Before any planned record change, perform the TTL-lowering ritual. This is the single most important Day-2 discipline.

DAY −1 (24 hours before change)

Lower TTL on the record you intend to change

If the current TTL is 3600 (1 hour), lower it to 60 (1 minute). Apply this change. Wait at least the old TTL — i.e., one hour — before assuming the change has propagated. Wait 24 hours to be safe (corporate DNS resolvers sometimes ignore TTLs and cache for arbitrary durations).

DAY 0 (the actual change)

Make the real change

With TTL at 60s, the change will propagate worldwide in ~1-2 minutes. Verify with dig +short app.netrust.click @1.1.1.1 and @8.8.8.8 from multiple geographies if possible.

DAY +1 (after change verified)

Raise TTL back to normal

Restore TTL to 3600 (or whatever your standard is). Why raise it back? Because high TTLs reduce query volume (lower cost) and improve resilience — if Route 53 had an incident, cached answers keep your service resolving.

Recommended alarms — minimum viable set

✅ Alarm 1 — Health check failed

Metric: HealthCheckStatus < 1 for 2 datapoints (60s) in 2 minutes.
Why: Direct signal that a Route 53 health check thinks your endpoint is down. If you have failover configured, traffic is now diverted — you need to know.

✅ Alarm 2 — Resolver endpoint unhealthy ENI

Metric: EndpointUnhealthyENICount ≥ 1 for 5 minutes.
Why: Inbound or Outbound resolver endpoints rely on 2+ ENIs. Losing one halves throughput and risks a full outage if the second fails.

✅ Alarm 3 — Resolver query rate approaching limit

Metric: InboundQueryVolume > 75% of (1024 × ENI count × 60) per minute.
Why: The .2 resolver throttles at ~1024 qps per ENI. Catching the trend before it throttles avoids the random-SERVFAIL outage scenario from §09.

✅ Alarm 4 — DNS Firewall BLOCK rate spike

Metric: Sum of BLOCK actions in FirewallRuleGroupQueryVolume > baseline × 3 over 10 min.
Why: A spike means either: (a) malware in your VPC trying to reach a known-bad domain, (b) a developer using a new SaaS not on the allow-list. Either case demands investigation.

✅ Alarm 5 — Unexpected NXDOMAIN rate

Metric: NXDOMAIN responses from query logs > 5% of total queries.
Why: Indicates either typos in app code (resolving wrong names) or potential DNS tunnel exfiltration probing. Both are worth investigating.

14 — Security Deep Dive

DNS is the most underestimated attack surface in AWS #

DNS exists at layer 7 but bypasses most of your security tooling. Firewalls filter ports; WAFs filter HTTP; SIEM filters logs. DNS slips through all of them. This section is your DNS attack catalogue.

The four DNS attack categories

① DNS spoofing / cache poisoning

Attack: Attacker forges DNS responses to redirect victims to malicious servers (e.g., fake login page for bank.com).
AWS defence: DNSSEC. Route 53 signs responses with a KMS-backed key; resolvers that validate DNSSEC reject forged responses. However: the chain of trust requires DS records at the parent zone (your registrar) and the client must validate. Many corporate resolvers don't validate by default — DNSSEC is half-deployed across the internet.
What to do: Enable DNSSEC on your public zones. Configure clients (Resolver endpoints) to validate.

② DNS DDoS (volumetric or NXDOMAIN flood)

Attack: Flood Route 53 nameservers with queries (often spoofed-source NXDOMAIN floods) to overload them.
AWS defence: Shield Standard is included free — Route 53 has anycast-based global distribution that absorbs large floods. Shield Advanced ($3000/month) adds cost protection (AWS reimburses query cost during DDoS).
What to do: Shield Standard is automatic. For high-target zones (financial-services, government), pay for Shield Advanced.

③ DNS tunnelling / data exfiltration

Attack: Malware encodes data into DNS query subdomains (e.g., stolen-data-base64.attacker.com) which the corporate resolver dutifully resolves. Bypasses egress firewalls because port 53 is usually open.
AWS defence: DNS Firewall with rule groups to BLOCK known-bad domains and ALERT on unusual query patterns. GuardDuty detects "high query volume to a single domain" as anomalous DNS behaviour.
What to do: Enable DNS Firewall on all VPCs. Subscribe to AWS-managed rule groups (AWSManagedDomainsMalwareDomainList, AWSManagedDomainsAggregateThreatList). Enable GuardDuty.

④ Subdomain takeover

Attack: An old CNAME blog.netrust.click → netrust.github.io points at a deprovisioned GitHub Pages site. Attacker creates a new GitHub Pages site at the same name and serves content under your domain. Phishing victims see your real domain in the URL bar.
AWS defence: None automatic. This is a Day-2 hygiene problem.
What to do: Quarterly audit of every CNAME pointing outside your AWS accounts. Decommission unused records immediately. Tools like subjack automate detection.

15 — DR & Multi-Region

Route 53 as the spine of your DR strategy #

Multi-region anything ultimately ends in a DNS decision. Route 53's failover, latency, and ARC routing controls are the levers — knowing which to pull when separates seniors from principals.

The four canonical DR patterns

Pattern 1 — Active/Passive with Failover Routing

Setup: Two records (primary + secondary), both with health checks. Primary in ap-southeast-1, secondary in ap-southeast-3 (Jakarta).

Failover trigger: Health check fails 3× consecutively (90s default). RTO ≈ health_check_interval × failure_threshold + DNS TTL.

Best for: Cost-conscious DR. Passive region runs minimal infra (database replica + AMIs ready) until promoted.

RTO realistic: 5-15 min including DNS propagation. Not "instantaneous".

Pattern 2 — Active/Active with Latency Routing

Setup: Same record name, latency policy, one record per region. Each tagged with region. Route 53 sends each user to their lowest-latency region.

Failover trigger: Health check failure → Route 53 stops returning that region's record. Users automatically shift to next-best region.

Best for: Global SaaS with stateless or globally-replicated state (DynamoDB Global Tables, Aurora Global).

RTO realistic: 1-2 min once health check trips. No manual action.

Pattern 3 — Weighted with Manual Cutover

Setup: Two regions, weighted records (e.g., 100/0). Operator changes weights to shift traffic.

Failover trigger: Human decision via runbook or Application Recovery Controller.

Best for: Disasters where AWS automation might be wrong (e.g., regional service health unclear, data plane partially up). Humans hold the lever.

RTO realistic: 5-30 min depending on how fast humans react.

Pattern 4 — Application Recovery Controller (ARC) Routing Controls

Setup: Special "routing controls" managed by ARC. Each routing control is an ON/OFF switch evaluated by Route 53 health checks. Operators flip switches via a 5-cell distributed cluster (one cell per AWS region) — making the failover decision plane itself fault-tolerant.

Failover trigger: Human flips the switch, OR ARC safety rules auto-flip based on configured logic.

Best for: Cell-based architectures, regulated industries that need an auditable, fault-tolerant control plane for failover decisions (MAS TRM expectation for tier-1 systems).

RTO realistic: <60s once decision made. Decision plane itself has 5-9s availability.

🌉 Storage bridge — DNS-driven DR vs storage replication

DNS failover is the announcement of the cutover; the actual data must be ready in the failover region. Pair DNS patterns with the right data layer: Aurora Global ↔ ARC controls (sub-minute RPO); RDS read replica + manual promotion ↔ failover routing (RPO seconds, RTO 5+ min); DynamoDB Global Tables ↔ latency routing (RPO single-digit-second). DNS is fast; databases are the limiting factor.

Health check geography matters

⚠ Default health checks come from US-based locations

Route 53 health checks originate from ~15 AWS locations globally. For an APAC-only service, US-based checkers see higher latency and may false-positive trip the alarm during transient transpacific issues. Configure the Regions field on the health check to use APAC-only checkers (Tokyo, Sydney, Singapore, Seoul) for ap-southeast-1 endpoints.

Designing for the eventual consistency window

When Route 53 propagates a failover decision, its 4 nameservers update independently over ~60s. During that window, different resolvers may get different answers. Critical pattern:

  1. Pre-create both records with a deactivated secondary (weight 0 or unhealthy by design).
  2. Health check or weight flip is the failover trigger — not record creation.
  3. Lower TTLs on critical records (60s) so propagation is faster.
  4. Stateful retries in clients — if a request fails, retry with fresh DNS resolution (some clients cache forever; force a resolver refresh).

Production-grade reference designs #

Five patterns you'll be asked to defend in a Principal Architect interview. Each presented as: business scenario → architecture → trade-offs → anti-pattern.

Pattern A — Hybrid split-horizon DNS for an FSI

  On-prem AD DNS (10.50.1.10)              AWS ap-southeast-1
  ┌────────────────────────┐               ┌────────────────────────────────┐
  │ corp.netrust.com       │               │ PHZ: aws.netrust.com           │
  │  - desktops, file svrs │               │  - rds.aws.netrust.com         │
  │  - all on-prem hosts   │               │  - api.aws.netrust.com         │
  │                        │               │  Public: netrust.com           │
  │  Conditional forwarders│  ───────────→ │  Inbound Resolver (2 ENIs)     │
  │  aws.netrust.com →     │               │                                │
  │   Inbound Endpoint IPs │  ←─────────── │  Outbound Resolver (2 ENIs)    │
  │                        │               │   Rule: corp.netrust.com →     │
  │                        │               │     on-prem AD DNS IPs         │
  └────────────────────────┘               └────────────────────────────────┘

Scenario: Netrust runs core banking on-prem and cloud-native apps in AWS. Both sides must resolve each other's hostnames. Compliance: MAS TRM, no DNS data must leak to public internet.

Trade-offs: Two Resolver Endpoints = $360/month fixed. Resolver Rules + RAM share allow multiple VPCs to use the same Outbound endpoint — share aggressively. Inbound endpoint is single point of forwarding from on-prem; the 2-AZ ENI design provides HA but on-prem AD must list both IPs as forwarders.

Anti-pattern: Forwarding * (all queries) from on-prem to AWS rather than just the AWS-owned namespaces. This sends every desktop's public-internet DNS query through AWS, ballooning resolver query costs and breaking on-prem DLP.

Pattern B — Active/Active multi-region with latency routing

       Public record: api.netrust.com (latency policy)
       ┌──────────────────────────────────────────────────────┐
       │ Latency record 1: ap-southeast-1 → alb-sg.aws.amzn   │
       │   HealthCheck: HTTPS to /healthz                     │
       │ Latency record 2: ap-southeast-3 → alb-jk.aws.amzn   │
       │   HealthCheck: HTTPS to /healthz                     │
       │ Latency record 3: ap-northeast-1 → alb-tk.aws.amzn   │
       │   HealthCheck: HTTPS to /healthz                     │
       └──────────────────────────────────────────────────────┘
                  ↓                ↓                 ↓
            Aurora Global     Aurora Global    Aurora Global
            (writer in SG)    (reader)         (reader)
            DynamoDB Global Tables across all three

Scenario: Multi-region SaaS serving APAC. Each user gets routed to the nearest healthy region.

Trade-offs: Latency routing requires Route 53 to know each region's edge latency to the user's resolver — works well for major cities, less accurate from corporate proxies. Health checks must originate from APAC regions (not the default US-leaning set). Aurora Global has a writer-region constraint; cross-region writes have a latency cost (1.5-3× single-region write latency).

Anti-pattern: Geolocation routing instead of latency routing. Geolocation routes by country, not network distance — a user in Sydney connecting via a Singapore VPN gets routed by VPN exit country, not their actual location. Latency routing handles this correctly.

Pattern C — Service discovery for containerised microservices

   Cloud Map namespace: services.local  (backed by a PHZ)
   ┌───────────────────────────────────────────────────────┐

Scenario: 40+ ECS services on Fargate need to discover each other without ALBs in front of every one. PHZ + Cloud Map = service mesh's data plane without Istio's overhead.

Trade-offs: Records change fast (every deploy). TTLs must be low (30s or less). Client-side DNS caching (JVM, Go's net resolver) must be tuned down or stale records cause requests to dead tasks. App Mesh adds layer-7 retries and circuit breaking on top.

Anti-pattern: Hand-managing ECS task IPs in PHZ records. Always use Cloud Map or service-discovery integration — manual record management at this churn rate guarantees drift and outages.

Pattern D — Blue/green deployment via weighted routing

   api.netrust.com (weighted)
   ├─ weight 100 → blue ALB    (current production)
   └─ weight 0   → green ALB   (new version, fully tested)

   Cutover: change weight to 100/0 → 95/5 → 50/50 → 0/100 over 2 hours
   Rollback: flip back to 100/0 in seconds

Scenario: Zero-downtime production deployment with the ability to abort fast if metrics turn bad.

Trade-offs: Both blue and green ALBs run simultaneously = 2× ALB cost for the cutover window. State (DB sessions, sticky logins) must work across both — JWT or stateless tokens, not server-side sessions. TTL must be low (60s) for fast rollback; higher TTLs trap users on a bad version.

Anti-pattern: Using weighted records for canary deployments at the DNS level when you have an ALB. ALB target groups can do weighted forwarding internally with no DNS dependency — faster, more accurate, cheaper. Use DNS weights for region-level shifts; use ALB target group weights for service-level canaries.

Pattern E — Agentic AI ingress with Bedrock fronting

Trade-offs: Route 53 + CloudFront + WAF gives you DDoS resistance and rate limiting for free — essential because LLM endpoints have non-trivial per-request cost (each Claude call = $$). Without WAF rate limits, a single attacker can rack up thousands of dollars in Bedrock charges in minutes.

For agentic systems the per-request cost asymmetry is brutal — a request that costs the attacker 1 cent of compute costs you 50 cents in Bedrock fees. 19 — Regular FAQ

Beginner questions, plain answers #

Is Route 53 free?

No — but it's cheap. Every public hosted zone is $0.50/month, plus $0.40 per million queries. A single small website might cost $1-2/month total. Resolver endpoints are the expensive part ($180/month per endpoint due to ENI charges).

What's the difference between a public hosted zone and a private hosted zone?

Public hosted zones answer queries from the internet — anyone in the world resolving netrust.click hits Route 53's public nameservers. Private hosted zones answer queries only from VPCs you associate with them — internet users get NXDOMAIN. Same record structure, different audience.

Do I need a VPC for Route 53?

For public zones, no. Public zones are global. For private zones, yes — you must associate at least one VPC. For Resolver endpoints, yes — they live inside a VPC like any other ENI.

Can I delete a hosted zone without breaking anything?

Yes, but only after you've moved or removed every record except the auto-created SOA and NS records. If you delete a public zone, anything still pointing at it gets NXDOMAIN. Always lower TTLs first, migrate traffic, verify zero queries, then delete.

What's the difference between an A record and an ALIAS record?

An A record points to an IPv4 address (1.2.3.4). An ALIAS record points to an AWS resource (ALB, CloudFront, S3 website, another Route 53 record) and Route 53 tracks the IP automatically as that resource changes. ALIAS is free to query; A records are metered. Always prefer ALIAS for AWS targets.

Can I use Route 53 if my domain is registered elsewhere?

Yes. Register your domain at Namecheap or wherever, create a public hosted zone in Route 53, and change the nameservers at the registrar to the 4 nameservers Route 53 assigns. Route 53 doesn't care where the domain was bought.

How long does a record change take to propagate?

To Route 53's own nameservers, ~60 seconds. To the rest of the internet, it depends on the TTL of the record before you changed it — resolvers will keep cached answers until that TTL expires. Plan changes around the existing TTL, not the new one.

Why do I have to look at us-east-1 for health checks?

Route 53 is a global service but its control plane and metrics infrastructure live in us-east-1. Health check status, CloudWatch metrics for health checks, and DNSSEC KMS keys all require us-east-1. This is a historical AWS quirk — annoying, but you adapt by using us-east-1 provider aliases in Terraform.

What's a "split-horizon" or "split-brain" DNS?

The same name resolves to different IPs depending on who's asking. api.netrust.com might resolve to an internal IP when queried from inside a VPC (via PHZ) but a public IP when queried from the internet (via public hosted zone). It's intentional and useful, but it requires careful design.

Do I need DNSSEC?

For most internal apps, no. For public-facing financial-services apps, government services, or anything where a forged DNS response could cause harm to users (phishing surface), yes. It's a half-deployed standard — many resolvers don't validate — but enabling it costs little and protects users on resolvers that do validate.

Can I migrate my domain to Route 53 without downtime?

Yes. Create the hosted zone in Route 53. Copy every record from the old DNS provider into the new zone (records-only; do not change registrar nameservers yet). Verify the zone with dig @ns-XXX.awsdns-XX.net netrust.click. Then change the nameservers at the registrar. During the propagation window (24-48h depending on old NS TTL) both services answer correctly because records match. Once propagation completes, decommission the old provider.

Why does AWS need 4 nameservers per zone?

Redundancy and load distribution. The 4 nameservers are anycast-routed across AWS's global edge — your zone can survive multiple regional failures without losing DNS service. This is why Route 53 advertises 100% availability SLA on the data plane.

20 — Interview Q&A

Principal Architect grade questions #

Questions calibrated for SAP-C02 scenarios, FAANG cloud architect loops, and Singapore FSI senior interviews. Answers are structured: claim → reasoning → trade-off → conclusion.

Walk me through how Route 53 achieves 100% availability SLA on the data plane.

Claim: Route 53's data plane (the nameservers that answer queries) is fully distributed across AWS's global edge network using anycast routing.

Reasoning: Each hosted zone is assigned 4 nameservers, but those nameservers aren't single locations — each is announced from dozens of AWS edge sites via BGP anycast. A query from Singapore hits a Singapore edge; a query from Frankfurt hits a Frankfurt edge. The system has no single point of failure: lose a region, lose a continent even, and the remaining edges continue answering.

Trade-off: The 100% SLA covers only the data plane. The control plane (creating/updating records, health checks, DNSSEC signing) lives in us-east-1 and does have outages — when it fails, you can still serve queries from existing records but can't make changes. Architectural implication: never depend on Route 53 control plane during a failover; pre-stage records and use weighted/failover routing that doesn't require an API call to flip.

Conclusion: Design for control-plane outages by pre-staging all DR records and using health-check-driven failover, not API-driven failover.

You have a multi-region SaaS. Walk me through your DNS architecture for an active-active deployment with sub-minute RTO.

Claim: Latency routing with regional health checks at the apex, weighted records for canary, and ARC routing controls for major-incident manual override.

Reasoning: Latency routing handles normal traffic distribution — each user goes to their fastest region. Health checks attached to each latency record (HTTPS check against /healthz) cause Route 53 to drop a region automatically when its endpoint fails 3 consecutive checks. TTL on these records is 60s so client resolvers refresh quickly. For deliberate region drains (e.g., AWS announces a regional issue you want to get ahead of), Application Recovery Controller routing controls are flipped — these are evaluated by Route 53 health checks and act like a kill switch with its own 5-cell distributed evaluation plane, so the act of failing over doesn't depend on the region being failed over from.

Trade-off: Latency routing requires the back-end state to be globally consistent or each-region-tolerant. Aurora Global gives single-digit-second RPO with one writer-region — adequate for most reads but writes pay cross-region latency. DynamoDB Global Tables give multi-master with last-writer-wins conflict resolution — better for stateless workloads. Cost: running active-active means paying for full capacity in every region instead of standby cost in one.

Conclusion: Sub-minute RTO is achievable with latency routing + health checks + ARC. The real constraint is the data layer — DNS will fail over in seconds; your database may not.

A team wants to put 50,000 records in a single hosted zone. What's your recommendation?

Claim: It works technically (the soft limit is 10k but Support routinely raises to 100k+), but it's a Day-2 anti-pattern. I'd push back and design differently.

Reasoning: The issues aren't capacity — they're operational. Terraform plans over a 50k-record zone become slow and unreadable. A single bad PR can mass-affect records. Audit becomes nearly impossible. Most large zones I've seen at this scale are service-discovery records that should live in AWS Cloud Map (which uses PHZs under the hood but provides automation) or in a service mesh's discovery layer.

Trade-off: Splitting into multiple smaller zones (e.g., us.svc.netrust.com, eu.svc.netrust.com) adds delegation complexity but makes ownership and blast radius manageable. Cloud Map / Service Connect is more expensive per call but eliminates the operational burden.

Conclusion: If the records represent dynamic service endpoints, use Cloud Map. If they represent static infrastructure, split by ownership. Single 50k-record zones are a code smell.

You suspect DNS exfiltration is happening from one of your VPCs. Walk me through how you'd investigate and contain.

Claim: Resolver query logs → identify anomalous patterns → DNS Firewall to block + isolate the source instance for forensics.

Reasoning: Step one is data — enable Resolver query logs to CloudWatch Logs (or S3) on the affected VPC. Look for: long subdomains (exfil encodes data into subdomain segments), repetitive queries to the same parent domain, NXDOMAIN rates above baseline, and unusually high per-instance query rates. GuardDuty's Trojan:EC2/DGADomainRequest and Backdoor:EC2/C&CActivity findings are correlated signals. Once the source instance is identified, isolate by changing its security group to one with no egress (preserves it for forensics), and add the suspect domain to DNS Firewall as a BLOCK rule.

Trade-off: Resolver query logs cost real money on busy VPCs (Scenario C in the cost section). Many teams only enable them after an incident — but then you have no baseline. The right answer is always-on logging with short retention (7-14 days, S3 destination) so you have evidence when you need it.

Conclusion: Always-on Resolver query logs (S3 destination), DNS Firewall with managed threat-feed rule groups, GuardDuty enabled, and a tested IR runbook. None of these alone is enough.

This Route 53 bill came in at $8,000 last month. Where would you look to cut?

Claim: Three usual suspects, in order of likelihood: (1) resolver query logging to CloudWatch Logs, (2) low-TTL records generating excess query volume, (3) CNAMEs to AWS targets that should be ALIASes.

Reasoning: CloudWatch Logs ingest at $0.50/GB on high-query-volume zones is the most common bill shock — query logs to S3 are 10× cheaper. Next, audit TTLs: records at TTL 30 generate 120× the queries of TTL 3600. For records that change rarely (MX, TXT, apex ALIAS), TTLs should be hours not seconds. Third, scan for CNAMEs whose target is an AWS resource — every CNAME query costs $0.40/M while ALIAS is free. ELBs, CloudFront, S3 websites, and even cross-zone Route 53 records all support ALIAS.

Trade-off: Raising TTLs trades cost for failover speed. Be deliberate about which records need fast cutover (failover targets: TTL 60) versus which are stable (TTL 3600+).

Conclusion: Cost Explorer with Route 53 service filter, group by usage type. The three line items above usually account for 80% of the spend. Cutting them is days of work and tens of thousands of dollars per year.

Why might you NOT use Route 53 for a particular zone?

Claim: Three scenarios: (1) anycast geographic routing more sophisticated than latency-based, (2) integrated edge security (CDN-level DDoS + WAF + DNS bundled), (3) regulatory data residency demanding non-AWS infrastructure.

Reasoning: NS1 and Cloudflare offer geographic routing decisions based on real-time RUM data, not just latency probes — useful for global media delivery. Cloudflare's bundle pairs DNS with their WAF and DDoS layer at the edge, which can be operationally simpler than stitching together Route 53 + CloudFront + Shield + WAF. For some regulated zones, the registrar and DNS provider must be in-country (Singapore's .sg with a Singapore-incorporated provider, for instance) — AWS doesn't always satisfy that.

Trade-off: Picking a non-AWS DNS provider means losing the deep AWS integrations: no ALIAS records, manual ALB target tracking, no native KMS-backed DNSSEC, no CloudFormation/Terraform aws_route53_* resources. For most enterprise workloads, the AWS integrations more than offset the alternative's strengths.

Conclusion: Default to Route 53 for AWS-resident workloads. Pick alternatives only when a specific feature is genuinely better and the integration loss is acceptable.

How would you design DNS for a strictly regulated FSI customer (MAS TRM, no public internet egress from production VPCs)?

Claim: Private hosted zones for all internal namespaces, Resolver endpoints for hybrid, DNS Firewall with default-deny outbound, VPC endpoints for all AWS services, and centralised query logging to a security account.

Reasoning: Production VPCs have no NAT Gateway and no IGW. AWS service traffic exits via VPC interface endpoints (which use AWS PrivateLink — DNS for these endpoints is automatic via the .2 resolver). DNS itself only goes to: (a) the .2 resolver for AWS-managed DNS, (b) the Outbound Resolver Endpoint for on-prem forwarding. DNS Firewall is in BLOCK-by-default mode on everything else — no public DNS resolution from prod. Query logs from every VPC stream to a centralised security account S3 bucket (cross-account log destination), where they're retained 7 years to satisfy MAS TRM evidence requirements. DNSSEC enabled on public zones. Health checks for internal records use AWS-native targets only.

Trade-off: The default-deny DNS Firewall posture catches legitimate access too — pip installs from PyPI, Docker pulls from Docker Hub, etc. Solution: AWS CodeArtifact and ECR with VPC endpoints, no public package fetches. Developer friction is real but the security posture is what the regulator expects.

Conclusion: Private-by-default DNS, centralised logging, VPC endpoints everywhere, DNSSEC on public, MFA + tagged-resource IAM for any record changes. This is the MAS TRM expectation, not a stretch goal.

Route 53 vs Cloud Map for service discovery — when do you pick which?

Claim: Cloud Map for ephemeral compute (ECS tasks, Lambda); Route 53 PHZ directly for static infrastructure (RDS, ALB, ElastiCache).

Reasoning: Cloud Map is a service-discovery API that uses Route 53 PHZs underneath but adds: automatic registration/deregistration tied to ECS task lifecycle, health-check integration without manual setup, namespace-as-first-class concept. For an ECS service that scales from 2 to 20 to 5 tasks across the day, Cloud Map is the right abstraction. For an RDS database that exists for years with a stable DNS name, just create the CNAME or ALIAS in a PHZ directly — Cloud Map adds no value.

Trade-off: Cloud Map costs ~$0.10/service/month plus per-discovery costs — meaningful at 100+ services. The operational savings (no manual record updates on deploy) usually justify it.

Conclusion: Dynamic = Cloud Map. Static = PHZ records. Don't manually maintain ECS task IPs in PHZ records.

Walk me through what happens when you flip a Route 53 failover record from PRIMARY to SECONDARY.

Claim: The flip is implicit — driven by health check state — but the propagation has 3 phases each with its own timing.

Reasoning: Phase 1, health check decision: Route 53 health checkers (running from ~15 global locations) probe the primary endpoint every 10s or 30s. The check fails when failure_threshold consecutive probes fail (default 3). So with default 30s interval × 3 = 90s before Route 53 considers primary down. Phase 2, nameserver update: once health check state changes, Route 53 propagates the new answer to its 4 nameservers — typically <60 seconds. During that window, different resolvers may get different answers (eventual consistency). Phase 3, downstream caching: every resolver in the world that cached the old answer will keep serving it until the cached TTL expires. With TTL 60, 5 minutes after the flip ~99% of resolvers have refreshed.

Trade-off: Lowering health check interval (10s instead of 30s) speeds Phase 1 but costs more ($1/check/month per "fast interval" feature). Lowering TTL speeds Phase 3 but increases query volume linearly. Realistic minimum RTO with TTL 60 + 10s/3-threshold = ~90 seconds end to end.

Conclusion: Total failover time = health_check_interval × failure_threshold + ~60s Route 53 propagation + TTL. For sub-minute RTO, use ARC routing controls, not health-check failover.

Your application uses a CNAME for the apex of a domain and it's not working. Why?

Claim: CNAMEs are forbidden at the apex by RFC 1034. Your DNS provider rejected it or silently substituted something. In Route 53, the correct construct is an ALIAS A record.

Reasoning: The apex of a zone (the zone name itself, e.g., netrust.click) must hold an SOA and NS records by spec. CNAME records "replace" the entire name — meaning a CNAME at the apex would collide with the required SOA/NS, which isn't allowed. Some providers fake support via "ANAME" or "ALIAS" records that resolve the target at query time and return its A records. Route 53's ALIAS records work this way — they look like CNAMEs in the Console but are stored and served as A records, fully apex-compatible and free to query.

Trade-off: ALIAS records only point at AWS resources (other Route 53 records, ALB, CloudFront, S3 websites, API Gateway, VPC endpoints). For non-AWS targets at the apex, your options are: redirect at the HTTP layer (apex → www via S3 redirect bucket + CloudFront), or use a third-party DNS provider that supports CNAME-flattening.

Conclusion: For AWS-hosted apex domains, always use ALIAS. For multi-cloud apex routing, plan to terminate at an AWS edge (CloudFront) or accept the redirect.

What's wrong with using Route 53 weighted records for a service-level canary deployment?

Claim: DNS caching makes the split inaccurate and rollback slow. ALB target group weights are the better tool for service-level canaries.

Reasoning: A weighted record with 95/5 weights only gets you "approximately 5% of resolvers will return the canary IP". But resolvers cache for the TTL, so a single corporate proxy that cached the canary will route 100% of its users to the canary regardless of weight — the actual user-level split is non-uniform and hard to reason about. Rollback requires changing the weight and waiting for TTL to expire — at TTL 60 that's still up to a minute where some users hit the bad version. ALB target group weighted forwarding evaluates the split on every request inside the load balancer — exact percentages, instant rollback.

Trade-off: DNS weighted records work fine for region-level splits (where you actually want all of a user's session to stay in one region for cache locality), and for blue/green at the LB-pair level (two separate ALBs). For canary deployment of two versions sitting behind the same ALB, target group weights win.

Conclusion: DNS weights are for coarse-grained, slow-changing splits (region cutover, blue/green). ALB target group weights are for fine-grained, fast-changing splits (canary deployment).

How do you think Route 53 will be used differently in an LLM/agentic AI stack vs a traditional web stack?

Claim: DNS becomes the cost-protection layer first, latency-routing second. The economic asymmetry of LLM calls changes the design pressure on the entry point.

Reasoning: A traditional web request costs the operator microseconds of compute. An LLM-backed request costs the operator real dollars (a single Claude Opus call might be 30¢). The cost ratio between an attacker's effort and the operator's pain is 1:50 or worse. DNS-level rate limiting via Route 53 doesn't exist directly, but combining Route 53 → CloudFront → WAF gives layered defence: CloudFront absorbs DDoS for free, WAF rate-limits by IP/JA3/header, then API Gateway adds per-user usage plans. Without this, a single attacker can rack up thousands of dollars in Bedrock charges in an afternoon. Beyond cost: agentic systems make many DNS queries to other services (RAG vector stores, KB endpoints, tool APIs), so .2 resolver throttling becomes a real risk at high concurrency — Resolver Endpoint capacity planning matters more.

Trade-off: Adding CloudFront in front of every LLM endpoint adds latency (~30-50ms for cache miss) and complexity. For internal agents, it's usually unnecessary. For public-facing chatbots, it's essential.

Conclusion: For AI workloads, DNS is the start of a cost-protection chain. Design it as such — Route 53 + CloudFront + WAF + API Gateway usage plans + Lambda concurrency limits + Bedrock guardrails. Skip any layer and you'll find out which one the attackers probe.

State management considerations

  • S3 backend with DynamoDB lock — prevents two engineers applying the same plan simultaneously. Mandatory for any team work.
  • Workspace per environment — separate state files for dev/stg/prod. Don't share state across blast-radius boundaries.
  • Version pinning — pin both Terraform and provider versions. Provider 5.50 behaves differently than 4.x for Route 53; surprises happen.
  • State encryption — KMS-encrypt the S3 bucket. State files contain ARNs, IP addresses, sometimes secrets.
  • Drift detection in CI — schedule a daily terraform plan with -detailed-exitcode; alert on exit code 2.

HCL pitfalls specific to Route 53

⚠ Common Terraform-Route53 traps
  • Forgetting provider = aws.use1 on health checks and DNSSEC resources. Apply succeeds; nothing works.
  • Mixing records and alias in the same aws_route53_record. One or the other, never both.
  • Inline records vs explicit resources — older module patterns use the deprecated inline-records-on-zone construct. Use aws_route53_record resources with for_each instead.
  • PHZ VPC association ordering — if the PHZ is created in one Terraform module and VPCs in another, you must use aws_route53_zone_association resources in the consuming module, not the inline vpc block on the zone (which conflicts with separate associations).
  • DNSSEC requires explicit dependency — the KMS key alias must exist before aws_route53_key_signing_key can reference it; use depends_on to be safe.

locals {
  common_tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
    Module      = "route53"
    Owner       = "platform-team"
  }
}

resource "aws_route53_zone" "public" {
  name = var.public_zone_name
  tags = local.common_tags
}

resource "aws_route53_zone" "private" {
  for_each = var.private_zones

  name = each.value.domain

  dynamic "vpc" {
    for_each = each.value.vpc_ids
    content {
      vpc_id     = vpc.value
      vpc_region = each.value.vpc_region
    }
  }

  tags = merge(local.common_tags, { Type = "private" })
}

resource "aws_route53_record" "public" {
  for_each = var.public_records

  zone_id = aws_route53_zone.public.zone_id
  name    = each.key == "@" ? var.public_zone_name : "${each.key}.${var.public_zone_name}"
  type    = each.value.type

  # Either alias OR ttl+records — never both
  ttl     = each.value.alias == null ? each.value.ttl : null
  records = each.value.alias == null ? each.value.records : null

  dynamic "alias" {
    for_each = each.value.alias == null ? [] : [each.value.alias]
    content {
      name                   = alias.value.name
      zone_id                = alias.value.zone_id
      evaluate_target_health = alias.value.evaluate_target_health
    }
  }
}
