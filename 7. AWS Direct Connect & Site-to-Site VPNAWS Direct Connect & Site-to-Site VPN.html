01 / CONCEPT

Concept & Mental Model #

Why Not Just Use the Internet?

The public internet is unpredictable. Latency varies. Routes change. Congestion on backbone peering points causes packet loss during peak hours. For a bank moving real-time payments data or a trading firm with microsecond-sensitive market data feeds, "unpredictable" is unacceptable. Direct Connect gives you a dedicated, private, physically separate path to AWS with consistent latency (typically 2–5 ms Singapore on-prem to ap-southeast-1), predictable throughput, and no exposure to the public internet's routing instability.

Site-to-Site VPN uses the internet but adds IPSec encryption. It's cheaper, faster to provision (minutes vs weeks for DX), and is the standard backup path for DX. Every production FSI DX deployment has a VPN backup — DX goes down, BGP fails over to VPN automatically.

Three Core Concepts to Internalize

1. DX is physical, and physical takes time. Ordering a DX Dedicated Connection requires a Letter of Authorization (LOA-CFA) from AWS, then you or your colocation provider does the physical cross-connect at the DX location. This takes 2–12 weeks depending on the facility. Start the DX order at the beginning of a project, not when you need it. Hosted Connections through a partner are faster (days not weeks) but share the underlying physical port.

2. VIFs are the logical layer; the physical port just carries them. A single 10 Gbps DX Dedicated Connection can carry multiple VIFs — a Private VIF to your production VPC, a Public VIF to reach S3 privately, and a Transit VIF to a TGW that serves 50 VPCs. BGP sessions run independently per VIF. This is the same mental model as 802.1Q trunking — one physical link, multiple isolated logical paths.

3. BGP is how you control traffic engineering. AWS advertises VPC CIDR ranges to your on-premises router via BGP over the VIF. Your on-premises router advertises your corporate prefixes to AWS. Traffic follows the BGP best path. You influence path selection using standard BGP attributes: AS_PATH prepending (make a path look less preferred), MED (suggest a preferred entry point to AWS), and LOCAL_PREF on your side (prefer DX over VPN backup). If you already run BGP for internet peering or MPLS, this is the same tool set applied to AWS connectivity.

What Did Engineers Do Before Direct Connect?

Before DX (available from 2012), all AWS connectivity was over the public internet. Large enterprises ran Site-to-Site VPN but accepted internet-path variability. FSI firms were effectively blocked from putting latency-sensitive workloads on AWS because of this variability. DX changed the calculus entirely — it made AWS connectivity equivalent to an MPLS leased line, predictable enough for financial-grade workloads. The Singapore DX locations (Equinix SG1, Equinix SG2) are where most FSI firms connect today.

The Leased Line + VLAN Analogy

Direct Connect ≈ an MPLS leased line to a carrier colocation where AWS happens to peer. VIFs ≈ MPLS VPNs or 802.1Q VLANs on that leased line — one physical circuit, multiple isolated logical services. BGP ≈ the same BGP you run with your MPLS provider for route exchange. The VGW ≈ the CE router in an MPLS VPN model — it terminates the virtual circuit and exchanges routes with the PE (AWS) side. The Direct Connect Gateway ≈ a route reflector that distributes routes between your single DX connection and multiple AWS regions/VPCs.

🌉 Bridge from Storage/Virtualisation

Direct Connect ≈ a dedicated 10GbE cross-connect from your DC to an AWS colocation cage. You've provisioned storage network connectivity via direct-attach, FC fabric, or iSCSI — DX is the same concept applied to cloud connectivity. The physical cross-connect at Equinix SG1 ≈ a cable between your switch port and the patch panel in the meet-me room. VIFs ≈ 802.1Q VLAN sub-interfaces on that cable — same physical path, logically separated by VLAN ID. BGP over DX ≈ the BGP you'd run over an MPLS CE-PE interface — standard route exchange, same attributes, same traffic engineering levers (MED, LOCAL_PREF, AS_PATH). BFD ≈ the link-state detection you'd run on a bonded uplink — sub-second failure detection without waiting for the routing protocol to time out. MACsec ≈ 802.1AE encryption on your campus fabric — wire-speed Layer 2 encryption between your router and the DX endpoint, transparent to Layer 3.

💡 Why This Matters — FSI Hybrid Architecture

MAS TRM §11 requires that data connections to cloud providers meet confidentiality and integrity standards. Direct Connect satisfies the private connectivity requirement — traffic never touches the public internet. Combined with MACsec (Layer 2 encryption) or IPSec over VPN (Layer 3 encryption), you satisfy both the private path (§11.1) and the encryption in transit (§11.3) requirements simultaneously. Every FSI hybrid cloud architecture in Singapore has a DX connection as its primary AWS connectivity. The VPN backup pattern is the standard HA approach. Understanding how to design, provision, and operate this connectivity is core to any FSI cloud architect role.

⚠️ Private VIF vs Transit VIF — The Scalability Cliff

A common early DX architecture mistake: use Private VIFs for each VPC. This works for 2–3 VPCs but creates a management nightmare at scale. You can only attach one Private VIF to one VGW — so 20 VPCs means 20 VGWs, 20 BGP sessions on your router, and 20 route entries per VPC. The correct architecture for multi-VPC environments: one Transit VIF → DX Gateway → Transit Gateway → all VPCs. One BGP session on your router, one route entry per VPC CIDR in TGW's route table. Migrate to this pattern early; retrofitting it is painful.

3.3 Canonical Patterns

Pattern 1: DX Primary + VPN Backup (Standard FSI)

Single DX connection (or LAG) as primary path. BGP LOCAL_PREF or MED set so DX routes are preferred. Site-to-Site VPN as backup over internet. BFD on DX VIF detects failure in <1 second. BGP converges and VPN routes become active. Failover is automatic — no human intervention. RTO for connectivity failure: <5 seconds with BFD. This is the architecture in virtually every Singapore FSI AWS deployment.

Pattern 2: Dual DX (Diverse Locations)

Two DX Dedicated Connections from two different DX locations (e.g., Equinix SG1 and Equinix SG2). Traffic load-balanced via ECMP BGP or Active/Passive with MED preference. Provides full redundancy against a single DX location failure — not just a circuit failure. Higher cost but appropriate for critical financial workloads where DX failure must not cause any outage. Each DX connects to the same DX Gateway and TGW.

Pattern 3: Transit VIF + TGW Hub (Multi-VPC Scale)

One DX connection → Transit VIF → DX Gateway → Transit Gateway → all workload VPCs. On-prem router has one BGP session. New VPCs are added to TGW without any DX or BGP change — just add a TGW attachment. This is the correct architecture for any Organisation with 5+ VPCs. Scales to hundreds of VPCs with a single DX connection.

Pattern 4: Public VIF for S3/Service Access

A dedicated Public VIF on the same DX connection as the Private VIF. On-prem workloads access S3, ECR, and other public services without hairpinning through the VPC. Direct path: on-prem → DX → AWS public endpoints. Eliminates the common pattern of routing S3 traffic through a NAT Gateway in the VPC (expensive, adds latency). Data transfer over DX Public VIF to S3 is not billed for DX data-out — only S3 standard egress rates apply.

Pattern 5: DX + VPN for Multi-Region DR

Primary DX to ap-southeast-1 (Singapore) via DX Gateway. DX Gateway also attached to ap-southeast-3 VGW (Jakarta) for DR. VPN backup for both regions. In a DR event where ap-southeast-1 is unavailable, the DX Gateway remains connected to ap-southeast-3. No new physical connection required. The DX Gateway's global nature is the design advantage — one physical connection, connectivity to any AWS region you attach to the DXGW.

🚫 Anti-Pattern: Single DX, No VPN Backup

A single DX connection with no VPN backup is an availability risk that fails MAS TRM §14 BCM requirements. DX connections do fail — maintenance windows, cable cuts, equipment failures at the DX location. Without VPN backup, a DX failure means complete loss of AWS connectivity. In 2019, a major AWS DX location outage in Asia-Pacific affected hundreds of customers who had no backup path. Every production DX deployment must have a VPN backup, even if VPN performance is inadequate for normal workloads — it provides connectivity for management access and low-volume traffic during DX outages.

🤖 AI / Agentic Angle

AI inference latency is acutely sensitive to network path quality. An agentic workflow running on-premises (e.g., a trading platform's pre-trade risk engine) calling a Bedrock endpoint for real-time market commentary requires consistent, sub-10ms round-trip to AWS. Over internet VPN this is unreliable; over DX it's 4–6 ms consistently. For hybrid AI architectures where on-prem model inference feeds into AWS orchestration layers (Step Functions, Lambda), DX is not optional — it's the difference between a viable agentic response latency (under 200ms end-to-end) and an unacceptable one. As LLM inference moves toward real-time applications in FSI, DX connectivity becomes part of the AI architecture design, not just the network design.

04 / PREREQUISITES

Prerequisites & Environment Setup #

For Direct Connect

  • AWS account with billing and appropriate IAM permissions (directconnect:*)
  • Physical presence at or arrangement with a DX location: For Singapore, this means Equinix SG1/SG2, Global Switch, or an APN Partner with a Hosted Connection offering. For the lab, you'll use a Hosted Connection simulation or the console-only walkthrough.
  • BGP-capable router with a configured ASN. For lab use, a software router (VyOS, FRR on a VM) suffices.
  • VPC already created in ap-southeast-1 with CIDR that doesn't overlap with your on-prem range. If using Transit VIF: TGW also created (Guide 02).
  • BGP ASN for your side: Private ASN (e.g., 65000) is fine for Private VIF. Document it — you'll need it when creating the VIF in the console.

For Site-to-Site VPN

  • Customer gateway device: Public IP required (static preferred; dynamic IP CGW supported with certificate-based authentication). For the lab, use a VyOS or pfSense VM with a public IP, or AWS's VPN simulator.
  • VGW or TGW already created and attached to your VPC
  • Pre-shared key or certificate: The console generates a pre-shared key by default; certificate-based is more secure for production
  • On-prem subnet ranges that will be advertised via BGP to AWS
💰 Cost Warning
  • DX Dedicated Connection port: 1 Gbps = $216/month; 10 Gbps = $1,620/month (ap-southeast-1). This is the port fee regardless of traffic volume.
  • DX data transfer out: $0.02/GB (within AWS to on-prem over DX, ap-southeast-1). Standard AWS data transfer rates apply inbound.
  • DX Gateway: Free. No charge for the gateway object itself.
  • Site-to-Site VPN: $0.05/hr per VPN connection = ~$36/month per connection. Plus standard data transfer rates.
  • LAG: Billed per individual connection in the LAG — 4× 10 Gbps LAG = 4× $1,620 = $6,480/month.
  • Lab estimate: If you use a Hosted Connection from a partner for the lab, expect ~$100–200 for a 50 Mbps connection/month. VPN lab costs ~$5 for a few hours.
🌉 Bridge from Storage/Virtualisation

Setting up DX prerequisites ≈ ordering a new uplink to a colocation facility. You need: (1) your equipment racked at the colo (or a patch to your existing equipment), (2) the LOA paperwork authorising the cross-connect, (3) the cross-connect physically installed by the colo's hands-and-eyes team, (4) the logical configuration (BGP ASN, IP addresses, VLANs) agreed between you and the upstream provider. In AWS's case, the "upstream provider" is AWS itself — they provision the router port, you provision the VIF, and BGP does the rest. The process is the same as any carrier circuit turn-up; only the AWS console replaces the carrier's order portal.

💡 The Asymmetric Routing Problem

A common production issue: on-prem traffic goes out via DX (preferred by LOCAL_PREF) but return traffic from AWS comes back via VPN (AWS doesn't know to prefer DX without MED or AS_PATH guidance). This creates asymmetric routing — stateful firewalls drop the return traffic as "unsolicited." Fix: use MED to guide AWS return traffic to the DX path. Set MED=100 on DX BGP advertisements, MED=200 on VPN BGP advertisements. AWS uses MED as a hint to prefer the lower value — traffic in both directions now follows DX.

aws ec2 describe-route-tables --route-table-ids rtb-xxxx \

Step 2 — The Deliberate Misconfiguration: BFD Not Enabled

You discover BFD was never enabled on the DX VIF. BGP holddown timer was at default 90 seconds. It took 90 seconds after DX failure for BGP to declare the DX peer down and withdraw routes — during which traffic was blackholed. VPN routes only became active after BGP converged.

Impact: 90-second connectivity outage instead of the <1 second that BFD would have provided. For a payments system processing real-time transactions, this was a material incident.

bash — Enable BFD (requires brief BGP session restart)

# On AWS side — check current BFD status
aws directconnect describe-virtual-interfaces \
  --virtual-interface-id dxvif-xxxx \
  --query 'virtualInterfaces[*].{BFD:awsDeviceName}'

# BFD is enabled when creating the VIF in the console (checkbox)
# For an existing VIF, you must delete and recreate it — there's no update API for BFD
# Plan a maintenance window for the VIF recreation

# On your router (Cisco IOS-XE example):
# interface GigabitEthernet0.100
#  bfd interval 300 min_rx 300 multiplier 3
# router bgp 65000
#  neighbor 169.254.1.1 fall-over bfd

# After BFD is active, test failover:
# Shut down the DX-facing interface on your router
# BFD detects within 900ms (300ms × 3)
# BGP withdraws DX routes, VPN routes take over
# Restore interface → BFD detects within 900ms → DX BGP re-establishes → routes restored

DXVIF shows "Available" but BGP status is "down" — no routes in VPC▼

Cause: The VIF's physical state is up but BGP session isn't established. Common causes: (a) incorrect BGP peer IP on your router — must match what you configured in the VIF (the Amazon router IP), (b) wrong BGP ASN — your router is advertising a different ASN than what was configured in the VIF, (c) BGP auth key mismatch — MD5 key configured on AWS VIF doesn't match your router's, (d) ACL/firewall blocking BGP (TCP 179) between your router and the AWS DX router IP, (e) BGP process not started on your router.

Fix: Check the VIF's BGP peer details in the console — confirm the Amazon router IP (169.254.x.x) and your router IP match what's configured on your router's sub-interface. Check BGP summary on your router: show bgp summary (Cisco) or show ip bgp summary. Look for Active or Idle state — Active means your router is trying to connect but AWS isn't responding (usually ASN or IP mismatch). Idle means your BGP process isn't trying at all.

DXBGP is up but on-prem hosts can't reach VPC instances — no routes in VPC route table▼

Cause: Route propagation is not enabled on the VPC route table. This is the #1 most common DX/VPN configuration miss. BGP session is up, routes are in the VGW's BGP table, but they're not propagated into the VPC route table that instances use. Fix: VPC → Route tables → select the private route table → Route propagation tab → Edit route propagation → enable for your VGW. Routes appear in the route table within seconds. Also check: are instances in the correct subnet using the private route table? Security Groups on the instances — are they allowing the on-prem source IP range?

VPNVPN tunnel shows "Up" but no traffic flows — intermittent packet loss▼

Cause: Most commonly, MSS (Maximum Segment Size) clamping is not configured on your router. IPSec adds overhead (50–100 bytes) to each packet. Without MSS clamping, large TCP packets exceed the VPN tunnel MTU, get fragmented or dropped. The tunnel appears up (ICMP pings work — they're small), but large data transfers (HTTPS, file copies) fail or are very slow.

Fix: Configure TCP MSS clamping on your router's VPN tunnel interface to 1379 bytes (AWS recommends this for its VPN). On Cisco: ip tcp adjust-mss 1379 on the tunnel interface. On Linux: iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --set-mss 1379. Also check: are both VPN tunnels configured? AWS provides two tunnels for HA — if only one is configured, you lose redundancy within the VPN itself.

DXAsymmetric routing — traffic from on-prem reaches VPC via DX but return traffic comes back via VPN▼

Cause: Your router uses LOCAL_PREF to prefer DX for outbound traffic, but AWS has no guidance on which path to use for return traffic — it load-balances or uses its own path selection. Return traffic via VPN + stateful firewall on-prem = firewall drops packets as unsolicited connections.

Fix: Use MED (Multi-Exit Discriminator) to guide AWS's return path. In your BGP advertisements to AWS, set MED lower for the DX VIF (e.g., MED=100) and higher for the VPN (MED=200). AWS uses MED as a hint to prefer the lower value for the same prefix. On Cisco: in the BGP outbound route-map, set metric 100. Verify with: run a traceroute from an EC2 instance to your on-prem IP — the first hop beyond VGW should go through the DX path, not internet.

DXPrivate VIF shows "Available" but DXGW association is "Disassociated"▼

Cause: The DX Gateway association with a VGW or TGW was deleted or failed to complete. Or: the allowed prefixes on the DXGW association don't include the on-prem prefixes being advertised — the DXGW filters routes that don't match the allowed prefix list.

Fix: Re-associate the VGW/TGW with the DXGW via Direct Connect → Direct Connect gateways → associations → Associate gateway. Verify the allowed prefixes include all on-prem CIDR ranges you're advertising. The allowed prefixes is a whitelist — prefixes not listed are silently dropped by the DXGW even if BGP is up.

DXDX connection stuck in "Requested" state for weeks▼

Cause: The LOA-CFA (Letter of Authorization) was not submitted to the colocation facility, or the facility is experiencing a delay. For Dedicated Connections, the cross-connect is not automatically installed — you must submit the LOA to the facility's remote hands team. Fix: Download the LOA-CFA from Direct Connect → Connections → select connection → Download LOA-CFA. Submit to the colocation facility's customer portal or remote hands team. Typical lead time: 3–10 business days at Equinix SG1. Once the cross-connect is installed, the connection transitions to "Pending" then "Available." If the LOA has expired (they're time-limited), request a new one from AWS Support.

14 / SECURITY

Security Hardening Deep Dive #

Encryption in Transit — DX vs VPN

Direct Connect is not encrypted by default. The physical circuit is private (not internet-routed), but traffic on the wire is cleartext unless you add encryption. For MAS TRM §11.3.2 compliance, you must add encryption on top of DX. Two options:

🔒

MACsec (Recommended for DX)

IEEE 802.1AE Layer 2 encryption. Available on 10 Gbps and 100 Gbps Dedicated Connections. Wire-speed, no latency penalty. Encrypts at the Ethernet frame level between your CE router and the AWS DX router at the DX location. Configure with a CAK (Connectivity Association Key) pre-shared between your router and AWS.

🛡️

IPSec over DX

Run a Site-to-Site VPN tunnel over the DX connection instead of the internet. Provides Layer 3 encryption. Works on all connection speeds (unlike MACsec). Slight performance overhead from IPSec processing. Uses the DX path (consistent latency) while adding encryption. Common for <10 Gbps Hosted Connections that don't support MACsec.

🌐

TLS/Application Layer

Application-level encryption (HTTPS, TLS 1.3) provides end-to-end encryption regardless of network path. Satisfies encryption requirements but doesn't prevent network-level inspection at the DX location. Use in addition to, not instead of, MACsec or IPSec.

📵

Private VIF ≠ Encryption

A common misconception: "DX is private, so it's secure." Private only means the traffic doesn't traverse the public internet. The DX location is a shared colocation facility — other tenants are present. Without MACsec or IPSec, traffic on the cross-connect is plaintext Ethernet frames. For regulated data (PII, financial transactions), MACsec or IPSec is mandatory.

Multi-Region DX Design via DX Gateway

The DX Gateway's global nature makes multi-region DR connectivity straightforward. One DX connection in Singapore (Equinix SG1) attaches to a DX Gateway. The DX Gateway is associated with VGWs in both ap-southeast-1 (primary) and ap-southeast-3 (DR). In normal operation, on-prem traffic routes to ap-southeast-1 VPCs via the DX path. In a DR event where ap-southeast-1 workloads fail over to ap-southeast-3, the existing DX connection provides connectivity to the DR region automatically — no new circuit, no new BGP session.

BGP prefix advertisement controls which region is active: when ap-southeast-1 is primary, the ap-southeast-1 VGW advertises VPC CIDRs with normal MED. When failing over to ap-southeast-3, the ap-southeast-3 VGW starts advertising its VPC CIDRs. On-prem routers see the new prefixes and begin routing to the DR VPCs. RTO for this path: seconds (BGP convergence time), not hours (physical circuit provisioning).

Pattern 3: Public VIF for High-Throughput S3 / ECR Access

Many FSI organisations route S3 and ECR traffic through a NAT Gateway in their VPC, adding latency and cost ($0.045/GB through NAT Gateway + $0.09/GB internet egress from S3). Alternative: a Public VIF on the same DX connection gives direct access to S3 and ECR public endpoints without traversing the VPC at all. Path: on-prem → DX Public VIF → S3/ECR directly. Data transfer cost over DX: $0.02/GB (vs $0.045 + $0.09 = $0.135/GB via NAT). For an organisation pulling 50 TB/month of Docker images from ECR: DX Public VIF = $1,000/month vs NAT Gateway path = $6,750/month. The Public VIF pays for itself at moderate transfer volumes.

Pattern 4: Accelerated Site-to-Site VPN

Standard Site-to-Site VPN tunnels terminate on AWS VPN endpoints in the same region. For organisations geographically distant from the AWS region (e.g., connecting from Europe to ap-southeast-1), the internet path introduces high latency. Accelerated VPN uses AWS Global Accelerator as the anycast entry point — your VPN traffic enters the AWS backbone at the nearest AWS edge location (e.g., London) and travels over AWS's private backbone to ap-southeast-1. Latency reduction: 30–50% for long-distance VPN. Premium: slightly higher cost. Use for: disaster recovery from distant locations, global employee connectivity, any VPN where latency is critical but DX isn't available yet.

Anti-Pattern: Private VIF Per VPC at Scale

An early DX architecture that worked for 2–3 VPCs but becomes unmanageable at 10+: one Private VIF per VPC, each with its own BGP session on your router. Problems at scale: (a) your router's BGP table has N sessions × M routes, where N grows with every new VPC. (b) Adding a new VPC requires provisioning a new VIF, BGP session configuration change on your router, and potentially a new VLAN. (c) Route summarisation becomes complex when each VPC has different CIDR ranges. (d) You approach the 50 VIF per connection limit. Solution: migrate to Transit VIF → DX Gateway → TGW pattern. One BGP session, all VPCs reachable via TGW routing.

19 / FAQ

Regular FAQ — Beginner Focused #

BeginnerIs Direct Connect encrypted?▼

No — Direct Connect is not encrypted by default. It provides a private circuit (your traffic doesn't traverse the public internet), but traffic on the wire is cleartext unless you add encryption. For MAS TRM §11.3 compliance, add MACsec (Layer 2 encryption, available on 10/100 Gbps Dedicated Connections) or run IPSec VPN tunnels over the DX connection. "Private" and "encrypted" are different properties — DX is private, but encryption is your responsibility to add.

BeginnerHow long does it take to get Direct Connect?▼

For a Dedicated Connection (1/10/100 Gbps ordered from AWS directly): 2–8 weeks typically. After submitting the order, AWS provisions the port in 3–5 business days and provides an LOA-CFA. You submit this to the colocation facility (e.g., Equinix SG1) which installs the cross-connect — typically another 5–10 business days. Then you provision the VIF and BGP. Total: 2–6 weeks from order to BGP up. For a Hosted Connection from an APN Partner (e.g., Singtel): days to 2 weeks — the partner already has the physical connection, they just provision a slice for you. Start DX orders at project kick-off, not when you need connectivity.

BeginnerWhat's the difference between a VGW and a TGW for VPN/DX termination?▼

A Virtual Private Gateway (VGW) is attached to a single VPC — it terminates VPN or DX Private VIF connections for that one VPC. A Transit Gateway (TGW) is a regional hub that can have many VPCs, VPN connections, and DX Transit VIFs attached. For one VPC: VGW is simpler. For multiple VPCs: TGW is the right answer — one VPN or Transit VIF can reach all TGW-attached VPCs through TGW route tables. At scale (5+ VPCs), always use TGW.

BeginnerDo I need BGP for VPN? Can I use static routing?▼

Static routing works but has significant limitations. With static routes, you manually define which IP ranges go over the VPN. Failover between the two VPN tunnels is not automatic — if Tunnel 1 goes down, traffic doesn't automatically shift to Tunnel 2 without manual intervention or monitoring. With BGP (dynamic routing), route exchange is automatic, both tunnels participate in BGP, and failover between tunnels is automatic. For any production use, always use BGP. Static routing is only appropriate for testing or very simple non-critical dev environments.

BeginnerWhy are there always two VPN tunnels?▼

AWS always provisions two IPSec tunnels per VPN connection, terminating on endpoints in different Availability Zones. This provides redundancy for AWS-side maintenance and failures. Both tunnels connect to the same Customer Gateway (your router) and can carry traffic simultaneously (Active/Active with ECMP) or in Active/Standby mode. Both tunnels should always be configured on your router — leaving one unconfigured means you lose the built-in HA. AWS charges for the VPN connection, not per tunnel — both tunnels are included in the $0.05/hr price.

ArchitectWhat is the DX Gateway for and do I always need one?▼

The DX Gateway is a global resource that enables one DX connection to reach VGWs or TGWs in multiple AWS regions. Without a DXGW, a Private VIF connects to one VGW in one region only. With a DXGW, the same VIF connects to the DXGW which is associated with VGWs/TGWs in any region worldwide. You need it if: (a) you want to connect to VPCs in multiple regions from one DX connection, or (b) you're using Transit VIF to reach a TGW. For a single-region, single-VPC deployment, a DXGW is optional — you can attach a Private VIF directly to a VGW. For any multi-VPC or multi-region deployment, DXGW is the correct architecture.

Principal Architect Interview Q&A #

Principal"Design the network connectivity from a Singapore FSI firm's DC to AWS ap-southeast-1 for a critical payments platform."▼

Strong answer: "For a critical payments platform, I'd design for zero-tolerance on connectivity failure with both performance and compliance requirements. The architecture: two 10 Gbps Direct Connect Dedicated Connections from different DX locations — Equinix SG1 and Equinix SG2. Diverse paths eliminate single-facility failure as a risk. MACsec enabled on both connections for Layer 2 encryption — satisfies MAS TRM §11.3.2 without IPSec overhead.

Both DX connections attach to a Direct Connect Gateway via Transit VIFs. The DX Gateway associates with a Transit Gateway in ap-southeast-1, which serves all production VPCs. This gives us one BGP session per DX connection, and adding new VPCs doesn't require any DX or BGP changes — just attach to TGW.

BFD enabled on all VIFs at 300ms/3 multiplier — sub-second failure detection. BGP traffic engineering: MED 100 on DX advertisements to AWS (prefer DX for return traffic), MED 200 on VPN. LOCAL_PREF 200 on DX routes on our router (prefer DX for outbound). AS_PATH prepending on VPN backup advertisements.

Site-to-Site VPN (IKEv2, AES-256-GCM) as last-resort backup over internet. Even though VPN can't carry full production bandwidth, it maintains management access and critical low-volume payment traffic during DX outages. The DX Gateway also attaches to ap-southeast-3 TGW for DR connectivity — no additional circuit needed when failing over to the DR region. Annual failover test per MAS TRM §14.2."

Principal"We have 20 VPCs and are currently using Private VIFs for the first 5. How do we scale to all 20?"▼

Strong answer: "Private VIFs don't scale beyond a handful of VPCs because each requires a separate VGW attachment and BGP session on your on-prem router. At 20 VPCs you'd have 20 BGP sessions, potentially approaching the 50 VIF per connection limit, and every new VPC requires a VLAN and VIF change. The migration path is to Transit VIF + DX Gateway + Transit Gateway.

Migration approach: First, create a TGW and attach all VPCs to it (this doesn't break existing connectivity). Then create a DX Gateway and associate the TGW with it. Create a Transit VIF pointing to the DXGW — this is the new unified connectivity path. Test connectivity through the Transit VIF to all VPCs. Once verified, decommission the existing Private VIFs one by one during maintenance windows. The on-prem router config simplifies from 5 BGP sessions to 1. Future VPC additions require only a TGW attachment — no DX changes needed. The entire migration can be done without a connectivity outage if planned correctly."

Principal"After a DX maintenance window, we noticed traffic from AWS was coming back via VPN instead of DX. What happened?"▼

Strong answer: "This is asymmetric routing — your on-prem traffic is going out via DX (correct, based on LOCAL_PREF on your router), but AWS return traffic is using the VPN path. The root cause is missing or misconfigured BGP traffic engineering on the AWS-facing advertisements.

When both DX and VPN advertise the same on-prem prefixes to AWS, AWS needs guidance on which path to use for return traffic. Without MED, AWS may choose the VPN path based on its own internal route selection (shortest AS_PATH, lower peer preference, or load balancing). Fix: configure your BGP outbound route-map to set MED=100 on DX VIF advertisements and MED=200 on VPN advertisements. AWS uses MED as a hint — lower value preferred for the same prefix from the same ASN. After applying, use traceroute from an EC2 instance to your on-prem IP to verify the return path goes through the DX endpoint. The issue likely surfaced after the maintenance window because the BGP session was reset and re-advertised routes may have different attributes than before."

Principal"Explain why Direct Connect provides better latency than VPN even when both use the same physical path from the DC to the ISP."▼

Strong answer: "The latency advantage of DX over VPN comes from the network path, not the encryption overhead. IPSec processing on modern hardware adds less than 1ms — that's not the differentiator. The difference is the network path itself.

With Site-to-Site VPN, the IPSec tunnel endpoint is a VPN gateway in the AWS region. Your traffic goes: DC → your ISP → internet backbone → AWS's edge → AWS network → VPN endpoint → VPC. The internet portion involves multiple hops across public peering points, congestion at IX (internet exchange) peering, and variable routing. Singapore to ap-southeast-1 over the internet: 10–30ms, variable.

With Direct Connect, the physical circuit goes from your DC cross-connect at Equinix SG1 directly to AWS's router at that same facility. The traffic then flows over AWS's private network backbone — not the public internet — from the DX location to the AWS VPC. AWS's Singapore DX locations are co-located with or directly connected to AWS's ap-southeast-1 region infrastructure. Singapore DC to ap-southeast-1 over DX: 2–5ms, consistent. The internet path is eliminated. This consistency is what makes DX suitable for financial-grade workloads — not the average latency, but the p99 latency and the absence of congestion-driven variability."

Principal"A client has one DX connection that just failed. They have no VPN backup. What are their options in the next 30 minutes?"▼

Strong answer: "Honest answer: their options in 30 minutes are limited, which is why this is a design failure, not just an operational failure. The immediate options: (1) If they have internet access from on-prem, set up a Site-to-Site VPN immediately. Creating a VPN in AWS takes 5 minutes. Configuring it on a Cisco/Juniper router takes another 10–15 minutes for a basic IPSec config. BGP up within 30 minutes is achievable if there's someone on the router console. VPN performance will be limited but connectivity is restored.

(2) If they have workloads that can tolerate DNS cutover, shift traffic to any internet-facing endpoints (API Gateway, ALB with internet-facing DNS) temporarily. This bypasses the DX dependency for some traffic. (3) For non-time-sensitive workloads, they wait for DX restoration — AWS's SLA for DX is 99.9% (for a single connection) which means up to 8.7 hours downtime per year is within SLA.

The broader response: use this incident to justify the VPN backup architecture. The business case now includes the actual downtime cost from this event. Going forward: VPN backup provisioned and tested before the next DX maintenance window. The post-incident action item is not just 'add VPN' but 'add VPN, test annual failover, and establish an operational runbook.' This is the MAS TRM §14 BCM requirement that was never implemented."

Key Terraform Patterns for DX/VPN

Route propagation via for_each: The aws_vpn_gateway_route_propagation resource must be applied to every route table that needs on-prem routes. Using for_each = toset(var.route_table_ids) ensures all route tables are covered without duplicating code.

VGW vs TGW conditional attachment: The VPN connection accepts either vpn_gateway_id or transit_gateway_id — not both. The conditional pattern shown uses a variable to switch between the two, keeping the module reusable.

Physical DX connection ID as a variable: The DX physical connection cannot be created by Terraform — it requires the LOA-CFA process. The connection ID from the AWS console is passed in as a variable. The VIF resources (aws_dx_private_virtual_interface, aws_dx_transit_virtual_interface) use this ID to create the logical layer on top of the physical connection.

PSK in variables, not hardcoded: Pre-shared keys must come from Secrets Manager, not from source code. In the module, var.vpn_psk_tunnel1 is passed in from a Secrets Manager data source in the calling module. Never hardcode PSKs in Terraform — they end up in tfstate (which is stored in S3) and in git history.
