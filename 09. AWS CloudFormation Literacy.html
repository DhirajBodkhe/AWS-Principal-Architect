Glossary & Key Terms #

CloudFormation (CFn)AWS's native IaC service. You write a template describing desired infrastructure state in YAML or JSON; CloudFormation provisions, updates, and deletes resources to match. AWS-managed, no state file to maintain.≈ A vSphere declarative config profile — you describe the VM spec, vSphere provisions it. No manual steps.
StackA single deployed instance of a CloudFormation template. All resources in a stack are created, updated, and deleted together as a unit. The stack is the unit of deployment and rollback.≈ A vApp — a collection of related VMs and resources treated as one deployable unit
TemplateThe YAML or JSON file that defines resources, parameters, outputs, and mappings. The blueprint. Stack SetDeploys the same CloudFormation template across multiple AWS accounts and regions simultaneously from a single management account. Change SetA preview of what changes a template update will make to an existing stack — before applying it. Shows which resources will be added, modified, or replaced (deleted + recreated). The "plan" step, equivalent to terraform plan.≈ A pre-migration checklist — see what will change before committing. Like reviewing snapshot deltas before a storage migration.

Identifies resources that were manually changed outside of CloudFormation ("drift"). Equivalent to configuration compliance checking.≈ A configuration compliance scan — comparing actual server config against the standard build profile to find deviations

Example: EnvironmentType: prod | staging | dev changes resource sizes based on the value passed.≈ Parameters in an Ansible playbook — the same playbook runs differently based on the inventory/variable file provided
OutputsValues exported from a stack — VPC ID, load balancer DNS name, security group ID. Other stacks can import these outputs via cross-stack references. The interface between stacks.≈ The discovered values from a provisioning script that you pass to the next script in a pipeline
MappingsStatic lookup tables inside a template. Example: map region to AMI ID. Used to make templates region-agnostic without parameters. Evaluated at deploy time.≈ A config lookup table in your provisioning script — "if DC is SG1, use these IP ranges; if DC is SG2, use these"

DependsOnExplicit dependency declaration between resources. CDK is the language; CFn is the deployment engine underneath.≈ Writing VMware automation in Python (pyVmomi) vs writing raw API XML — CDK gives you a proper programming language over CFn's configuration format

The parent stack manages child stack lifecycle.≈ A modular provisioning script that calls sub-scripts — each sub-script is independently deployable but the master script orchestrates the full build
Stack PolicyA JSON document that protects specific resources in a stack from being modified or deleted during updates. Prevents accidental replacement of production databases during template updates.≈ A write-protect flag on a storage volume — prevents unintended modification of critical data
01 / CONCEPT

Concept & Mental Model #

The Goal of This Guide — Literacy, Not Authorship

CloudFormation is the dominant IaC tool in existing AWS enterprise environments — not because it's better than Terraform or CDK, but because it was first, it's AWS-native, and hundreds of thousands of organisations deployed it before alternatives matured. When you join a client engagement, there is a 70%+ probability their existing infrastructure is managed in CloudFormation. You will not rewrite it on day one. You need to read it, understand it, and work with it.

The goal of this guide: read any CFn template and understand what it deploys, why it's structured the way it is, and whether it has problems. Write basic CFn only when necessary. Let CDK or Terraform generate CFn for you when possible. Review CFn templates the way a senior engineer reviews any infrastructure code — with the ability to spot risks, not just parse syntax.

What Problem CFn Solves

Before IaC, AWS environments were created manually through the console or via scripts that called the AWS API imperatively. Two problems: (1) drift — the console click-path that created the environment isn't reproducible; what was created isn't documented in runnable form. (2) consistency — different engineers created similar environments differently, with no enforcement of standards. CloudFormation solved both: the template IS the documentation, and deploying the same template guarantees the same result every time.

Declarative vs Imperative — The Key Mental Shift

Imperative IaC (Bash + AWS CLI) says: "Create an S3 bucket, then enable versioning, then set the lifecycle policy." The order matters. If the bucket already exists, the script fails unless you write explicit handling. Declarative IaC (CFn, Terraform) says: "The desired state is: an S3 bucket with versioning enabled and this lifecycle policy." CloudFormation figures out what API calls to make to reach that state — whether it's a fresh create, an update, or a no-op. This is the mental shift from scripting to IaC. You describe the destination, not the journey.

CFn vs Terraform — The Honest Comparison

CloudFormation: AWS-native, no state file to manage, tight AWS service integration (new services appear in CFn within weeks of launch), StackSets for multi-account deployment, free. Weaknesses: YAML/JSON only (verbose, error-prone), no multi-cloud, no modules ecosystem comparable to Terraform Registry, rollback behaviour can be opaque, error messages are notoriously unhelpful, no plan equivalent without Change Sets (which are slower). Terraform: multi-cloud, HCL is more readable than CFn YAML, excellent module ecosystem, terraform plan is faster than a Change Set, state file is an operational burden and a security concern. For new greenfield work: Terraform. For existing client CFn environments: read and work with CFn, propose CDK or Terraform migration on a timeline that makes sense.

🌉 Bridge from Storage/Virtualisation

CloudFormation ≈ a storage array configuration profile applied declaratively. On a NetApp or Pure Storage array, you define a volume configuration profile — size, QoS, protocol, snapshot policy — and apply it. The array provisions the volume to match. If you update the profile, the array reconciles the actual volume to the new desired state. CFn works identically: the template is the profile, the stack is the deployed instance, and update operations reconcile actual state to the declared template. Drift detection ≈ a configuration compliance scan that compares actual array configuration against the policy profile — flags volumes that were manually changed outside the management system. StackSets ≈ a mass-push of a configuration profile to all arrays in a fleet simultaneously, with rollback if any fail.

💡 Why This Matters — You'll Review CFn, Not Write It

In 80% of enterprise AWS engagements, CloudFormation templates exist and must be understood. Control Tower (Guide 05) uses CFn under the hood for account vending. AWS Service Catalog distributes CFn templates. Partner solutions arrive as CFn templates. AWS Quick Starts are CFn. When a client says "here's our landing zone template" — it's CFn. Your ability to read it quickly, understand the resource graph, and spot misconfigurations (overly permissive SGs, missing encryption, absent deletion policies on databases) is what distinguishes a senior architect from someone who only works in their preferred tool.

Resource Graph and Dependency Resolution

CloudFormation builds a dependency graph from your template automatically. When you use !Ref MyVPC inside an EC2 resource, CFn knows the VPC must exist before the EC2 instance — it handles the ordering. Resources with no dependencies are created in parallel. Resources with explicit DependsOn or implicit Ref/GetAtt dependencies are created sequentially. Understanding this graph is how you debug slow or stuck stack deployments — identify which resource is the bottleneck in the dependency chain.

💡 The Resource Graph Is Your Debug Tool

When a stack gets stuck in CREATE_IN_PROGRESS for 20+ minutes, find the blocking resource in the Events tab and trace its dependencies backward. The resource waiting is almost always waiting for a resource above it in the dependency chain. Common blockers: custom resources (Lambda-backed) with timeouts, VPC waiting for NAT Gateway (which waits for EIP which waits for IGW), IAM roles with circular trust policies. The Events tab shows the real-time status — refresh it during deploys to see the execution order.

3.3 Canonical Patterns

Pattern 1: Layered Stacks (Network → Compute → App)

Separate templates for each layer: networking stack (VPC, subnets, route tables, IGW, NAT GW), compute stack (EC2 ASG, launch template, ALB — imports VPC outputs), application stack (RDS, ElastiCache, EFS — imports compute outputs). Each layer is independently deployable and independently updateable. Networking changes don't require touching application stacks. Cross-stack references via Outputs/ImportValue wire the layers together. This is the correct pattern for any non-trivial environment.

Pattern 2: StackSets for Landing Zone Baseline

From the management account, a StackSet deploys the same baseline to every new account: default VPC deletion, CloudTrail org trail, Config recorder, GuardDuty enablement, IAM password policy, S3 block public access. New accounts receive the baseline automatically via OU-targeted StackSet deployment. Any drift (someone disabled GuardDuty manually) is detected centrally and can be remediated by updating the StackSet.

Pattern 3: Service Catalog + CFn for Self-Service

Platform team creates CFn templates for approved resource configurations (approved EC2 sizes, approved RDS configurations, approved VPC patterns). These are published as Service Catalog products with constraints (can't choose instance types outside the approved list, must provide mandatory tags). Application teams self-serve from the catalog without needing AWS console access. Every resource is tagged, compliant, and within approved configurations. Common FSI pattern for separation of duties between platform and application teams.

🚫 Anti-Pattern: Monolithic Templates

A single CFn template deploying VPC, EC2, RDS, ALB, IAM roles, S3 buckets, and Route 53 records. Problems: (a) Any failure rolls back the entire stack — a misconfigured RDS option tears down an otherwise successful VPC deployment. (b) Templates approach the 500-resource limit. (c) Update operations on one resource (e.g., scaling EC2) require touching the whole template. (d) Teams can't independently manage their layer. Break large stacks into layers. Use nested stacks or cross-stack references. The 200-resource limit per stack is a hard constraint that forces decomposition for large deployments.

🤖 AI / Agentic Angle

04 / PREREQUISITES

Prerequisites & Environment Setup #

Tools Required

  • cfn-lint: pip install cfn-lint — validates templates before deployment. Non-negotiable. Every template should pass cfn-lint before being submitted.
  • AWS CLI v2: For stack operations, describe-stacks, describe-stack-events. Already installed from earlier guides.
  • Python 3.8+ (for CDK intro): CDK supports multiple languages; Python is the most accessible for infrastructure engineers without a JavaScript background.
  • AWS CDK: npm install -g aws-cdk — even if you only use the synth output, understanding how CDK generates CFn is valuable.
  • A text editor with YAML support: VS Code with the AWS Toolkit extension provides CFn template autocomplete, validation, and inline documentation. Strongly recommended.
⚠️ YAML Indentation — The Silent Killer

More CFn deployments fail due to YAML indentation errors than any other cause. YAML uses spaces (not tabs) for indentation, and the nesting level must be exactly correct. A property indented one space too many or too few becomes a different structure than intended — and CFn's error messages ("Template format error") don't always tell you where. Always use a YAML-aware editor with visible indentation markers. VS Code with the YAML extension shows indentation guides. Run cfn-lint before every deployment — it catches indentation problems as syntax errors before they hit the API.

🌉 Bridge from Storage/Virtualisation

Setting up a CFn development environment ≈ installing a storage management client. You wouldn't manage a NetApp array without ONTAP System Manager or the ONTAP CLI — you'd miss too much validation and context. Similarly, writing CFn in a plain text editor without cfn-lint or the AWS Toolkit is flying blind. cfn-lint ≈ the pre-flight validation step on an ONTAP upgrade — run it before touching production, catch problems in a safe environment. The cfn-lint database contains the full AWS resource specification — every property, every required field, every valid value. It catches configuration errors that would otherwise take a 10-minute stack rollback to discover.

05 / GUI IMPLEMENTATION

Step-by-Step GUI Implementation #

Three parts: (A) Deploy a stack from a template, (B) Create and execute a Change Set, (C) Run Drift Detection.

Part A: Deploy a Stack

1
Create a New Stack from Template
WhereCloudFormation → Stacks → Create stack → With new resources (standard)
Template sourceSelect Upload a template file → choose your YAML file. Alternatively: Amazon S3 URL if the template is in S3 (required for templates >51KB). Use a sample template — AWS provides example templates for learning (LAMP stack, WordPress, etc.).
DesignerClick View in Designer to see a visual graph of the resources in the template before deploying. This is the fastest way to understand an unfamiliar template — the graph shows resources and dependencies visually.
Why S3 for large templatesCFn has a 51KB limit for templates uploaded directly. Production templates regularly exceed this. Best practice: always store templates in S3 and reference via URL, even for small templates — consistent workflow, no size surprises.
2
Configure Stack Details and Parameters
Stack namenetrust-network-prod — use a consistent naming convention: {org}-{layer}-{environment}. Stack name is permanent and becomes part of resource physical IDs.
ParametersFill in values for any Parameters defined in the template. Good templates use SSM Parameter Store for defaults — you'll see AWS::SSM::Parameter::Value type parameters that auto-resolve from SSM.
TagsApply stack-level tags — these are inherited by all resources created by the stack (for those resources that support tag inheritance). This is how you ensure tagging consistency — set Environment, Team, and CostCentre here and everything in the stack gets those tags.
PermissionsIAM role for CloudFormation to use. If left blank, CFn uses the permissions of the deploying IAM user. Production: always specify a dedicated CFn execution role with minimum required permissions — least privilege applies to IaC too.
Rollback on failure✅ Enable — default and correct. Disable only during initial template development to inspect failed resource state. Never disable in production.
Termination protection✅ Enable for production stacks. Prevents accidental delete-stack. Must be explicitly disabled before a stack can be deleted. The equivalent of a storage volume write-protect flag.
3
Monitor Stack Events During Deployment
WhereCloudFormation → Stacks → select stack → Events tab
What you seeReal-time event stream showing each resource's status: PENDING → IN_PROGRESS → COMPLETE (or FAILED). Events are timestamped and show the logical resource ID, physical resource ID (the actual AWS resource ID), and status reason for failures.
Reading eventsEvents are shown newest-first. Scroll to the bottom to see the starting point. The first FAILED event is the root cause — subsequent rollback events are consequences of that failure.
Visual cueStatus banner at top: green = CREATE_COMPLETE, yellow = IN_PROGRESS, red = ROLLBACK_COMPLETE. Resources tab shows every resource with its physical ID — this is where you find the actual ARN of created resources.
✅ Checkpoint A: Stack status = CREATE_COMPLETE. Resources tab shows all expected resources with physical IDs. Outputs tab shows any defined output values. All tags from stack creation are visible on each resource.

Part B: Change Sets — Preview Before Applying

4
Create a Change Set for a Template Update
WhereCloudFormation → Stacks → select stack → Stack actions → Create change set for current stack
What it doesUpload or specify the updated template. CFn compares it against the currently deployed template and calculates what changes would occur — without making any changes. Equivalent to terraform plan.
Reading the Change SetEach change shows: Logical ID (resource name in template), Action (Add/Modify/Remove), Replacement (whether the resource will be destroyed and recreated vs updated in place). Replacement: True = the resource will be deleted and recreated — for a production database, this means downtime. This is the critical field to review.
Replacement reasonsSome resource properties are immutable — changing them requires replacement. RDS: changing engine type. EC2: changing AMI. S3: changing bucket name (names are immutable). Replacement = brief or extended downtime depending on the resource.
Why this mattersChange Sets prevent the most common production CFn incident: updating a stack expecting an in-place modification, but actually triggering a replacement of a production database. Always create and review a Change Set before executing template updates against production stacks.
5
Execute the Change Set
ActionAfter reviewing the Change Set and confirming no unexpected replacements: Execute. The changes apply immediately. Monitor the Events tab as with a fresh deployment.
Stack Policy checkIf a Stack Policy exists protecting specific resources, a Change Set that tries to modify those resources will fail at execution — the Change Set itself may not show this restriction clearly. Check the Stack Policy before creating a Change Set if the stack is protected.

Part C: Drift Detection

6
Detect Stack Drift
WhereCloudFormation → Stacks → select stack → Stack actions → Detect drift
What happensCFn compares each resource's actual current configuration (retrieved via AWS APIs) against what the template says it should be. Takes 1–10 minutes depending on stack size.
ResultsStack Drift Status: IN_SYNC (no drift) or DRIFTED (at least one resource differs). Click "View drift results" → per-resource list showing MODIFIED or NOT_CHECKED. Click a MODIFIED resource → side-by-side diff of expected vs actual property values.
Common drift sourcesManual console changes (someone added an inbound SG rule), manual tag additions, a separate process modifying an IAM policy attached to a stack-created role. Drift doesn't cause immediate problems but erodes IaC control — over time, the template becomes increasingly inaccurate as the source of truth.
RemediationOption 1: Update the template to match the drift (importing the manual change into IaC). Option 2: Import the drifted resource back to template state via stack update. Option 3: Use CloudFormation import to bring manually created resources under stack management.
✅ Checkpoint C: Drift detection completed. Stack shows IN_SYNC or you've identified specific drifted resources and their property diffs. You can read the "Expected" vs "Actual" JSON comparison and understand what changed.

💼 Career Application

The Change Set review step is where architects earn their keep. In a client environment where an SRE is about to run aws cloudformation update-stack without reviewing a Change Set, catching a "Replacement: True" on a production RDS instance is the kind of intervention that prevents major incidents. Change Sets are a non-negotiable practice for any production CFn update — the 2-minute wait is worth avoiding an unplanned database recreation. In interviews: "How do you safely update a production CloudFormation stack?" The answer is: always create a Change Set, review the replacement column, confirm no unexpected replacements, then execute. That answer — with the reasoning — demonstrates operational maturity.

DeletionPolicy — The Most Critical CFn Property You'll Ever Review

DeletionPolicy ValueWhat Happens When Stack/Resource DeletedUse For
Delete (default)Resource is permanently deleted. For S3: bucket must be empty first. For RDS: all data gone.Non-persistent resources (SGs, route tables, IAM roles). Never for databases or S3 buckets with data.
RetainResource is removed from stack management but NOT deleted. Continues to exist and bill.S3 buckets with data. Resources you want to preserve after stack deletion. Orphaned resources need manual cleanup.
SnapshotTakes a final snapshot before deletion (RDS, ElastiCache, Redshift). Snapshot persists after stack deletion.All databases in production. The correct default for any stateful resource.
🚫 The Default DeletionPolicy Kills Databases

The default DeletionPolicy is Delete. For an RDS instance, this means: if someone deletes the stack (intentionally or accidentally), the database and all its data is permanently gone. No prompt, no confirmation beyond "delete the stack?" No recovery. Every RDS, ElastiCache, and Redshift resource in a production CFn template must explicitly set DeletionPolicy: Snapshot. If you're reviewing a client's CFn template and their production database doesn't have this property — that's a critical finding. This is the first thing to check in any template review. After that: UpdateReplacePolicy: Snapshot to protect against accidental replacement during updates.

CFn Template Review Checklist

When reviewing a client's CFn template, check in this order:

  1. DeletionPolicy on all databases and S3 buckets — Snapshot or Retain. Default = Delete = data loss risk.
  2. Hardcoded secrets — passwords, API keys, connection strings. Should use {{resolve:secretsmanager:...}} or SSM SecureString parameters. A plaintext password in a CFn template is stored in CloudFormation's history (visible in stack events) and S3.
  3. Overly permissive Security Groups — CidrIp: 0.0.0.0/0 on port 22 or 3389. Review every ingress rule.
  4. Encryption settings — StorageEncrypted: true on RDS, Encrypted: true on EBS volumes, SSE on S3.
  5. IAM roles with * in Action or Resource — signals over-permissioned role. Flag and request justification.
  6. Missing tags — are mandatory tags (Environment, Team) applied to all taggable resources?
  7. Termination protection — is it enabled at deploy time for production stacks?
  8. Public S3 buckets — PublicAccessBlockConfiguration set to all true unless explicitly justified.

09 / TROUBLESHOOTING

Troubleshooting & Failure Modes #

StackStack stuck in ROLLBACK_COMPLETE — can't update or delete▼

Cause: A stack in ROLLBACK_COMPLETE state failed during initial creation and rolled back. It exists but has no resources. It can only be deleted, not updated. Fix: Delete the stack (aws cloudformation delete-stack --stack-name NAME), fix the template, and redeploy. If the stack can't be deleted (resources were partially created and the rollback itself partially failed — "stuck in rollback"), use --retain-resources to delete the stack while retaining the problematic resources: aws cloudformation delete-stack --stack-name NAME --retain-resources Resource1 Resource2. Then manually clean up the retained resources.

IAM"Requires capabilities: CAPABILITY_IAM" error when deploying▼

Cause: The template creates IAM resources (roles, policies, instance profiles). CFn requires explicit acknowledgment that you understand IAM resources will be created — preventing accidental privilege escalation. Fix: Add --capabilities CAPABILITY_IAM to the CLI command. For templates creating IAM resources with custom names, also add CAPABILITY_NAMED_IAM. In the console: a checkbox appears on the final review page — "I acknowledge that AWS CloudFormation might create IAM resources with custom names." This is not a bug — it's a deliberate safety check. Review the IAM resources being created and ensure they follow least privilege before acknowledging.

Template"Template format error: YAML parse error" — no line number in error▼

Cause: YAML syntax error — most commonly: tab characters (YAML requires spaces), inconsistent indentation, or a special character that needs quoting (colons, brackets, ampersands in strings). AWS's validate-template API often doesn't give a useful line number. Fix: Run python3 -c "import yaml; yaml.safe_load(open('template.yaml'))" — Python's YAML parser gives better error messages with line numbers. Or use cfn-lint template.yaml — it catches parse errors with location. Or paste the template into an online YAML linter (yaml-online-parser.appspot.com). Fix from the first error upward — subsequent errors are often cascade effects of the first.

Export"Export with name X already exists" — can't create stack▼

Cause: Another stack in the same region already exports a value with the same name. CFn export names must be unique per region per account. Common when deploying multiple environments (prod and staging) from the same template without distinguishing the export names. Fix: Make export names environment-aware: !Sub "${AWS::StackName}-VpcId" uses the stack name as a prefix — different stack names produce different export names. Never use hardcoded export names without a stack-specific prefix. If the conflict is from a deleted stack that still has active exports: wait up to 30 minutes for CFn to clean up, or delete the exporting stack if it's no longer needed.

UpdateStack update fails with "No updates are to be performed"▼

Cause: Not actually an error — CFn is telling you the submitted template is identical to the currently deployed template (or the parameter values haven't changed). This is a common source of confusion in CI/CD pipelines where a template is submitted even when nothing changed. Fix: This is expected behaviour and often correct — no action needed. If you believe the template did change, compare the submitted template against the currently deployed template (aws cloudformation get-template --stack-name NAME) and diff them. In CI/CD: catch this exit code (255) separately from actual errors and treat it as a no-op success, not a pipeline failure.

StackSetStackSet update stuck — some instances failed, others succeeded▼

Cause: StackSets deploy with configurable failure tolerance (FailureToleranceCount or FailureTolerancePercentage). If failures exceed the tolerance, the StackSet operation stops. Successfully deployed instances keep their update; failed instances roll back. The StackSet is in a partially updated state. Fix: Check the StackSet operation status to see which accounts/regions failed and why. Correct the issue (often an IAM permission missing from the target account, or a service limit reached). Re-run the StackSet update — it will only update the failed instances, not re-deploy the successful ones. After resolution, run a drift detection to confirm all instances are in sync.

CFn Execution Role — Least Privilege for IaC

By default, CloudFormation inherits the permissions of the IAM principal that calls CreateStack/UpdateStack. This means an administrator deploying a stack has administrator-level CFn execution — the stack can create any resource. Better: specify a dedicated CFn execution role with only the permissions needed to deploy that specific stack. The deploying user needs iam:PassRole to the CFn execution role, plus cloudformation:*. The CFn role has only the permissions to create the specific resource types in the template.

Deployment Concurrency and Failure Tolerance

bash — StackSet update with controlled rollout
# Update a StackSet with controlled concurrency (don't blast all accounts simultaneously)
aws cloudformation update-stack-set \
  --stack-set-name baseline-security \
  --template-body file://baseline.yaml \
  --operation-preferences '{
    "RegionOrder": ["ap-southeast-1", "ap-southeast-3"],
    "MaxConcurrentPercentage": 20,    # Update 20% of accounts at a time
    "FailureTolerancePercentage": 10, # Allow up to 10% of accounts to fail
    "ConcurrencyMode": "SOFT_FAILURE_TOLERANCE"
  }'

# MaxConcurrentPercentage: 20 on 50 accounts = 10 accounts updated simultaneously
# If 5 of those 10 fail (10% of 50), operation stops — remaining accounts untouched
# This prevents a bad update from propagating to all accounts at once

# Deploy to a specific OU (service-managed StackSet)

🌉 Bridge from Storage/Virtualisation

StackSets with controlled concurrency ≈ a phased firmware upgrade across a storage array fleet. You don't upgrade all 200 arrays simultaneously — you upgrade 20% at a time (canary deployment), verify no issues, then proceed. If the first batch fails, you stop and investigate before the bad firmware reaches the rest of the fleet. StackSets' MaxConcurrentPercentage and FailureTolerancePercentage are exactly this pattern applied to infrastructure code deployment. The "regions in order" preference ≈ upgrading DR site first, validating, then upgrading primary site — conservative, methodical, recoverable.

CFn vs CDK vs Terraform — Patterns & Migration #

When Each Tool Is Right

📄

Use Raw CloudFormation When

Reviewing or maintaining existing client templates. Working within Service Catalog (products are CFn). Building minimal AWS-native deployments where Terraform isn't available. SAM templates for serverless. Control Tower customisations (must be CFn).

🏗️

Use CDK When

New greenfield work where the team knows a programming language. Complex conditional logic that's painful in YAML. Building reusable infrastructure constructs for internal platform use. L3 constructs (e.g., ApplicationLoadBalancedFargateService) that encode entire patterns in one call.

🔧

Use Terraform When

Multi-cloud infrastructure. Strong module ecosystem preference. Team already invested in Terraform. Fast plan feedback loop is important. External provider integrations (Datadog, PagerDuty, GitHub) alongside AWS resources.

🔄

CFn → Terraform: run both in parallel. Terraform manages new resources; CFn manages existing. Gradually move resources to Terraform via terraform import. Full migration is a multi-year project for large environments. Don't rush it.

19 / FAQ

Regular FAQ — Beginner Focused #

BeginnerDo I have to use CloudFormation if I'm using Terraform?▼

No — you can use Terraform exclusively for new infrastructure. However, you'll encounter CFn in client environments regardless of your preference. Some AWS services also generate CFn under the hood (Control Tower, Service Catalog, CDK) that you need to understand even if you don't write it. The goal of this guide is reading fluency — being able to understand and review CFn templates, not necessarily author them for every project.

BeginnerWhat happens if a stack deployment fails halfway through?▼

CloudFormation automatically rolls back by default — it deletes any resources that were successfully created before the failure, leaving the account in the same state as before the deployment. This is safe for initial deployments. For update deployments (updating an existing stack), rollback restores the previous configuration. The stack ends in ROLLBACK_COMPLETE (initial create failure) or UPDATE_ROLLBACK_COMPLETE (update failure) state. Read the Events tab to find the first FAILED event — that's the root cause. Fix it and redeploy.

BeginnerCan I delete individual resources from a stack without deleting the whole stack?▼

Not directly — you remove a resource from a stack by removing it from the template and updating the stack. When CFn sees a resource in the current stack that's not in the updated template, it deletes it. This is how resource removal works in IaC generally — you declare the desired final state and let the tool figure out what to delete. For removing a resource from CFn management without deleting it, use resource import/export: remove it from the template but set DeletionPolicy: Retain first — the resource stays alive but is no longer managed by the stack.

BeginnerWhat's the difference between Outputs and Parameters?▼

Parameters go IN to a stack at deploy time — they're the inputs (what environment? what instance size?). Outputs come OUT from a stack after deployment — they're the results (what's the VPC ID that was created? what's the ALB DNS name?). Other stacks consume Outputs via !ImportValue. Think of it like a function: Parameters = function arguments, Outputs = return values. A well-designed template uses Parameters for configuration and Outputs to expose resource identifiers that other stacks need.

BeginnerWhat does CAPABILITY_IAM mean and why do I need it?▼

CAPABILITY_IAM is an explicit acknowledgment that your template creates IAM resources (roles, policies, instance profiles). AWS requires this because IAM resources can escalate privileges — a template could create an admin role that didn't exist before. By requiring CAPABILITY_IAM, AWS forces you to consciously acknowledge "yes, I know this template creates IAM resources." Add it to your CLI command (--capabilities CAPABILITY_IAM) or check the console checkbox. For templates creating IAM resources with custom names, also add CAPABILITY_NAMED_IAM.

ArchitectHow do I safely update a resource property that requires replacement?▼

First, confirm replacement is actually required — create a Change Set and check Replacement = True. If replacement is unavoidable: (1) for databases, ensure DeletionPolicy: Snapshot and UpdateReplacePolicy: Snapshot are set — the replacement will create a snapshot before deleting the old instance. (2) Communicate the expected downtime (replacement of an RDS instance takes 5–20 minutes). (3) For zero-downtime requirements, consider blue-green deployment: deploy a new stack alongside the old one, migrate data, cut over traffic, then delete the old stack. This avoids in-place replacement entirely. Replacement via Change Set with a snapshot safety net is the standard approach for most non-critical databases.

20 / INTERVIEW Q&A

Principal Architect Interview Q&A #

Principal"A developer deleted a CloudFormation stack and lost the production database. How would you prevent this in future?"▼

Strong answer: "Three layers of protection, each addressing a different failure mode. First: DeletionPolicy: Snapshot on all RDS and stateful resources. If the stack delete proceeds, the database takes a final snapshot before deletion — data recoverable from the snapshot. This is the last line of defence and must be present regardless of other controls.

Second: stack termination protection enabled on all production stacks. A stack with termination protection cannot be deleted without first disabling the protection — an extra manual step that creates friction and forces intentionality. The developer would need to explicitly say 'I know I'm about to delete a production stack' before proceeding.

Third: IAM controls on who can delete production stacks. The developer's IAM role should not have cloudformation:DeleteStack permission on production stacks. This can be enforced via an SCP (Deny: cloudformation:DeleteStack on accounts tagged as production for any principal except the deployment pipeline role), or via IAM policy on the developer role. The combination: data is recoverable (DeletionPolicy), deletion is gated (termination protection), and most users can't delete at all (IAM). Defense in depth applied to IaC operations."

Principal"When would you choose CloudFormation over Terraform for a new project?"▼

Strong answer: "The honest answer is rarely for pure authoring preference — Terraform is generally more ergonomic to write and has a better plan experience. But there are specific scenarios where CFn is the right choice. When the project is tightly coupled to AWS-native tooling: Control Tower customisations must be CFn, Service Catalog products must be CFn, and anything that needs to work with StackSets across an Organization is most naturally expressed in CFn. When the team needs automatic rollback guarantee — Terraform's partial state on failure is a real operational burden that CFn's automatic rollback avoids. When there's no state file management capability — teams without an S3 backend and DynamoDB table set up, or without Terraform expertise, can deploy CFn immediately from the console without infrastructure for state management. And when AWS CDK is being adopted — CDK synthesises to CFn, so choosing CFn and CDK together gives you the authoring ergonomics of CDK with the deployment safety of CFn rollback. For multi-cloud or when the Terraform module ecosystem is central to the design, Terraform wins."

Principal"Describe how you would deploy a consistent security baseline across 50 AWS accounts using CloudFormation."▼

Strong answer: "StackSets with service-managed deployment, targeting the Workloads OU in Organizations. The template defines the baseline: GuardDuty detector enabled, Config recorder and delivery channel configured, CloudTrail enabled with log file validation and KMS encryption, S3 block public access at account level, and IAM password policy. Deploy to all current accounts with a 25% concurrency (12 accounts simultaneously) and 10% failure tolerance (5 accounts can fail before stopping). Future accounts automatically receive the StackSet on joining the OU — no manual action needed.

The StackSet is maintained in Git with cfn-lint in CI. Updates go through a Change Set review process. Drift detection runs weekly via a scheduled Lambda — any account that shows drift gets an SNS alert. Drift is addressed either by updating the StackSet (if the change should be permanent) or by re-applying the StackSet to the drifted account (if it was an unauthorized manual change). This gives you a repeatable, auditable, and automatically-enforced baseline across the entire organisation without per-account manual configuration."

Principal"What are Change Sets and when is it not safe to skip them?"▼

Strong answer: "A Change Set is CFn's preview mechanism — it shows what changes a template update would make to an existing stack before applying them. The key field to review is 'Replacement' — whether a resource will be updated in place (safe, non-disruptive) or replaced (deleted and recreated, potentially disruptive). Skipping Change Sets is acceptable in two scenarios only: initial stack creation (nothing to compare against) and deploying to a completely non-critical sandbox that you're happy to roll back from. For any production update, Change Sets are non-negotiable. The reason: some property changes that look innocuous in a template diff actually trigger replacement. Changing an RDS engine minor version, changing an EC2 subnet, changing an ALB's security group while certain conditions are met — these can all trigger replacement. Without a Change Set, you discover this only when CFn starts deleting your production database. The 2-minute wait for a Change Set is the cheapest possible insurance against an unplanned outage."

Principal"A client wants to migrate from CloudFormation to Terraform. How would you approach this?"▼

Strong answer: "Carefully and incrementally — never a big-bang migration. First, assess the scale: how many stacks, how many resources, how interconnected are cross-stack references. A 10-stack environment with 200 resources is migrateable in weeks; a 200-stack environment with 5,000 resources is a multi-year programme. For a phased migration: start with new resources in Terraform, leaving existing CFn stacks intact. Use terraform import to bring specific resources under Terraform management without recreating them. Break cross-stack reference dependencies by using SSM Parameter Store as the interface instead of CFn !ImportValue — both Terraform and CFn can read/write SSM. Run both tools in parallel indefinitely if needed — there's no requirement to complete the migration. For production stateful resources (RDS, ElastiCache): import them to Terraform state but don't recreate them. Take a snapshot first, import the resource, validate Terraform plan shows no changes, then manage via Terraform. The risk is highest at this step — test thoroughly in non-prod first. The honest advice: complete migration is rarely worth the risk and effort unless there's a strong business reason (multi-cloud, team preference, tooling standardisation). A mixed CFn/Terraform environment is entirely operable and often the right long-term state."

## ══ PARAMETERS → VARIABLES ══════════════════════════════════
# CFn:
# Parameters:
#   Environment:
#     Type: String
#     AllowedValues: [prod, staging, dev]
#     Default: dev

variable "environment" {
  type    = string
  default = "dev"
  validation {
    condition     = contains(["prod", "staging", "dev"], var.environment)
    error_message = "Must be prod, staging, or dev."
  }
}

## ══ CONDITIONS → LOCALS + TERNARY ════════════════════════════
# CFn:
# Conditions:
#   IsProd: !Equals [!Ref Environment, prod]
# Usage: !If [IsProd, db.r6g.xlarge, db.t3.medium]

locals {
  is_prod        = var.environment == "prod"
  db_instance    = local.is_prod ? "db.r6g.xlarge" : "db.t3.medium"
  multi_az       = local.is_prod
}

## ══ MAPPINGS → LOCALS MAP ════════════════════════════════════
# CFn:
# Mappings:
#   RegionAMI:
#     ap-southeast-1: { AMI: ami-0abc123 }
#     us-east-1: { AMI: ami-0def456 }
# Usage: !FindInMap [RegionAMI, !Ref AWS::Region, AMI]

locals {
  region_ami = {
    "ap-southeast-1" = "ami-0abc123"
    "us-east-1"      = "ami-0def456"
  }
  ami_id = local.region_ami[data.aws_region.current.name]
}

## ══ OUTPUTS + EXPORT → OUTPUTS + REMOTE STATE ════════════════
# CFn:
# Outputs:
#   VpcId:
#     Value: !Ref VPC
#     Export:
#       Name: !Sub "${AWS::StackName}-VpcId"
# Consumer: !ImportValue netrust-network-prod-VpcId

output "vpc_id" { value = aws_vpc.main.id }
# Consumer uses remote state data source:
data "terraform_remote_state" "network" {
  backend = "s3"
  config  = { bucket = "netrust-tfstate"; key = "network/terraform.tfstate"; region = "ap-southeast-1" }
}
# Usage: data.terraform_remote_state.network.outputs.vpc_id

## ══ DeletionPolicy → lifecycle.prevent_destroy ══════════════
# CFn: DeletionPolicy: Snapshot
# Terraform equivalent (partial — prevent_destroy prevents deletion but no auto-snapshot):
resource "aws_db_instance" "prod" {
  lifecycle {
    prevent_destroy = true   # Blocks terraform destroy — like termination protection
    # No auto-snapshot equivalent — use final_snapshot_identifier
  }
  final_snapshot_identifier = "prod-db-final-${formatdate("YYYY-MM-DD", timestamp())}"
  skip_final_snapshot       = false   # Equivalent to DeletionPolicy: Snapshot
}

# CFn: StackSet deploys same template to multiple accounts
# Terraform equivalent: provider aliases + for_each across account IDs
variable "target_accounts" { default = ["123456789012", "234567890123"] }
resource "aws_guardduty_detector" "all" {
  for_each  = toset(var.target_accounts)
  provider  = aws.accounts[each.key]   # Provider alias per account via AssumeRole
  enable    = true
}
