01 / CONCEPT

Concept & Mental Model #

Two Different Questions, Two Different Services

CloudTrail answers: "Who made what API call, when, from where?" It is the management-plane audit log. Every CreateBucket, AttachRolePolicy, DeleteTrail call is recorded with the principal identity, source IP, timestamp, and request parameters. CloudTrail is the forensic record of intent.

AWS Config answers: "What does this resource look like right now, what did it look like yesterday, and is it compliant with my policy?" Config records configuration state — not who changed something, but what the resource configuration is at every point in time. An S3 bucket's Config item tells you its versioning state, public access settings, tags, and policy — timestamped continuously.

They are complementary: Config tells you a Security Group was non-compliant (port 22 open to 0.0.0.0/0), CloudTrail tells you which engineer opened it, at what time, from which IP. Together they give the full forensic picture required for MAS TRM §12 audit evidence.

What Did Engineers Do Before?

Before CloudTrail (pre-2013), AWS had no centralised audit logging. Post-incident forensics meant cobbling together partial logs from different services with no cross-service timeline. Change management was entirely process-based — you could ask "did someone change this security group?" but had no technical way to answer it. Before Config (pre-2014), compliance was snapshot-based: run a script periodically, generate a report, act on violations. Between scans you were blind — no way to ask "was this instance ever non-compliant this month?"

Three Core Concepts

1. CloudTrail records API calls, not resource states. CloudTrail knows that someone called PutBucketPublicAccessBlock at 14:32 UTC. The resulting bucket configuration is Config's domain. You need both.

2. Config is regional; trails can be multi-region. Config must be enabled per-account per-region. An Org Trail is multi-region by default — it captures events in all regions from one configuration.

3. Config Rules are detective, not preventive. A rule flagging unencrypted EBS volumes fires after the volume is created — it does not prevent creation. For prevention use SCPs (Guide 05) or IAM. Config is your "what slipped through" safety net and compliance evidence generator.

🌉 Bridge from Storage/Virtualisation

CloudTrail ≈ vCenter audit log + ESXi syslog forwarded to a central server. Every admin action on every resource logged centrally. The Org Trail ≈ configuring all ESXi hosts to forward to one syslog server automatically — one destination, full coverage. Config ≈ your CMDB with automatic discovery and continuous change tracking. In a well-run DC, your CMDB shows each host's current config plus change history. Config does this automatically — every configuration change timestamped and versioned without agents or manual input. Config Rules ≈ compliance baselines in your vulnerability scanner, but they fire within minutes of a change — not weekly.

💡 Why This Matters — MAS TRM §12

MAS TRM §12 requires comprehensive audit trails of all system access and changes, tamper-evident storage, and minimum retention periods. §12.1 = log all privileged access and config changes (CloudTrail Org Trail). §12.2 = protect log integrity (CloudTrail log file validation + S3 Object Lock). §12.3 = monitor and alert (Config Rules + CloudWatch metric filter alarms). Build this correctly and audit evidence is a console screenshot. Build it wrong and you're generating manual spreadsheets the night before the audit.

⚠️ S3 Data Events Can Bankrupt Your CloudTrail Budget

Enabling S3 data events on all buckets in a multi-account Org generates billions of events per day at active scale. At $0.10/100k events a busy environment can cost $10,000–50,000/month. Enable selectively on specific buckets containing regulated data (PII, financial records) only. Use S3 Server Access Logs for general access logging at near-zero cost.

💡 CloudTrail is Not Real-Time Detection

Log files deliver to S3 within ~5 min. CloudWatch Logs delivery adds ~10 min. CloudTrail Lake has ~15 min latency. CloudTrail is a forensic tool, not a real-time alarm. For real-time threat detection use GuardDuty (Guide 38) — it processes CloudTrail events with near-real-time ML analysis. CloudTrail is your evidence trail; GuardDuty is your alarm system.

3.3 Canonical Patterns

Pattern 1: MAS TRM §12 Full Audit Stack

Org CloudTrail Trail → S3 (Log Archive, Object Lock) + CloudWatch Logs + CloudTrail Lake. Config recorder in every account/region → S3 + SNS. Config Aggregator in Audit account. 14 CIS CloudWatch metric filter alarms. Config Rules for encryption, public access, MFA, VPC Flow Logs. EventBridge on non-compliance → SNS → PagerDuty. This is the architecture every FSI engagement starts with on day one.

Pattern 2: Automated Remediation Pipeline

Config Rule detects non-compliance (e.g., S3 public access enabled) → EventBridge → SSM Automation → resource remediated (Block Public Access re-enabled) → Config re-evaluates → COMPLIANT. Satisfies both detective and corrective control requirements. Use cautiously: test in non-prod for 48 hours before enabling auto-remediation in production OUs.

Pattern 3: CloudTrail Lake Forensic Investigation

Security incident: "someone deleted our production DynamoDB table at 3am." CloudTrail Lake SQL query: filter by eventName='DeleteTable' in the time window. Result: IAM principal, source IP, session context, user agent — all in one query in seconds. No Athena partitioning, no S3 prefix navigation, no gzip decompression.

Pattern 4: Compliance Trend Reporting

EventBridge rule on Config compliance state changes → Lambda → DynamoDB → store daily compliance score per rule per account. Monthly compliance report Lambda queries DynamoDB → generates PDF → emails to compliance team. Automated MAS TRM §12 evidence package without human intervention.

🚫 Anti-Pattern: Disabling Config to Cut Costs

Config costs ~$3–8/account/month. Disabling it to save costs creates a MAS TRM §12 compliance gap, eliminates compliance history, and removes automated drift detection. The cost of a failed audit examination is orders of magnitude higher. If costs are a concern, scope the recorder to security-relevant resource types only (EC2, IAM, S3, RDS, SecurityGroup, CloudTrail) — this cuts CI volume by 60–70% while maintaining all compliance-critical coverage.

🤖 AI / Agentic Angle

CloudTrail Lake's SQL interface is a natural data source for AI-assisted security operations. A Bedrock-powered security agent can receive a GuardDuty finding, query CloudTrail Lake to gather context (what other API calls did this principal make in the last hour?), cross-reference Config items to understand the resource state at the time of the finding, then synthesise a natural-language incident summary with suggested remediation. Config's resource relationship graph can be fed as structured context to an LLM for blast-radius analysis: "this IAM role is attached to 7 Lambda functions — here are their names." Build the audit infrastructure correctly now; AI-assisted ops workflows will use it natively as LLM tooling matures.

04 / PREREQUISITES

Prerequisites & Environment Setup #

  • Guide 05 complete: AWS Organizations, OUs, Log Archive account with S3 Object Lock, Organizations trusted access for CloudTrail and Config enabled.
  • IAM permissions: cloudtrail:*, config:*, logs:*, s3:* on the relevant buckets. AdministratorAccess in the management account covers all.
  • KMS key: Create a CMK in ap-southeast-1 for CloudTrail/Config encryption before starting (Key usage: Encrypt/decrypt, key policy must allow cloudtrail.amazonaws.com).
  • SNS topic: audit-alerts in the management or Audit account with your email subscribed — receives Config and CloudTrail alarm notifications.
  • S3 bucket policy on Log Archive: Must permit CloudTrail and Config service principals to write. See the AWS documentation for the standard CloudTrail bucket policy template.
💰 Cost Warning — Know Before You Click
  • CloudTrail management events: First trail free. Additional trails: $2.00/100k events.
  • CloudTrail data events: $0.10/100k. Do not enable on all buckets. Target sensitive buckets only.
  • CloudTrail Insights: $0.35/100k management events analysed. ~$2–5/month small org.
  • Config CIs: $0.003 per CI. 10 accounts × ~1,500 CIs/month = ~$45/month.
  • Config rule evaluations: $0.001 per evaluation.
  • CloudTrail Lake: $0.005/GB ingested; $0.005/GB scanned per query.
  • Lab estimate: ~$5–15 for one day. Running one month: ~$25–50 across 3 accounts.
🌉 Bridge from Storage/Virtualisation

Setting up CloudTrail + Config ≈ deploying a syslog infrastructure and CMDB together. The S3 Log Archive ≈ your centralised syslog server with WORM storage. The Config recorder ≈ your CMDB discovery agent that runs continuously. The KMS encryption of logs ≈ encrypting syslog archives at rest — you need the decryption key to read them, and access to that key is itself logged (recursive audit trail). The CloudTrail→CloudWatch Logs delivery ≈ real-time syslog forwarding to your SIEM for alerting — the S3 delivery is your long-term archive, CloudWatch Logs is your live alert feed.

SQL — CloudTrail Lake: IAM changes last 24 hours
-- Replace EVENT_DATA_STORE_ARN with your Lake data store ARN
SELECT
    eventTime,
    eventName,
    json_extract_scalar(userIdentity, '$.arn')         AS principal,
    sourceIPAddress,
    awsRegion,
    recipientAccountId,
    errorCode
FROM EVENT_DATA_STORE_ARN
WHERE eventTime > DATE_ADD('hour', -24, NOW())
  AND eventSource = 'iam.amazonaws.com'
  AND eventName IN ('AttachRolePolicy','DetachRolePolicy','CreatePolicy','DeletePolicy',
                   'PutRolePolicy','DeleteRolePolicy','CreatePolicyVersion')
  AND errorCode IS NULL
ORDER BY eventTime DESC LIMIT 100

    sourceIPAddress, userAgent,
    json_extract_scalar(requestParameters, '$.bucketName') AS bucket

CloudTrail Delivery error: "NoSuchBucket" — logs not appearing in S3 ▼

Cause: The S3 bucket no longer exists, or the bucket policy was modified and removed the CloudTrail allow statement. Fix: Verify bucket: aws s3api head-bucket --bucket BUCKET. Check policy: aws s3api get-bucket-policy --bucket BUCKET. The policy must allow s3:PutObject for cloudtrail.amazonaws.com with the correct aws:SourceArn condition. Once fixed, CloudTrail resumes delivery automatically. Prevention: S3 Object Lock prevents bucket deletion. Config Rule s3-bucket-policy-not-configured detects policy changes.

CloudTrail CloudTrail Lake queries return no results from member accounts ▼

Cause: Organizations trusted access for CloudTrail not enabled, or the data store was created before trusted access was established. Fix: Verify: aws organizations list-aws-service-access-for-organization | grep cloudtrail. If absent: aws organizations enable-aws-service-access --service-principal cloudtrail.amazonaws.com. Wait 30–60 minutes for first member account events. Events are not backfilled — the Lake only receives new events after trusted access is enabled.

Config All rules show "Insufficient data" — no evaluations running ▼

Cause: (a) Config recorder not started, (b) delivery channel misconfigured, or (c) AWSServiceRoleForConfig service-linked role missing. Fix: Start recorder: aws configservice start-configuration-recorder --configuration-recorder-name default. Check delivery: aws configservice describe-delivery-channel-status. Verify service-linked role: aws iam get-role --role-name AWSServiceRoleForConfig. If missing, it's recreated automatically when you re-enable Config from the console. Rules show evaluations within 5–10 minutes of recorder becoming active.

Config Config Aggregator shows some accounts as "Authorisation pending" ▼

Cause: For Org-based aggregator: Organizations trusted access for Config not enabled. Fix: aws organizations enable-aws-service-access --service-principal config.amazonaws.com. For account-based aggregator: each target account must accept the authorisation request in Config → Aggregators → Authorisation. The aggregator management account ARN must match the pending authorisation.

CloudTrail CloudWatch metric filter alarms not firing on real events ▼

Cause: CloudTrail CloudWatch Logs delivery requires an IAM role that CloudTrail can assume. If the role's trust policy doesn't allow cloudtrail.amazonaws.com, or the permission policy lacks logs:PutLogEvents on the specific log group ARN, delivery silently fails. Fix: Check role: aws cloudtrail describe-trails --query 'trailList[*].CloudWatchLogsRoleArn'. Verify the role's trust policy and permission policy. CloudTrail is specific about the log group ARN in the permission — it cannot be *. After fixing, trigger a test event and check the log group for new entries within 15 minutes.

CloudTrail validate-logs reports "INVALID" — potential tampering ▼

Most common cause (not tampering): Log files were moved, renamed, or recompressed after delivery. The digest records the exact S3 key and ETag. Any post-delivery object operation breaks validation even if content is intact. Actual tampering: Someone with S3 write access modified log file content. Investigation: Check S3 access logs for the log file. Check CloudTrail for s3:PutObject on the log key in the Log Archive bucket. If reorganisation: document it. If modification: treat as a security incident — escalate to CISO immediately.

Config Automated remediation breaking production applications ▼

Cause: Auto-remediation fired on a resource that was intentionally "non-compliant" for a valid reason (e.g., an internet-facing ALB SG open on 443 triggering the unrestricted traffic rule). Fix: Immediately switch to Manual: Config → Rules → rule → Remediation → Edit → Manual. Investigate the false positive. Add scope exclusions (resource tags or specific resource IDs) to the rule. Re-test in sandbox. Prevention: Always test automatic remediation in Sandbox OU for 48 hours before enabling in Prod OU. Never enable auto-remediation on a new rule without a dry-run period.

14 / SECURITY

Security Hardening Deep Dive #

Audit Infrastructure Attack Surface

CloudTrail and Config are primary attacker targets because disabling them is a standard technique (MITRE ATT&CK T1562.001 — Disable or Modify Tools). An attacker who compromises a privileged account will try to stop logging before their exfiltration. Your defences must make this either impossible (SCP) or immediately detectable (CloudWatch alarm) — preferably both.

🔒

SCP Protection (Guide 05)

Deny: cloudtrail:StopLogging, DeleteTrail, config:StopConfigurationRecorder at Root. Even a compromised admin in a member account cannot stop logging.

🚨

Immediate Alert on Tampering

CloudWatch alarm on CloudTrailChanges fires within 5 minutes. PagerDuty P1. Do not rely on daily log review to catch this.

🗄️

WORM Log Storage

S3 Object Lock (GOVERNANCE) on Log Archive bucket. Even root cannot delete logs during the retention period. COMPLIANCE mode is stricter.

🔑

CMK Encryption + Access Logging

Every CloudTrail log read generates a KMS event. Attacker reads logs → creates its own evidence. CMK protects against S3 data exfiltration — logs are useless without the key.

✅

Log File Integrity Validation

SHA-256 digests alongside logs. Run validate-logs before relying on log evidence. INVALID digest during incident = potential evidence tampering.

🏛️

Separate Log Archive Account

Logs land in a separate account (Guide 05 pattern). Compromising a workload account gives no access to Log Archive. SCPs on Log Archive deny log deletion.

19 / FAQ

Regular FAQ — Beginner Focused #

BeginnerIs CloudTrail always on by default?▼

Every new AWS account has a free 90-day rolling view of management events in the Event history console — but this isn't a persistent trail and doesn't write to S3. Events older than 90 days are gone. To have permanent, searchable audit logs you must create a trail explicitly. For any production or regulated environment, create the trail on day one. The Org Trail from Guide 05's Organizations setup is the right starting point — one trail, full coverage.

BeginnerWhat's the difference between CloudTrail and CloudTrail Lake?▼

CloudTrail (the trail) delivers log files as JSON.gz archives to S3. To query them you need Athena + Glue catalog setup or manual S3 navigation and gunzip. CloudTrail Lake is a managed data lake that ingests the same events and lets you query them with SQL directly in the browser — no S3 navigation, no partitioning, no decompression. Think of the trail as your tape backup (reliable, cheap long-term) and CloudTrail Lake as your online database (fast queries, more expensive). Most organisations run both: trail for long-term compliance evidence, Lake for forensic investigation.

BeginnerDoes Config record everything automatically once enabled?▼

Once the Configuration Recorder is started, yes — Config automatically discovers and records all supported resource types without agents or manual configuration. New resource types added by AWS are automatically included when you've selected "all supported resources." Config discovers via periodic sweeps (every 6 hours) and event-triggered recording (within ~3 minutes of a change). One catch: Config only records resources in the region where the recorder is enabled. You need a recorder in each governed region, or specifically enable global resource recording in one designated region for IAM, CloudFront, etc.

BeginnerCan CloudTrail help me recover deleted resources?▼

CloudTrail records the delete API call but doesn't contain the resource data itself — it tells you that DeleteBucket was called, not what was in the bucket. For data recovery you need AWS Backup or manual snapshots. Config resource history shows the last recorded configuration of the resource (what the resource looked like), but not the data it contained. CloudTrail + Config together answer "what was deleted, who deleted it, when, and what did it look like before" — actual data recovery requires separate backup tooling (Guide 53).

BeginnerDo I need both the Org Trail AND CloudTrail Lake? Isn't that double cost?▼

They serve different purposes with different cost profiles. The Org Trail's S3 delivery is near-free (just S3 storage cost) and is your long-term compliance evidence store. CloudTrail Lake adds ~$5/month for a small org but makes forensic investigation dramatically faster — SQL in a browser vs writing Athena queries and navigating S3 key prefixes. For a 10-account org, the $5/month Lake cost is worth hours saved during any incident investigation. At 100+ accounts, re-evaluate based on ingest volume. The Trail remains cheap at any scale; the Lake scales with event volume.

ArchitectHow do Config Rules work across multiple accounts — do I define rules in every account?▼

You have two options. Option 1: deploy Config Rules independently in each account via CloudFormation StackSets — the Config Aggregator then collects compliance results from all accounts into one view. Option 2: deploy a Conformance Pack from the management or delegated-admin account to all member accounts simultaneously via Organizations. This is the recommended approach at scale: one conformance pack definition, deployed to 50 accounts in one API call, compliance data aggregated into one view. New accounts added to the Org automatically receive the conformance pack deployment.

Principal"How would you prove to a MAS TRM auditor that your AWS environment has been compliant for the last 12 months?"▼

First, CloudTrail integrity evidence: run aws cloudtrail validate-logs for the full 12-month period — output shows all log files valid, no tampering detected. The logs are in the Log Archive account with S3 Object Lock — I show the bucket configuration and the unbroken SHA-256 digest chain. This satisfies MAS TRM §12.2.

Second, Config compliance history: I export the Config compliance state change events from EventBridge to a time-series store and generate a weekly compliance score report for all 20 accounts over 12 months. This is the difference between a mature governance program and a spreadsheet."

Principal"What's the difference between using CloudTrail for detection versus GuardDuty? When would you rely on each?"▼

Strong answer: "CloudTrail is a forensic record — it captures every API call faithfully and durably, but it's not a detection service. CloudWatch metric filter alarms built on top of CloudTrail are rule-based and fire on specific known patterns — they won't catch novel attack techniques.

GuardDuty is a managed ML-based detection service that processes CloudTrail events, VPC Flow Logs, and DNS logs in parallel. It detects anomalies, known-bad IPs, credential compromise patterns, and lateral movement that no static rule set would catch. GuardDuty findings appear within minutes; CloudTrail log files arrive within 5–15 minutes.

In practice they're complementary: CloudTrail metric filter alarms are my known-bad detectors (root login, CloudTrail modified, specific dangerous API calls). GuardDuty is my unknown-bad detector. After GuardDuty fires, I use CloudTrail Lake to reconstruct the full picture. GuardDuty triggers the investigation; CloudTrail is the evidence trail. Running only one leaves a gap — GuardDuty without CloudTrail gives you an alarm but no forensic record; CloudTrail without GuardDuty gives you complete evidence but slow detection."

Principal"A customer says Config is too expensive and wants to disable it. How do you respond?"▼

Strong answer: "First I'd quantify: Config costs $3–8/account/month for a well-scoped recorder. For a 20-account FSI environment, that's $60–160/month — negligible against total AWS spend and the cost of a MAS TRM compliance gap finding.

Then I'd fix the root cause of high cost, which is usually global resource recording enabled in every region. IAM is global — recording it in all regions creates duplicate CIs. Disable global resource recording in all regions except one — this cuts Config costs 30–50% without losing any compliance coverage. If cost remains a concern, scope the recorder to security-relevant resource types only: EC2, IAM, S3, RDS, SecurityGroup, CloudTrail. This reduces CI volume 60–70% while covering all MAS TRM §7 and §12 requirements.

What I'd never accept is disabling Config in production or regulated accounts. The absence of a continuous compliance record is a material MAS TRM finding. The conversation is 'let's optimise Config cost' not 'let's disable Config.'"

Principal"How would you investigate a suspected data exfiltration using AWS native tools only?"▼

Strong answer: "Three phases. First, triage: GuardDuty gives me the initial signal — compromised credential or unusual API activity. Note the IAM principal, time window, and affected resources from the GuardDuty finding JSON.

Second, reconstruct the attack chain using CloudTrail Lake. Query for all API calls by the flagged principal in the 48-hour window: what did they do, in which accounts, from which IPs? Data-access actions to focus on: S3 GetObject, RDS queries, Secrets Manager GetSecretValue. Cross-account role assumptions indicate lateral movement. The Lake query returns the complete timeline in under a minute.

Third, assess data exposure using Config. Which S3 buckets were accessed? Config resource history shows the bucket's access policy at the time of the incident — was it already misconfigured, or did the attacker modify it? Config's evaluation timeline shows whether the bucket was compliant or non-compliant during the incident window. Finally, run aws cloudtrail validate-logs to confirm log integrity before relying on the evidence in court or for regulatory notification."

Principal"Should the Config Aggregator be in the management account or the Audit account?"▼

Strong answer: "The Audit account, using the delegated administrator pattern. The reason is the same as every Guide 05 governance decision: the management account should run governance services only and be touched by as few people as possible. The Config Aggregator is an operational security tool — security engineers query it daily to check compliance status, investigate incidents, and generate reports. Running it in the management account means those engineers need access to the management account, increasing its blast radius.

The implementation: in the management account, designate the Audit account as Config delegated administrator (aws organizations register-delegated-administrator --service-principal config.amazonaws.com). Create the Aggregator in the Audit account. Security engineers do all compliance work from Audit — never from management. The same principle applies to Security Hub, GuardDuty, and IAM Access Analyser. Management account = governance operations only: creating accounts, modifying SCPs, billing."

Key Terraform Patterns for This Module

for_each on CIS alarms: Using a locals map for metric filter + alarm pairs keeps the code DRY — add a new alarm by adding one entry to the map. This pattern is in the config_hardening.tf Rosetta Stone from Section 07.

Config provider aliases: The Config Aggregator should run in the Audit account (delegated admin). Use a provider alias aws.audit with assume_role for the Audit account's OrganizationAccountAccessRole. This is the same multi-account provider pattern from Guide 05.

Data events as variables: Expose a variable sensitive_s3_buckets = [] that takes a list of bucket ARNs. The module creates data event selectors only for those buckets. This prevents accidental all-bucket data events when the module is reused across environments.

depends_on chain for Config: Config requires a strict creation order: recorder → delivery channel → recorder status. Break this chain and Terraform will create the status resource before the delivery channel exists, causing an error. Always maintain the depends_on chain.

SAP-C02 High-Frequency Topics from This Guide

🎯 Exam Focus Areas
  • CloudTrail trail types: Management vs data events, Org Trail vs account trail, single-region vs multi-region — exam loves "which trail captures X?"
  • Log file validation: What it does (SHA-256 digest), what it proves (tamper-evidence after delivery), what it doesn't prove (real-time)

  • Cost optimisation: Exclude KMS events, disable global resource recording in extra regions, scope data events to sensitive buckets — these are favourite exam scenarios.
