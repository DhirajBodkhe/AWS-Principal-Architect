01 / CONCEPT

Concept & Mental Model

#

What Problem Does Transit Gateway Solve?

Before TGW, connecting multiple VPCs in AWS meant creating a VPC peering mesh — a direct, non-transitive connection between each pair of VPCs. If you had 10 VPCs, you needed up to 45 peering connections (n×(n-1)/2). Each peering relationship required manual route table updates on both sides. When you added VPC #11, you added 10 more peering connections and 20 more route table entries. This was manageable at small scale and a maintenance nightmare at enterprise scale — the exact scenario every FSI (Financial Services Institution) running multi-account AWS environments faces.

On top of the mesh problem: each VPC had its own VPN connection to on-premises, meaning 10 VPCs required 10 separate VPN tunnels to your data center. Customer gateways needed to handle 10x the sessions. Direct Connect required 10x the virtual interfaces. Monitoring was fragmented across all connections.

TGW solves this with a hub-and-spoke model: one TGW sits at the center, all VPCs attach to it as spokes, and all on-premises connectivity (VPN, Direct Connect) attaches to the TGW. The number of connections scales linearly (one per VPC) instead of polynomially (n²).

💡 Why This Matters
The VPC mesh problem is exactly why large enterprises stall on AWS. A Netrust-scale FSI deployment with separate accounts for prod, dev, staging, shared services, security, and backup quickly hits the peering complexity wall. TGW is not optional at that scale — it's the prerequisite for everything else. Guide 01's 3-AZ VPC is now one spoke on a TGW you're about to build.

What Did Engineers Do Before TGW?

The pre-TGW era (pre-2018) had three messy options: VPC peering meshes (non-scalable), software VPN appliances in a hub VPC (single point of failure, EC2 instance cost, bandwidth capped by instance size), or Direct Connect to every VPC separately (expensive, operationally complex). AWS partners built "transit VPC" patterns using EC2-based routers (Cisco CSR 1000V, Juniper vSRX) as software hubs — paying EC2 compute costs for what is now a managed service. TGW replaced all of these in November 2018, and the software transit VPC pattern is now effectively obsolete.

The 3 Core Concepts to Internalize Before Touching the Console

1. Attachments Are Logical Ports

A TGW attachment is how a resource (VPC, VPN, DXGW, another TGW) connects to the TGW. Each attachment occupies one or more ENIs in your VPC (one per AZ for VPC attachments). The TGW itself has no IP addresses — it operates at the routing layer, not the interface layer. Think of attachments as switch ports being plugged into your core switch.

2. Route Tables Control Who Talks to Whom

A TGW can have multiple route tables. Each attachment is associated with exactly one route table (which determines what routes it can see) and propagates its routes into one or more route tables (which determines who can reach it). This is the mechanism for route domain isolation: Prod VPCs associated with the Prod route table, Dev VPCs associated with the Dev route table, with no cross-domain routes unless explicitly added. This is the most nuanced part of TGW design — most architects get this wrong initially.

3. Transitive Routing Is Opt-In, Not Default

VPC peering is deliberately non-transitive — traffic cannot hop through a peer. TGW makes transitive routing possible, but only for traffic that the route tables explicitly allow. If VPC-A is attached to TGW and VPC-B is attached to TGW, they can communicate only if both VPCs propagate routes into a shared route table (or you add static routes). TGW does not auto-allow all-to-all — you must configure it. This is good: it means you have explicit control over who can reach what.

ℹ️ Common Misconception
TGW is NOT a firewall. It routes — it does not inspect packets. The Inspection VPC pattern (Section 17) uses TGW to force traffic through a third-party firewall appliance, but TGW itself only drops traffic via blackhole routes or missing route table entries. If you need stateful inspection, TGW is the routing fabric; AWS Network Firewall or Palo Alto is the inspection engine.

Real-World Analogy: The Airport Hub Model

Think of TGW as a major hub airport (Changi, JFK, Heathrow). Each VPC is a city with its own local airport (spoke). Flights between spoke cities always transit through the hub — there are no direct routes between most spokes. The gate assignments (route tables) determine which cities each terminal handles: Terminal 1 (Prod) handles destinations A, B, C; Terminal 2 (Dev) handles D, E, F. A passenger (packet) from city A wanting to reach city D must transit the hub, but the gate agent (route table) won't let Terminal 1 passengers board a Terminal 2 gate — unless you've explicitly added a cross-terminal route. On-premises networks are the international terminal — a separate wing connected to all terminals via a single international arrivals hall (DXGW/VPN).

🌉 Bridge from Storage/Virtualization
TGW is your core network fabric, not your storage fabric — but the mental model maps cleanly. In your VMware world: TGW ≈ a distributed vSwitch at data center scale, where port groups = TGW route tables (logical segmentation), VMs/hosts = spoke VPCs (attached workloads), and uplinks = TGW attachments. Route domains ≈ VLANs — isolated L2/L3 domains that don't see each other's traffic by default. The key difference: in vSphere you manage a switch; in AWS, TGW is a managed service — AWS handles the underlying routing hardware, redundancy, and scaling. You only manage the logical configuration.
💡 Why This Matters
Getting the mental model right before clicking is worth 30 minutes of your time. Architects who misunderstand TGW route table association vs. propagation spend hours debugging "why can't VPC-A reach VPC-B when they're both attached to the same TGW?" The answer is always route table configuration, not TGW itself. Build the mental model now; the Console steps in Section 05 will make immediate sense.

💡 Why This Matters — Association vs. Propagation
This is the most-confused concept in TGW design. Association answers: "which route table does this attachment USE to forward traffic?" (1:1). Propagation answers: "which route tables LEARN this attachment's CIDRs?" (1:many). An Inspection VPC attachment might be associated with the Inspection route table (it uses those routes for forwarding) but propagate its CIDR into the Prod route table (so Prod VPCs know how to reach the Inspection VPC). You configure each independently.

3.3 Canonical Patterns & Pairings

Pattern 1: Hub-Spoke with Route Domain Isolation

Description: Prod VPCs, Dev VPCs, and Shared Services VPC each in separate TGW route tables. Prod ↔ Shared is allowed; Prod ↔ Dev is blocked by missing routes. On-premises traffic flows to all domains via separate route table entries.

When to use: Default starting pattern for any multi-account AWS environment. Required for FSI environments where MAS TRM mandates network segmentation between production and non-production.

Services involved: TGW + multiple VPCs + RAM (if multi-account) + CloudTrail for audit

Pattern 2: Inspection VPC (East-West Traffic Inspection)

Description: All spoke-to-spoke traffic is hairpinned through a Inspection VPC running AWS Network Firewall or a 3rd-party NGFW. Spoke VPCs have default route (0.0.0.0/0) pointing to TGW; TGW routes to Inspection VPC; Inspection VPC firewall inspects and forwards; return traffic hairpins back. Requires Appliance Mode on Inspection VPC attachment to prevent asymmetric routing.

When to use: When MAS TRM §11.2 or internal security policy mandates east-west inspection between VPCs. Standard for financial services "zero trust" network architectures.

Services involved: TGW + Inspection VPC + AWS NFW or Palo Alto/Fortinet + Appliance Mode + specific TGW route table design

Pattern 3: Centralised Egress (Internet via Shared VPC)

Description: Only the Shared Services (or Egress) VPC has an Internet Gateway and NAT Gateways. All spoke VPCs route their default route through TGW → Egress VPC → NAT GW → Internet. No spoke VPC has its own IGW or NAT GW. This centralizes internet cost and egress inspection.

When to use: When you want centralized internet egress control, reduced NAT Gateway costs (one NAT GW fleet vs. one per VPC), and a single egress point for security monitoring.

Services involved: TGW + Egress VPC (NAT GW + IGW) + spoke VPCs (no IGW/NAT) + VPC Flow Logs on egress VPC

⚠️ Cost Trap
Centralised egress through TGW introduces additional TGW data processing charges ($0.02/GB) on top of NAT Gateway costs. For high-egress workloads, this can be more expensive than per-VPC NAT Gateways. Always model the cost. Small accounts: centralised egress wins. High-throughput accounts: run the numbers first.

Pattern 4: Multi-Region Active-Active via TGW Peering

Description: TGW in ap-southeast-1 (Singapore primary) peers with TGW in ap-northeast-1 (Tokyo DR). Route tables in each region have static routes pointing cross-region traffic to the peering attachment. Applications in each region can reach the other region's resources directly via the AWS backbone.

When to use: Active-active or warm-standby DR designs. MAS TRM §14 BCM requirements. Note: no BGP across TGW peering — you must add static routes manually on both ends.

Services involved: Two regional TGWs + peering attachment + Route 53 health checks + static routes in both TGW route tables

Pattern 5: Centralised VPC Endpoints (PrivateLink Hub)

Description: All Interface VPC Endpoints (S3, STS, ECR, Secrets Manager, SSM, Bedrock, etc.) live in the Shared Services VPC. Spoke VPCs access them via TGW routing to the Shared VPC. Eliminates the need to deploy endpoints in every VPC — significant cost saving at scale ($0.01/hr per endpoint per AZ).

When to use: Any environment with 5+ VPCs and heavy AWS service usage. A Bedrock endpoint in every VPC at $0.01×3 AZ×$730 hr/month = $21.90/month per VPC — at 20 VPCs that's $438/month just for one endpoint type. Central hub: $21.90 total.

Services involved: TGW + Shared Services VPC + Interface Endpoints + Private DNS resolution (requires Route 53 Resolver rules propagated to all spoke VPCs)

Anti-Pattern: Using TGW for Simple 2-VPC Connectivity

Description: Using TGW to connect two VPCs when VPC peering would suffice. TGW costs $0.05/attachment-hour × 2 VPCs = $73.20/month in attachment fees alone, before data processing charges. VPC peering is free for intra-region connections.

When NOT to use TGW: Fewer than 3-5 VPCs, no on-premises connectivity, no future growth expected. VPC peering is cheaper and simpler for small environments. Use TGW when you need the hub-spoke scale, multi-account sharing, or on-premises integration.

💡 Pro Tip — Honest TGW Weakness Assessment
TGW has genuine design warts worth knowing: (1) No BGP across TGW peering — inter-region routing is static-routes-only, which means no automatic failover; you must use Route 53 health checks + EventBridge automation for route failover. (2) 50 Gbps ceiling per peering attachment — if you're moving petabytes cross-region (e.g., analytics workloads), this is a hard ceiling AWS cannot raise. (3) RAM sharing complexity — sharing a TGW across accounts requires careful orchestration of who can see what; the attachment workflow from spoke accounts is not intuitive. (4) No native FQDN-based routing — TGW routes by CIDR only; domain-based filtering requires the Inspection VPC pattern with AWS NFW or a 3rd-party NGFW.

Insecure Defaults — What AWS Ships and Why It's Risky

🔴 Insecure Default #1 — Default Route Table Association Enabled
AWS defaults TGW to automatically associating all new attachments with the default route table. This creates a flat network where every VPC can potentially reach every other VPC. For an FSI with prod/dev isolation requirements, this is an immediate compliance failure. Disable it before attaching any VPCs. You cannot apply this retrospectively to existing attachments — you'd need to move them manually.
⚠️ Insecure Default #2 — No TGW Flow Logs
TGW Flow Logs are not enabled by default. AWS makes you opt in. In a MAS TRM environment, TGW is a critical network choke point — every flow between VPCs traverses it. Not logging here is a significant visibility gap. Enable Flow Logs in the same step as TGW creation, not as an afterthought.

Troubleshooting & Failure Modes

#

Debug Runbook — First 5 Steps When TGW Traffic Breaks

🔍 Debug Runbook
Step 1: Run VPC Reachability Analyzer — gives you the exact failure point without guessing.
Step 2: Check VPC route tables on the SOURCE VPC — does it have a route to TGW for the destination CIDR?
Step 3: Check TGW route table associations — is the source attachment associated with a route table that has the destination CIDR?
Step 4: Check TGW route table propagations — is the destination CIDR propagated into the source's route table?
Step 5: Check Security Groups and NACLs on destination instance — TGW routing can be perfect but SG/NACL blocks the traffic at the last hop.

Top 10 Real-World TGW Errors

Error 1 — "VPC attachment stuck in pending"
Symptom: VPC attachment state stays pending for more than 5 minutes.
Root cause: Most commonly, the TGW subnet in the VPC has a NACL blocking inbound traffic, or the subnet is in a different availability zone than the TGW expects. Less commonly: service quota hit on number of attachments.
Fix: Check NACL on the TGW subnet (allow all inbound/outbound temporarily to test). Check Service Quotas → EC2 → Transit Gateway attachments per transit gateway. Check CloudTrail for CreateTransitGatewayVpcAttachment errors.
Prevention: Use dedicated TGW subnets with permissive NACLs (SG-level security is sufficient for TGW subnets). Monitor Service Quotas proactively.
Error 2 — "Traffic drops between VPCs — routes look correct"
Symptom: Ping/TCP fails between two VPCs. TGW route tables show correct propagated routes.
Root cause: VPC route table on source VPC not updated to point traffic at TGW. The TGW knows the route; the VPC doesn't know to use the TGW.
Fix: Add route 10.0.0.0/8 → Transit Gateway in the private subnet route tables of both VPCs.
Prevention: Checklist: TGW route table ✓ AND VPC route table ✓. Both required.
Error 3 — "Asymmetric routing breaks firewall / NAT"
Symptom: Traffic through an Inspection VPC is intermittently dropped. Firewall logs show half of TCP flows with no matching session. One AZ works; another doesn't.
Root cause: Appliance Mode not enabled on the Inspection VPC attachment. TGW is load-balancing across AZ ENIs based on 5-tuple hash — SYN goes through AZ-1a ENI, SYN-ACK returns through AZ-1b ENI. Stateful firewall sees SYN-ACK without a SYN — drops it.
Fix: Enable Appliance Mode on the Inspection VPC attachment: VPC → Transit gateway attachments → select Inspection attachment → Actions → Modify → Enable Appliance mode support.
Prevention: Always enable Appliance Mode on any TGW attachment that connects to a stateful inspection appliance. Without exception.
Error 4 — "RAM-shared TGW attachment fails from spoke account"
Symptom: Spoke account engineer cannot see the shared TGW when creating a VPC attachment, or gets "You are not authorized" error.
Root cause: RAM sharing requires Organization-wide RAM sharing to be enabled in the management account. Or: the RAM resource share was created but the spoke account hasn't accepted the invitation (if not using auto-accept for Org members).
Fix: In management account: AWS Organizations → Services → RAM → enable sharing. Or: RAM → Resource shares → check invite status for spoke account. AWS Orgs members with auto-accept don't need manual acceptance.
Prevention: Enable Org-wide RAM sharing before any multi-account TGW design. It's a one-time setup with no cost.
Error 5 — "BGP session not establishing on VPN attachment"
Symptom: VPN tunnel shows UP but BGP state is ACTIVE or IDLE (not ESTABLISHED). No routes propagated from on-premises.
Root cause: ASN mismatch (TGW ASN matches on-premises ASN — eBGP requires different ASNs), incorrect BGP timer configuration, MD5 password mismatch, or firewall blocking TCP port 179 on the on-premises side.
Fix: Download the VPN configuration file from Console — it shows the correct BGP settings for common router platforms. Verify ASNs differ. Check on-premises router for TCP 179 ACLs. Verify MD5 password matches on both ends.
Prevention: Set TGW ASN to a private ASN clearly different from on-premises ASN at creation time. Document both ASNs.
Error 6 — "ECMP not load-balancing across VPN tunnels"
Symptom: Two VPN connections to TGW, but all traffic goes through one tunnel. Bandwidth doesn't aggregate.
Root cause: VPN ECMP support was not enabled on the TGW at creation time. Or: both tunnels are not advertising identical BGP prefixes at identical local-pref/MED — ECMP requires equal-cost paths (same prefix, same BGP attributes).
Fix: If ECMP was not enabled at TGW creation, you must create a new TGW (it cannot be changed). Verify BGP: on-premises should advertise same prefix from both tunnels with identical attributes.
Prevention: Always enable VPN ECMP support at TGW creation. Even if you don't need it today, you will.
Error 7 — "TGW peering routes not working cross-region"
Symptom: TGW peering attachment is active between ap-southeast-1 and ap-northeast-1, but cross-region traffic drops.
Root cause: TGW peering does NOT support BGP — routes across peering must be added as static routes manually. Most engineers forget this.
Fix: In ap-southeast-1 TGW route table, add static route: Tokyo VPC CIDRs → peering attachment. In ap-northeast-1 TGW route table, add static route: Singapore VPC CIDRs → peering attachment. Both sides must have static routes.
Prevention: Document that peering = static routes only. Add cross-region routes as part of the peering setup checklist.
Error 8 — "Centralised VPC Endpoints not resolving from spoke VPCs"
Symptom: Spoke VPC EC2 instances cannot reach S3, SSM, ECR etc. via the central VPC Endpoints in Shared Services VPC. DNS resolves to public IP instead of private IP.
Root cause: Route 53 Resolver forwarding rules not deployed to spoke VPCs. Private DNS on the endpoint not propagated. Or: the Shared Services VPC endpoint doesn't have the right Security Group allowing traffic from spoke VPC CIDRs.
Fix: Create Resolver outbound endpoint + forwarding rules in Shared Services VPC. Share rules via RAM to spoke accounts. In each spoke VPC, associate the forwarding rule. Check endpoint SG allows TCP 443 from all spoke VPC CIDRs.
Prevention: Deploy centralised VPC Endpoints as a complete pattern (endpoints + Resolver rules + RAM share + association) — not incrementally.
Error 9 — The Weird One: IAM Propagation Delay After RAM Share
Symptom: Spoke account engineer can see the shared TGW in the Console but gets an error when creating an attachment: "Transit gateway tgw-xxx does not exist"
Root cause: IAM and RAM share state have propagated to the spoke account, but the TGW resource itself hasn't fully propagated in the spoke account's regional endpoint yet. This is eventual consistency — AWS typically propagates within 60 seconds but occasionally takes up to 5 minutes.
Fix: Wait 2–5 minutes and retry. Not a configuration error. If it persists beyond 10 minutes, verify RAM share status in both accounts.
Prevention: Build a wait step into IaC deployment pipelines after RAM share creation — add a time_sleep resource in Terraform for 120 seconds.
Error 10 — The Weird One: TGW Flow Logs Show Duplicate Entries
Symptom: TGW Flow Logs show the same flow appearing twice for traffic between two VPCs — inflating your flow log volume and storage costs.
Root cause: Both TGW-level flow logs AND VPC-level flow logs are enabled. TGW logs see traffic at the attachment level (ingress and egress of the TGW). VPC flow logs see the same traffic at the ENI level. If you enable both TGW Flow Logs AND VPC Flow Logs for spoke VPCs, every TGW-transiting flow appears in both log streams.
Fix: Decide on a single flow log strategy. For MAS TRM compliance, TGW Flow Logs cover inter-VPC and VPC-to-on-premises flows. VPC Flow Logs cover intra-VPC east-west traffic. Run both only for VPCs where you need both visibility planes — avoid blanket deployment of both.
Prevention: Design logging strategy upfront. TGW Flow Logs + CloudTrail is usually sufficient for network audit; add VPC Flow Logs selectively for specific high-risk VPCs.

⚠️ Cost Traps
Trap 1 — Centralised egress through TGW: Routing spoke VPC internet traffic through TGW to a central NAT GW adds $0.02/GB TGW processing on top of NAT GW charges ($0.045/GB). For high-egress workloads, this can be MORE expensive than per-VPC NAT GWs. Model it before implementing.

Trap 2 — TGW Flow Logs to CloudWatch: At $0.76/GB CW ingestion, a TGW handling 10 TB/day generates enormous log costs. Use S3 as the primary destination for flow logs; CloudWatch for short-retention operational queries only.

Trap 3 — Cross-AZ TGW traffic: TGW processing charges apply regardless of whether traffic is cross-AZ or same-AZ. Unlike EC2 cross-AZ data transfer ($0.01/GB), TGW charges are for processing, not data transfer between AZs. Keep inter-AZ application traffic within VPCs (not through TGW) where possible.

Trap 4 — Peering attachment for low-volume cross-region: Two peering attachments ($73/month) for 1 GB/month of cross-region traffic ($0.08) means you're paying $73 for $0.08 of data movement. Use S3 replication or application-level replication for low-volume cross-region data instead of TGW peering.

🔴 Hard Ceiling: 10,000 Routes Per TGW
This is the one limit that can genuinely break large-scale deployments. In a large enterprise with hundreds of VPCs, fine-grained CIDRs (/24 per AZ per subnet type), on-premises prefixes, and multiple DX VIFs advertising detailed routes, the 10,000-route ceiling is reachable. Mitigation: use VPC CIDRs at /16 (not more specific), summarize on-premises routes before advertising to TGW, use Route 53 Resolver for DNS-based routing instead of specific subnet routes where possible. At 8,000+ routes, start planning route summarization actively.

When Does TGW Break? Honest Answer

At scale, TGW breaks in two ways:

  1. Route table complexity: At 50+ VPCs across multiple accounts with varying isolation requirements, managing associations and propagations manually becomes error-prone. This is where AWS Cloud WAN (TGW's successor for global networks) starts making sense — it introduces policy-based routing that replaces manual route table management.
  2. Inter-region bandwidth ceiling: The 50 Gbps TGW peering ceiling is a genuine architectural constraint for high-throughput cross-region workloads. If your DR or analytics patterns require moving petabytes between regions, TGW peering is not the right tool — use Direct Connect cross-connect or S3 replication instead.
🌉 Bridge from Storage/Virtualization
The 10,000-route TGW ceiling is your storage array's maximum LUN count — a hard architectural ceiling that you plan around from day one, not discover at 9,500 routes. Just as you'd tier LUN allocation across multiple arrays when approaching the LUN limit, you'd tier routing across multiple TGWs (with peering between them) when approaching the route limit. The solution pattern is the same: horizontal scale-out rather than vertical scale-up.

MACsec on Direct Connect

MACsec (802.1AE) provides Layer 2 encryption on Direct Connect connections. This is distinct from IPSec (Layer 3) — MACsec encrypts at the Ethernet frame level, before the IP packet. Some MAS TRM interpretations for FSI environments require MACsec on DX as the baseline for data confidentiality on private circuits. It requires DX Dedicated connections (not Hosted) and MACsec-capable customer-side hardware.

ℹ️ MACsec vs IPSec on DX
MACsec: Encrypts the L2 Ethernet frame. Zero performance overhead at line rate. Requires dedicated DX and MACsec-capable hardware on both ends. AWS supports: 1 Gbps, 10 Gbps, 100 Gbps DX Dedicated connections.
IPSec over DX: Encrypts IP payload. Requires a Site-to-Site VPN connection over a Transit VIF (not Private VIF). Adds ~5–10% CPU overhead for encryption. Supported on any DX connection type.
For Netrust FSI: MACsec on DX Dedicated + IPSec VPN as backup is the defence-in-depth recommendation. MACsec for the DX path, IPSec for the VPN failover path.

The BGP Peering Gap — TGW's Biggest DR Limitation

🔴 Critical Design Constraint
TGW peering attachments do NOT support BGP. Unlike VPN or DX attachments where BGP dynamically exchanges routes, inter-region TGW peering requires all routes to be configured as static entries in each region's TGW route tables. This has a critical DR implication: when the primary region has a partial failure, TGW peering will not automatically withdraw routes. Traffic will continue routing to the primary region even if it's degraded — until someone (or automation) manually updates the static routes. This is the #1 gotcha in multi-region TGW DR designs.

Automated Route Failover with EventBridge + Lambda

Python — Lambda: TGW Failover Route Update
import boto3 import os # Lambda triggered by EventBridge when Route 53 health check fails # Switches TGW route table in DR region to point to local VPCs instead of peering DR_REGION = "ap-northeast-1" PRIMARY_REGION = "ap-southeast-1" DR_TGW_RTB = os.environ["DR_TGW_ROUTE_TABLE_ID"] PRIMARY_CIDRS = ["10.0.0.0/16", "10.1.0.0/16", "10.2.0.0/16"] # Primary region VPC CIDRs DR_LOCAL_ATTACH = os.environ["DR_LOCAL_ATTACHMENT_ID"] PEERING_ATTACH = os.environ["PEERING_ATTACHMENT_ID"] def lambda_handler(event, context): ec2 = boto3.client("ec2", region_name=DR_REGION) # Step 1: Delete static routes pointing to primary region via peering for cidr in PRIMARY_CIDRS: try: ec2.delete_transit_gateway_route( TransitGatewayRouteTableId=DR_TGW_RTB, DestinationCidrBlock=cidr ) print(f"Deleted route {cidr} → primary peering") except ec2.exceptions.ClientError as e: if "InvalidRoute.NotFound" not in str(e): raise # Step 2: Create blackhole for primary CIDRs (prevent routing loops) for cidr in PRIMARY_CIDRS: ec2.create_transit_gateway_route( TransitGatewayRouteTableId=DR_TGW_RTB, DestinationCidrBlock=cidr, Blackhole=True ) print(f"Blackholed {cidr} in DR route table — DR is now isolated") # Step 3: SNS notification to on-call sns = boto3.client("sns", region_name=DR_REGION) sns.publish( TopicArn=os.environ["ALERT_TOPIC_ARN"], Subject="TGW FAILOVER EXECUTED — DR Region Active", Message=f"Primary region {PRIMARY_REGION} health check failed. DR TGW route table updated. DR VPCs now isolated from primary region routing." ) return {"status": "failover_complete"}

Pattern 2: Inspection VPC (East-West Traffic Hairpin)

Business scenario: MAS TRM §11.2 requires all production east-west traffic to pass through a stateful NGFW. AWS Network Firewall is deployed in a dedicated Inspection VPC. All spoke VPC traffic is forced through TGW → Inspection VPC → NFW → back through TGW to destination.

ℹ️ Route Design for Inspection VPC Hairpin
This is the most complex TGW routing pattern. The key insight: spoke VPCs have a default route (0.0.0.0/0) pointing to TGW. The TGW Inspection route table routes that default to the Inspection VPC. The Inspection VPC NFW inspects and forwards. The Inspection VPC's own route table has routes for all spoke CIDRs pointing back to TGW (to send traffic onward to destination). This creates a "hairpin" — traffic goes: Spoke → TGW → Inspection → TGW → Destination.

Appliance Mode MUST be enabled on the Inspection VPC TGW attachment. Without it, ingress traffic arrives on AZ-1a ENI and return traffic exits on AZ-1b ENI — NFW has no session state for the return traffic and drops it.
Inspection VPC Hairpin — Packet Flow VPC-Prod-A EC2 (10.0.1.100) → hits SG/routing for 10.1.1.50 (VPC-Prod-B) Step 1: EC2 sends to 10.1.1.50 VPC route table: 10.0.0.0/8 → TGW (tgw-xxx) ↓ enters TGW via Prod-A attachment Step 2: TGW looks up 10.1.1.50 in rtb-prod rtb-prod: 0.0.0.0/0 → Inspection VPC attachment ← default route forces inspection ↓ enters Inspection VPC Step 3: Inspection VPC NFW/NGFW - Stateful inspection: is this traffic allowed? - Yes: forward to 10.1.1.50 Inspection VPC route table: 10.0.0.0/8 → TGW (hairpin back) ↓ re-enters TGW via Inspection VPC attachment (Appliance Mode: same AZ ENI) Step 4: TGW looks up 10.1.1.50 in rtb-inspection rtb-inspection: 10.1.0.0/16 → Prod-B VPC attachment (propagated) ↓ exits to VPC-Prod-B → reaches 10.1.1.50 Return path (Step 5): same in reverse, same NFW AZ (Appliance Mode ensures symmetric)

This is the production-grade network pattern for multi-agent AI systems. Each EKS cluster hosts specialised agents (one for customer queries, one for document processing, one for model updates). All agents access Bedrock Claude API through the centralised VPC Endpoint, ensuring no Bedrock traffic exits to the public internet. The TGW route table (rtb-ai) is your network-level access control policy for the entire agent ecosystem. When you scale to 10 EKS clusters, you add attachments to TGW — no peering mesh explosion.

Pattern 4 (Anti-Pattern): Direct Spoke-to-Spoke Without TGW Route Design

What goes wrong: Engineer creates TGW with default association and propagation enabled, attaches all VPCs, and calls it done. All VPCs can now reach all other VPCs — the classic flat network. A compromised EC2 in the Dev VPC can now scan and probe the Prod VPC database subnets. There's no route-level isolation — only Security Groups, which are host-level controls and are more error-prone to maintain at scale than route-level controls.

The lesson: TGW default settings create a flat network. Architectural segmentation requires explicitly designed route tables with disabled default association and propagation. The flat network is the anti-pattern; the explicit route domain design is the architecture. These are not the same thing. The Console makes it far too easy to create the anti-pattern — Step 7 and 8 of Section 05 are specifically to prevent this.

Regular FAQ — Beginner Questions

#
BasicsIs TGW free?

No. TGW charges $0.05/hour per attachment (~$36/month per VPC, VPN, or DX connection attached) plus $0.02/GB of data processed. For a lab with 3 VPCs attached, that's ~$110/month just in attachment fees. Always clean up lab TGWs when done — see the cleanup checklist in Section 16.

BasicsDo I need TGW or can I use VPC Peering?

Use VPC peering for 2–3 VPCs with no on-premises connectivity and no need for network segmentation. Use TGW when you have 4+ VPCs, multi-account environments, on-premises connectivity, or need to isolate prod/dev traffic at the routing layer. VPC peering is free (intra-region), transitive routing isn't possible, and managing a large peering mesh becomes a maintenance nightmare. TGW costs money but provides clean hub-spoke routing at any scale.

Storage analog: VPC peering ≈ direct-attach storage (simple, point-to-point). TGW ≈ SAN fabric (hub, shared, scalable). Pick the right tool for the scale.

BasicsWhat's the difference between a TGW route table and a VPC route table?

A VPC route table controls how traffic leaves a subnet inside a VPC — including whether to send traffic to TGW. A TGW route table controls how traffic is forwarded between TGW attachments. Both must be configured. The most common mistake: configuring TGW route tables correctly but forgetting to add the TGW entry to the VPC route tables — resulting in 100% packet loss that looks like a TGW problem but is actually a VPC routing problem.

BasicsCan I attach VPCs from different AWS accounts to my TGW?

Yes — this is one of TGW's most powerful features. You share the TGW across accounts using AWS RAM (Resource Access Manager). The TGW lives in a central "Network" account; spoke accounts share it and create their VPC attachments to it. This requires RAM sharing to be enabled in your AWS Organization. The spoke account engineer creates the attachment from their own account, but the TGW lives in the network account.

BasicsWhat is Appliance Mode and when do I need it?

Appliance Mode forces TGW to route return traffic through the same AZ ENI that received the forward traffic. You need it any time a VPC attachment connects to a stateful inspection appliance (AWS Network Firewall, Palo Alto, Fortinet). Without it, TGW load-balances across AZ ENIs, and stateful firewalls see return packets without a matching session entry — they drop them. Enable Appliance Mode on the Inspection VPC attachment and nowhere else.

BasicsCan I connect my on-premises network to TGW?

Yes — two methods: (1) Site-to-Site VPN: IPSec tunnels from your on-premises router to TGW. BGP supported. ECMP across multiple tunnels for higher bandwidth. (2) Direct Connect (via DX Gateway): Private circuit from your colocation to AWS via a DX partner. More reliable, lower latency, higher bandwidth than VPN. For FSI production workloads, DX is the standard with VPN as backup. TGW supports both simultaneously — DX as primary with VPN failover.

BasicsHow do I see what TGW costs me?

In AWS Console: Cost Explorer → filter by Service = EC2 (TGW costs appear under EC2 service, not as a separate service line) → group by Usage Type → look for TransitGateway-Hours and TransitGateway-Bytes. Better: apply a tag to your TGW at creation (Cost-Center: networking) and use Cost Explorer tag filters. TGW costs don't appear under a "Transit Gateway" service line — they're under EC2, which catches many people off guard.

BasicsCan I delete TGW without breaking my VPCs?

You cannot delete a TGW while it has active attachments. Delete the attachments first, then the TGW. When attachments are deleted, TGW ENIs are removed from your VPC subnets, but your VPC subnets, route tables, and EC2 instances remain intact. However: your VPC route table entries pointing to TGW will become invalid (stale routes) — clean those up as well. Deleting a TGW is a planned operation, not something you do in a hurry.

BasicsDoes TGW work across regions?

TGW is regional — it only connects resources in the same AWS region. To connect resources in different regions, you create a TGW Peering attachment between two TGWs in different regions. Traffic stays on the AWS backbone (not public internet). The key limitation: TGW peering does not support BGP — you must add static routes manually on both ends for cross-region routing. Bandwidth is also capped at 50 Gbps per peering attachment.

BasicsWhat's the difference between TGW and AWS Cloud WAN?

TGW is the per-region managed router — you configure attachments and route tables per region manually. Cloud WAN is TGW's global-scale successor — it uses a policy-based model where you define network segments and policies, and AWS manages the underlying TGW infrastructure across regions automatically. Cloud WAN is more expensive but dramatically reduces the operational complexity of multi-region networking. For a 1–3 region deployment, TGW is simpler and cheaper. For 4+ regions with complex routing policies, Cloud WAN starts making sense.

ArchitectureWalk me through how you'd design TGW route tables for a 12-VPC FSI environment with strict prod/dev isolation.

Answer: I'd start by identifying network domains — Prod, Dev, Shared Services, Inspection. Each domain gets its own TGW route table. The key design decisions are: (1) Disable default route table association and propagation — forces every attachment to be explicitly assigned. (2) Prod VPCs associate with rtb-prod, which receives propagated routes from Prod VPCs and Shared Services VPC — but not Dev. (3) Dev VPCs associate with rtb-dev, which receives Dev and Shared Services routes — but not Prod. (4) Shared Services associates with rtb-shared, which has routes to all domains (it serves all). (5) Inspection VPC associates with rtb-inspection, which has routes to all VPCs (it must forward inspected traffic to any destination).

The trade-off: this explicit model requires more upfront design but is far more secure and auditable than auto-propagation. For MAS TRM §11.2.1 compliance, the explicit model is mandatory — you need to demonstrate that prod/dev isolation is enforced at the routing layer, not just at the IAM or Security Group layer.

SecurityA developer says: "We have TGW connecting our VPCs — we're secure." What's wrong with that statement?

Answer: TGW is a router, not a security device. It routes packets based on CIDR matches in route tables — it does not inspect packet content, enforce application-layer policies, or prevent lateral movement beyond what route tables explicitly deny. If default route table association is enabled (AWS default), all VPCs can reach all other VPCs — a compromised Dev EC2 can scan Prod databases. Even with route isolation, TGW does not inspect traffic between allowed networks. The correct statement: "TGW provides network-layer segmentation when properly configured with explicit route tables. Security requires TGW route isolation PLUS Inspection VPC with stateful firewall PLUS Security Groups PLUS IAM." TGW is one control in a layered model, not the complete model.

ArchitectureWhy does Appliance Mode exist? Explain the underlying routing mechanics that make it necessary.

Answer: Without Appliance Mode, TGW distributes traffic across AZ ENIs based on a 5-tuple hash (source IP, dest IP, source port, dest port, protocol). The hash may route the SYN packet for a TCP connection through the 1a ENI and the SYN-ACK return packet through the 1b ENI. A stateful firewall tracks connection state per ENI — when it sees a SYN-ACK with no corresponding SYN in its state table, it drops the packet. This is asymmetric routing breaking stateful inspection.

Appliance Mode instructs TGW to use the same AZ for both directions of a flow — forward and return traffic traverse the same AZ ENI, giving the stateful appliance consistent state. The trade-off: Appliance Mode reduces AZ diversity for the Inspection VPC attachment, meaning an AZ failure on the Inspection VPC side could affect all traffic passing through that AZ. Mitigate by deploying firewall instances in all AZs within the Inspection VPC.

CostThis TGW bill came in at $8,000/month. Where would you look to cut it?

Answer: I'd audit in this priority order: (1) Attachment count — at $36/month each, 220 attachments = $7,920. Audit for orphaned attachments from decommissioned VPCs. (2) Data processing volume — at $0.02/GB, $8,000 implies ~400 TB/month transiting TGW. Identify if centralized egress through TGW is forcing unnecessary traversal for internet-bound traffic — compare cost of per-VPC NAT GW vs. TGW processing overhead. (3) Cross-region peering data transfer — inter-region charges stack on top of TGW processing. Review if peering attachments justify their combined attachment + data transfer cost. (4) CloudWatch flow log ingestion — at $0.76/GB, high-volume TGW flow logs can add thousands. Redirect to S3. (5) Unnecessary peering attachments — TGW peering for low-volume cross-region workloads where S3 replication would be cheaper. Each optimization should be modeled before applying.

DRHow would you implement a DR strategy for your TGW-based network with RTO <15 minutes?

Answer: A 15-minute RTO is achievable with warm standby: pre-deploy a full TGW in the DR region (ap-northeast-1) with all route tables and attachments configured, but DR VPCs running minimal or no compute. Establish TGW peering between primary and DR regions with static routes on both ends. The automation layer: Route 53 health checks monitor primary region endpoints. On health check failure, EventBridge triggers a Lambda function that: (1) updates DR TGW route tables to activate DR VPCs as primary destinations, (2) publishes DNS failover via Route 53 routing policies, (3) triggers auto-scaling groups in DR region to scale up compute.

The critical constraint: TGW peering has no BGP, so route failover is not automatic — the Lambda automation is what bridges this gap. Test it quarterly. The trade-off: warm standby doubles infrastructure cost in the DR region; for MAS TRM §14 BCM compliance in FSI, this cost is typically non-negotiable.

ScaleHow would you architect TGW to support 500 VPCs across 50 AWS accounts?

Answer: At 500 VPCs, the key constraints are: (1) TGW hard limit of 5,000 VPC attachments per TGW — 500 is well within range. (2) 10,000 route limit — at 500 VPCs with /16 CIDRs, that's 500 routes, well within range. (3) Route table management complexity — 500 VPCs across 50 accounts with varying isolation requirements makes manual route table management error-prone. Design: create a dedicated Network Services account owning the TGW; share via RAM using AWS Organizations; automate attachment creation and route table assignment via Terraform pipelines triggered by VPC provisioning. Use a Landing Zone approach where new accounts/VPCs automatically get attached to the correct TGW route table based on account metadata tags. Monitoring: CloudWatch dashboards tracking attachment count, route count vs. the 10,000 limit (alert at 8,000). At this scale, evaluate AWS Cloud WAN as a replacement for the manual TGW route table management.

SecurityHow do you ensure all inter-VPC traffic passes through your NGFW without gaps?

Answer: The Inspection VPC pattern with TGW route design. The route design is the enforcement mechanism: (1) All spoke VPCs have a default route (0.0.0.0/0) in their private subnet route tables pointing to TGW. (2) The TGW route tables for spoke VPCs route default traffic to the Inspection VPC attachment — there is no direct spoke-to-spoke route. (3) The Inspection VPC runs the NGFW (NFW, Palo Alto, etc.). (4) After inspection, the Inspection VPC's route table sends traffic back to TGW with specific destination routes. (5) Appliance Mode is enabled on the Inspection VPC attachment to prevent asymmetric routing. The gap analysis: this pattern inspects east-west spoke traffic. It does not inspect traffic within a single VPC (intra-VPC east-west uses VPC routing, not TGW). For intra-VPC inspection, you'd need GWLB with inline appliances. Cloudtrail and TGW Flow Logs provide the audit trail to prove all cross-VPC traffic traversed the Inspection VPC.

ArchitectureTGW vs. AWS PrivateLink — when do you use each?

Answer: TGW provides general VPC-to-VPC routing — all traffic between attached VPCs can potentially flow, controlled by route tables. It's a general-purpose network fabric. PrivateLink exposes a specific service (a Network Load Balancer endpoint) from one VPC to consumers in other VPCs, without the consumers having general network access to the producer VPC. PrivateLink is unidirectional and service-scoped; TGW is bidirectional and network-scoped.

Decision rubric: Use TGW when VPCs need general network connectivity (multiple services, bidirectional traffic, on-premises routing). Use PrivateLink when you want to expose a specific API/service from one team to another without granting general network access — e.g., a payments team exposing a transaction API to the mobile app team without letting the mobile app team reach the payments database. The right answer for most enterprise environments: TGW as the general network fabric, PrivateLink for selective service exposure between specific producer/consumer pairs.

OperationsProduction alert: PacketDropCountNoRoute spiked to 50,000/min. What's your incident response?

Answer: Immediate triage in this order. (1) Check if new VPCs were attached in the last 30 minutes — the most common cause: a new VPC attachment whose CIDR hasn't been propagated into the relevant TGW route table. Check CloudTrail for recent CreateTransitGatewayVpcAttachment events. (2) Run Reachability Analyzer from a known-working source to the failing destination — the ExplanationCode tells you exactly which route table has the missing route. (3) Check if any route table propagations were accidentally deleted — CloudTrail query for DeleteTransitGatewayRouteTablePropagation in the last hour. (4) Check if spoke VPC CIDRs overlap — overlapping CIDRs can cause route table corruption. (5) If the drop count is massive and widespread (not isolated to one VPC): suspect a TGW route table association was accidentally changed. Compare current associations against the IaC state (Terraform plan output). Resolution: add the missing propagation or static route. Post-incident: add CloudWatch alarm for PacketDropCountNoRoute > 1000/min, route all TGW config changes through Terraform to prevent manual drift.

ArchitectureHow would you use TGW as the network backbone for a multi-VPC AI inference platform?

Answer: I'd design dedicated VPCs per function: EKS-Inference (real-time, latency-sensitive), EKS-Batch (throughput), EKS-Training (GPU), and Shared Services (centralised VPC Endpoints). TGW connects all four with a single rtb-ai route table routing all AI VPCs together and to Shared Services. The centralised Bedrock VPC Endpoint in Shared Services saves $21.90/month per AI VPC at scale — at 10 AI VPCs with 3 AZs each, that's $219/month saved vs. per-VPC endpoints, for one endpoint type alone.

The architecture advantage: when we add more EKS clusters (new model types, new geography), we add a new VPC + TGW attachment — the network topology scales linearly. Service mesh (Istio) operates at L7 over TGW's L3 fabric — TGW handles routing, Istio handles mTLS, traffic management, and observability. TGW Flow Logs provide the network audit trail for the AI platform; Bedrock access through centralised endpoint ensures all LLM API calls are logged via CloudTrail and never traverse the public internet.

Common HCL Pitfalls for TGW

  • Propagation order dependency: Route table propagation resources depend on both the attachment and the route table being created first. Use depends_on explicitly if Terraform plan shows dependency errors.
  • RAM share timing: Add a time_sleep resource (120 seconds) after aws_ram_principal_association before spoke accounts try to create attachments — RAM propagation has eventual consistency.
  • Appliance mode immutability: Appliance mode cannot be changed on an existing attachment without destroying and recreating it. Get it right in code before apply.
  • for_each on propagation pairs: The local.propagation_pairs flatten pattern avoids nested for loops that Terraform can't handle in for_each. Always use the string key pattern "attach-key->rtb-key" to ensure unique map keys.
  • Cross-account attachments: The spoke account creates the aws_ec2_transit_gateway_vpc_attachment resource using a provider aliased to the spoke account. The TGW owner account must accept the attachment (auto-accept can be enabled on the TGW via auto_accept_shared_attachments = "enable").
