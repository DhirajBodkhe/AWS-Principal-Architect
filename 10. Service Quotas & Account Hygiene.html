Glossary & Key Terms #

Service QuotaA limit on the number of resources or operations of a specific type you can have in an AWS account per region. Examples: 5 VPCs per region, 20 EC2 instances per region, 100 S3 buckets per account. Suitable for quick testing, actively harmful for production (resources deployed into it by accident get public IPs).≈ The default VLAN on an unmanaged switch — everything connects there unless explicitly configured otherwise. 01 / CONCEPT

Concept & Mental Model #

Why Quotas Exist

Service quotas are not billing controls — they don't directly limit your spend. They're protective defaults that prevent accidental runaway resource creation (a misconfigured autoscaling group spinning up 10,000 instances) and ensure AWS can maintain service quality for all customers. Most defaults are conservative for new accounts. As you demonstrate responsible usage and scale legitimately, quotas are raised on request — often instantly for common limits.

The architect's responsibility: know which quotas are relevant to your architecture before you need them. A production launch blocked by a quota ceiling is embarrassing and preventable. Pre-emptively request increases for limits you'll approach — VPCs per region, EC2 instances per region, Lambda concurrent executions, EIPs per region — well before launch day.

Quotas vs Throttling — Two Different Problems

Quotas limit how many resources exist. Throttling limits how fast you make API calls. Both can block your application but require different fixes. Quota breach: "You have reached the maximum number of VPCs allowed in this region" — fix by requesting an increase. Throttling: "Rate exceeded — please retry your request" (HTTP 429) — fix by implementing exponential backoff, reducing API call frequency, or caching responses. Both will appear in your application logs and both are normal to encounter at scale.

Account Hygiene — The Foundation Nobody Talks About

Account hygiene is the set of configurations an account must have before any workload is deployed. It's not about the workload — it's about the account itself being safe and observable. An account without GuardDuty is blind to threats. An account with a root access key is a security incident waiting to happen. An account without CloudTrail has no audit trail. These aren't optional configurations — they're table stakes for any production AWS account. Yet an astonishing number of enterprise AWS accounts fail basic hygiene checks because they were created quickly for a project and "we'll add security later" — which never comes.

🌉 Bridge from Storage/Virtualisation

Service quotas ≈ storage array resource limits. Your NetApp array has a maximum LUN count, a maximum volume count, a maximum snapshot count per volume. You know these limits before you design your storage layout — you don't discover them when a provisioning job fails at 2am. AWS quotas work the same way: know the limits relevant to your architecture, request increases proactively, set CloudWatch alarms at 80% of the quota so you have headroom to act before hitting the ceiling. Account hygiene ≈ server hardening baseline — every new server that enters the DC gets the security build applied before it's connected to any production network. AWS accounts are the same: hygiene baseline before any workload.

💡 Why This Guide Closes Phase 1

Quotas and hygiene are the unsexy foundation that everything else in Phase 1 builds on. Your VPC design (Guide 01) will fail at launch if you haven't requested enough EIPs or VPCs. Your DX connectivity (Guide 07) depends on having a clean account baseline with CloudTrail enabled for audit trails. Your cost management (Guide 08) is undermined if compromised IAM credentials generate unexpected charges that weren't detected by GuardDuty. Every guide in Phase 1 assumed a well-configured account underneath. This guide documents what that assumption requires.

🤖 AI / Agentic Angle

Service quotas become critical infrastructure for AI workloads. Amazon Bedrock has per-account token-per-minute (TPM) quotas per model — if an agentic workflow makes 100 parallel Bedrock calls, each with a large context window, it can hit the TPM quota in seconds and start receiving throttling errors. Lambda concurrent execution quotas affect agentic orchestration patterns where each agent step is a Lambda invocation. SageMaker has endpoint instance quotas that can block model deployment. Before any AI workload launch, audit the relevant quotas: Bedrock TPM per model, Lambda concurrent executions, and SageMaker endpoint instance limits. These are the three most commonly underestimated quotas for AI-native architectures.

04 / PREREQUISITES

Prerequisites & Environment Setup #

Access Requirements

  • AWS Support plan: Basic support (free) allows quota increase requests for many limits. Some limits require Business or Enterprise support for faster responses. Check support plan before planning a launch.
  • IAM permissions for Service Quotas: servicequotas:ListServiceQuotas, servicequotas:RequestServiceQuotaIncrease, cloudwatch:PutMetricAlarm for quota alarms.
  • Root account access for hygiene checks: Some hygiene configurations require root — enabling MFA on root, deleting root access keys, changing account contact information.
  • Organization management account access: For enabling GuardDuty, Security Hub, and Config at organization level (most efficient approach for multi-account).
⚠️ Quota Increases Take Time — Plan Ahead

Most common quota increases are instant (auto-approved). But some — particularly very large EC2 vCPU increases, Bedrock quota increases for high-volume models, or increases to hard-to-supply instance types — require AWS support team review and can take 1–5 business days. For any production launch, identify quota dependencies at least 2 weeks in advance. Submit requests immediately — you can always not use the increased quota, but you can't unblock a launch at the last minute if AWS needs review time.

🌉 Bridge from Storage/Virtualisation

Planning quota increases before launch ≈ ordering additional disk shelves before a storage migration. You don't wait until the array is at 95% capacity to order new shelves — lead time is weeks, and the array can't wait. Same for AWS quotas: identify them during architecture design, request increases during build phase, verify before launch. The Service Quotas console shows your current usage vs limit in real time — use it the same way you'd use a storage capacity dashboard during a migration project.

# CloudWatch alarm at 80% of VPC quota
resource "aws_cloudwatch_metric_alarm" "vpc_quota_80" {
  alarm_name          = "vpc-count-80pct"
  comparison_operator = "GreaterThanOrEqualToThreshold"
  evaluation_periods  = 1
  metric_name         = "ResourceCount"
  namespace           = "AWS/Usage"
  period              = 300
  statistic           = "Maximum"
  threshold           = 4   # 80% of default quota (5). Update if quota raised.
  dimensions = {
    "Service"  = "VPC"
    "Resource" = "VPC"
    "Type"     = "Resource"
    "Class"    = "None"

}

05 / GUI IMPLEMENTATION

Step-by-Step GUI Implementation #

Three parts: (A) Service Quotas — view, alarm, request increase. (B) Account hygiene baseline — Day 0 configurations. (C) Security Hub — unified posture view.

Part A: Service Quotas

1
View Your Current Quotas and Usage
WhereService Quotas → AWS services → select a service (e.g., Amazon VPC)
What you seeA list of all quotas for that service with: Quota name, Applied quota value (your current limit), AWS default value, whether it's adjustable, and a Usage column showing your current count vs limit as a percentage bar.
Usage columnThe Usage % bar is the key metric. Green = safe, yellow = approaching limit, red = near/at limit. Any quota showing >60% usage should have a CloudWatch alarm and a pre-emptive increase request.
DashboardService Quotas → Dashboard → shows quotas approaching their limits across all services in one view. Use this as your weekly quota health check. Pin high-risk quotas to the dashboard.
2
Create CloudWatch Alarm for a Quota at 80%
WhereService Quotas → select a service → select a quota → Create alarm
Alarm thresholdSet to 80% of current quota value. Example: VPCs per region = 5, alarm threshold = 4. You want to know you're approaching the limit before you hit it.
SNS topicConnect to your platform alerts SNS topic (same one used for Budget alerts in Guide 08). Quota alerts and cost alerts going to the same channel is intentional — both are operational risk signals.
Why 80%At 80% you still have time to request an increase and wait for approval before hitting the ceiling. At 95% you're in emergency territory. At 100% your deployments are failing.
3
Request a Quota Increase
WhereService Quotas → select service → select quota → Request increase at account level
Requested valueEnter the new limit you need. Be realistic — request 2–3× your current need to avoid returning immediately for another increase. Example: VPCs at 5, need 10, request 20.
JustificationBrief business justification: "Multi-account landing zone requiring additional VPCs for workload isolation per AWS Well-Architected guidance." Clear and concise is better than elaborate.
Processing timeMost common increases (VPCs, EIPs, standard EC2 types): instant or same-day auto-approval. GPU instances, very large vCPU counts, Bedrock high-volume: 1–5 business days. Check status in Service Quotas → Quota request history.
Visual cueAfter submission: status shows "Pending." After approval: status shows "Approved" and the quota value updates in the console. You receive an email notification for both outcomes.
✅ Checkpoint A: You can navigate to any service's quotas, read the usage %, create a CloudWatch alarm at 80%, and submit a quota increase request. The Quota request history tab shows any pending or completed requests.

Part B: Account Hygiene Baseline

4
Secure the Root Account
MFA on rootAccount menu → Security credentials → Multi-factor authentication (MFA) → Assign MFA device. Use a hardware TOTP device (YubiKey preferred) for root, not a phone app — phones can be lost/compromised. The root MFA device should be stored in a secure, access-controlled location.
Delete root access keysSame page → Access keys → if any root access keys exist, delete them immediately. Root access keys cannot be restricted by IAM policies — any key that has them is a catastrophic security risk. Check: there should be zero root access keys on any account that's been in use.
Root email alertVerify the root account email address is a distribution list (not one person's inbox) so that root login notifications and billing alerts reach the right people when the account owner changes roles.
Why criticalRoot credentials bypass all IAM policies, SCPs, and permission boundaries. A compromised root account is total account loss — all data, all resources, all IAM controls. Treat root like a nuclear launch key: store securely, never use unless absolutely required, audit every use.
5
Enable EBS Default Encryption
WhereEC2 → Settings (in left nav) → EBS encryption → Manage
ActionEnable Default encryption → select your KMS key (use the AWS-managed EBS key initially; use a CMK for production accounts that require customer-managed keys per MAS TRM §11.3). Click Update EBS encryption.
EffectAll new EBS volumes created in this region are automatically encrypted. No per-volume encryption setting needed. Existing unencrypted volumes are unaffected — this is region-scoped and applies to new volumes only.
WhyWithout default encryption, developers launching EC2 instances without explicitly setting encryption get unencrypted root volumes. MAS TRM §11.3 requires encryption at rest for regulated data. Default encryption makes compliance automatic rather than opt-in.
6
Block S3 Public Access at Account Level
WhereS3 → Block Public Access settings for this account
ActionClick Edit → enable all four settings: Block public ACLs, Block public bucket policies, Ignore public ACLs, Restrict public buckets → Save changes.
EffectNo S3 bucket in this account can be made public — regardless of individual bucket settings. An account-level block overrides any bucket-level or object-level public access configuration. This is a safety net against accidental public exposure.
ExceptionIf an account legitimately needs public S3 (e.g., a static website hosting account), disable only at the bucket level for that specific bucket — keep account-level block enabled and override at bucket level for the specific exception.
7
Enable GuardDuty
WhereGuardDuty → Get Started → Enable GuardDuty
For OrganizationsBetter approach: enable GuardDuty at the Organization level from the management account (Guide 05 pattern). GuardDuty → Settings → Accounts → Enable for entire organization. All current and future accounts receive GuardDuty automatically.
Cost noteGuardDuty costs ~$1–5/month for small accounts (based on CloudTrail events + data volume analyzed). For a production FSI account: $20–100/month is typical. This is the most cost-effective threat detection available — cheaper than a single security incident.
30-day free trialGuardDuty has a 30-day free trial per account. The trial shows you estimated monthly cost so you can budget before committing.
8
Delete or Tag the Default VPC
WhereVPC → Your VPCs → identify Default VPC (IsDefault: Yes)
Option 1 (preferred)Delete the default VPC: Actions → Delete VPC. First delete its dependencies: default subnets (one per AZ), default route table associations, internet gateway (detach then delete). The delete-default-vpc AWS CLI command automates this.
Option 2If deletion is too disruptive (some services require a default VPC): tag it clearly as Name: DO-NOT-USE-default-vpc and configure an AWS Config rule to alert if any resource is deployed into it.
WhyThe default VPC has public subnets in every AZ. Any EC2 instance launched without specifying a subnet goes into the default VPC with a public IP — unintended internet exposure. Deleting it forces developers to explicitly choose a properly configured VPC. In the SCP-governed landing zone (Guide 05) this is prevented anyway, but hygiene-in-depth means not relying on SCPs alone.
✅ Checkpoint B: Root has MFA, no access keys. EBS default encryption enabled. S3 account public access blocked. GuardDuty enabled. Default VPC deleted or tagged. These 5 items are your hygiene baseline minimum.

Part C: Security Hub — Unified Posture

9
Enable Security Hub and Standards
WhereSecurity Hub → Get Started → Enable Security Hub
StandardsSelect: AWS Foundational Security Best Practices (enable always — AWS's own checklist), CIS AWS Foundations Benchmark (for FSI compliance — MAS TRM aligns with CIS), PCI DSS (if you handle payment card data).
After enablingSecurity Hub runs initial checks. After 24 hours, you get a Security Score (0–100%). A new account with basic hygiene typically scores 60–75%. Target: 85%+ for production FSI accounts. Each failed check is a finding with severity and remediation guidance.
IntegrationsSecurity Hub automatically pulls findings from GuardDuty, Config, Inspector (if enabled), and IAM Access Analyzer — no extra configuration. The unified view is the value: one console for all security findings, prioritized by severity.
Visual cueSecurity Hub summary shows Security Score + a findings breakdown by severity: Critical, High, Medium, Low, Informational. Click any severity to see the specific failing checks with remediation steps.
✅ Checkpoint C: Security Hub enabled with AWS Foundational and CIS standards. Initial findings visible with severity scores. Integrations from GuardDuty and Config are pulling findings automatically. Security Score visible in the summary.

09 / TROUBLESHOOTING

Troubleshooting #

QuotaDeployment fails with "LimitExceeded" or "ResourceCountExceeded"▼

Cause: You've hit a service quota ceiling. The error message usually includes the quota name. Fix: Navigate to Service Quotas → find the relevant service → identify the quota → Request increase. For quotas that are commonly hit in production (EC2 vCPUs, Lambda concurrent executions): submit the request now, then implement exponential backoff or throttle your deployment until the increase is approved. For VPCs: check if you can reuse existing VPCs rather than creating new ones while waiting for the increase. The increase usually takes minutes for standard quotas — check Service Quotas → Quota request history for status.

APIApplication getting "ThrottlingException" or "Rate exceeded" errors▼

Cause: Throttling is a rate limit on API calls per second — separate from service quotas (which limit resource count). You're making too many API calls too fast. Common causes: loop calling DescribeInstances without pagination, Lambda functions calling the same API simultaneously across many concurrent invocations, or a CLI script without backoff. Fix: Implement exponential backoff with jitter in your application code. Use pagination for large list operations. Cache API responses where possible — if you're calling DescribeSecurityGroups 100 times/minute, cache the result for 60 seconds. For SDK calls: all AWS SDKs have built-in retry with backoff — ensure you're not disabling it with custom retry configurations.

Security HubSecurity Hub score is low — how to prioritise remediation?▼

Approach: Don't try to fix everything at once — triage by severity and impact. CRITICAL findings first (these map to controls that can be exploited or cause data loss directly). HIGH findings next (significant risk but not immediately exploitable in most cases). Sort by "Failed resources" count — a single finding affecting 50 S3 buckets gets fixed before a finding affecting 1 resource. Suppress findings for intentional exceptions (e.g., a public S3 bucket hosting a static website — suppress the public access finding with a justification). Track the score weekly — aim for 5% improvement per sprint. From a typical starting score of 55%, reaching 85% within 30 days is achievable with focused effort on the Critical and High findings.

GuardDutyGuardDuty finding for "UnauthorizedAccess:IAMUser/MaliciousIPCaller" — what do I do?▼

Don't panic — GuardDuty findings require investigation, not immediate action. This finding means an IAM user's credentials were used from an IP address that's in GuardDuty's threat intelligence feed (known malicious IPs). Steps: (1) Identify which IAM user/role is involved — GuardDuty shows the principal in the finding detail. (2) Check CloudTrail for what API calls were made from that IP. (3) Immediately disable the IAM user's access keys if credentials are suspected compromised. (4) Check for any resources created during the suspicious activity period (new EC2 instances, new IAM users, new S3 buckets). (5) Rotate all credentials for the affected user. (6) Review for persistence mechanisms (new IAM users, Lambda backdoors, new access keys on existing users). GuardDuty findings are alerts, not confirmed incidents — investigate before assuming the worst, but treat high-severity findings with urgency.

14 / SECURITY

Security Hardening — Quotas as a Security Control #

Using Quotas Defensively

Service quotas are typically thought of as ceilings to raise. But they can also be used defensively — as a control that limits the blast radius of a compromised account. If a developer's credentials are compromised and an attacker tries to spin up a crypto-mining fleet of GPU instances, a low EC2 G-instance quota (default 0–8 vCPUs) means they can only launch 1–2 instances before hitting the limit. This doesn't prevent the compromise, but it limits the financial damage. Combined with GuardDuty (which detects the unusual API pattern) and Budget alerts (which alert on the spike), the layered defense catches the incident quickly.

SCP as Quota Enforcement (Hard Limits)

For strict environments, SCPs can enforce tighter limits than service quotas allow. An SCP denying ec2:RunInstances unless the instance type is in an approved list (t3, m5, c5 — no GPU) prevents expensive instance launches entirely, regardless of quota. This is harder enforcement than a soft quota limit and doesn't require a support case to change — it's controlled by your Organizations team. FSI environments often layer both: service quotas as the capacity limit, SCPs as the type restriction.

17 / HYGIENE PATTERNS

Account Hygiene Patterns #

Pattern 1: Hygiene as Code via Account Factory

The most mature pattern: account hygiene is deployed automatically when a new account is created, not applied manually afterward. Account Factory (Control Tower, Guide 05) provisions new accounts and immediately deploys the hygiene module via CloudFormation StackSet. By the time the account owner receives access, all hygiene controls are already in place: GuardDuty enabled, Security Hub running, EBS encryption on, S3 block active, CloudTrail recording, Config rules deployed. The account owner cannot disable these controls — SCPs prevent GuardDuty suspension and CloudTrail disabling. This is the target state for any organisation managing 10+ accounts.

Pattern 2: Quota Pre-flight Checklist for Launches

Before any significant production launch, the architect runs a quota pre-flight: identify every resource type the workload creates (EC2 instances → check vCPU quota, Load Balancers → check ALB quota, Lambda → check concurrent execution quota, RDS → check DB instance quota), calculate peak resource count with headroom, verify current quota supports peak × 1.5, submit increase requests for any quota below that threshold. Document this as a "Launch Readiness Checklist" with quota status as a required sign-off item. No launch proceeds with a red quota status.

Pattern 3: Security Score SLA

Establish a Security Hub score SLA for each account tier: sandbox accounts ≥ 60%, development accounts ≥ 75%, production accounts ≥ 85%, PCI-scoped accounts ≥ 90%. Score is checked weekly via automated Lambda. Accounts below SLA receive an automatic Jira ticket to the owning team with the specific failing checks. Accounts that remain below SLA for 2+ weeks trigger an escalation to the CISO. This transforms a subjective "are we secure?" question into an objective, tracked metric with clear accountability. The score is visible in a shared dashboard — social pressure from team visibility is an underrated motivator for remediation.

🤖 AI / Agentic Angle

Account hygiene and quota management are natural candidates for AI-assisted operations. An agentic system with access to Security Hub findings, Service Quotas API, and Jira can: (1) weekly, pull new Security Hub findings and create remediation tickets automatically with the relevant Config rule documentation as context, (2) monitor quota utilisation and predict breach dates using linear regression on usage trends, raising a ticket 30 days before the projected breach, (3) generate the Account Health Report as a formatted document from live AWS API data on demand. These are the "toil elimination" use cases that free platform engineers to focus on architecture rather than operational reporting.

Regular FAQ — Beginner Focused #

BeginnerCan I raise any service quota to any value I want?▼

No — there are two constraints. First, some quotas are "hard limits" that cannot be raised at all (5 IGWs per VPC, for example — you'd never need more). Second, even for adjustable quotas, AWS won't approve requests that are unreasonably large without justification or that exceed what your account tier supports. A new account requesting 10,000 EC2 vCPUs with no prior usage history is unlikely to be instantly approved. AWS reviews large quota increases manually and may ask for justification. For production workloads: request 2–3× your projected need. For very large requests: provide context (production launch, migration from on-prem, specific business timeline).

BeginnerWhat's the difference between a service quota and a billing limit?▼

Service quotas limit how many resources you can create — they don't stop your bill from growing. Billing limits (Budgets, AWS Credit limits) control spend. You can have plenty of quota headroom but still hit your budget. Conversely, you can be within your budget but hit a quota ceiling. They're independent systems solving different problems. A production launch requires checking both: "do I have enough quota to deploy the workload?" AND "does the projected cost fit within budget?" Both questions must be answered before launch day.

BeginnerWhy should I delete the default VPC? I might need it.▼

The default VPC is dangerous precisely because it's the path of least resistance. When a developer launches an EC2 instance without specifying a subnet, it goes into the default VPC — with a public IP, in a public subnet, with a permissive default security group. This is accidental internet exposure. If you need a VPC for testing, create a properly configured one (private subnets, no IGW for private resources, specific SGs). The discipline of creating a VPC intentionally prevents the class of "I accidentally made this public" incidents. In a well-governed environment with SCPs (Guide 05), the SCP should enforce subnet specification anyway — but defense in depth means not relying on that alone.

BeginnerHow do I know which quotas are relevant to my workload?▼

Map your architecture to resource types, then look up each resource type's quota in Service Quotas. For a typical 3-tier web application: EC2 instances (check vCPU quota for your instance family), ALBs (check ALB quota), RDS instances (check DB instance quota), VPCs (check VPC count), EIPs for NAT GWs (check EIP quota), Lambda if used (concurrent execution quota). The Service Quotas console has a Dashboard view that shows any quotas approaching their limits — if you've run the workload in a dev environment, this view shows which quotas are trending upward. For completely new workloads, estimate peak resource count per type and check that against the default quota for each.

BeginnerIs GuardDuty the same as an antivirus?▼

No — GuardDuty operates at the network and API layer, not at the file/process level of traditional antivirus. GuardDuty analyses CloudTrail API logs, VPC Flow Logs, and DNS query logs to detect behavioral anomalies: an IAM user making API calls from a Tor exit node, an EC2 instance communicating with a known C2 server, unusual spikes in data transfer (potential exfiltration), crypto-mining traffic patterns. It doesn't scan files on disk or intercept process execution. For file-level scanning, AWS Inspector (EC2/ECR vulnerability scanning) and GuardDuty Malware Protection (EBS volume scanning) complement GuardDuty. Think of GuardDuty as a network-level IDS/SIEM, not endpoint protection.

ArchitectWe have 50 accounts. How do we apply the hygiene baseline without doing it manually 50 times?▼

Two approaches, often used together. First: enable security services at the Organization level from the management account — GuardDuty, Security Hub, Config, CloudTrail, and IAM Access Analyzer all support Organization-level enablement that automatically applies to all member accounts. One action in the management account covers 50. Second: deploy the hygiene Terraform module via CloudFormation StackSets (using the service-managed model targeting the Workloads OU) — this handles the account-level settings (EBS encryption, S3 block, IAM password policy, quota alarms) that don't have Organization-level enablement. The combination of Org-level service enablement + StackSet for account-level settings covers the full hygiene baseline with zero per-account manual work. New accounts get it automatically when they join the OU.

20 / INTERVIEW Q&A

Principal Architect Interview Q&A #

Principal"We're about to launch a new SaaS product on AWS. What would you check before go-live?"▼

Strong answer: "I'd run through three areas: service quotas, account hygiene, and operational readiness. For quotas: map every resource type the application creates at peak load, verify current quotas support peak × 1.5, submit any necessary increases 2 weeks prior. For hygiene: run the account health checklist — root MFA, no root keys, GuardDuty enabled, Security Hub running with CIS standard, CloudTrail active, EBS encryption default on, S3 public access blocked. For operational readiness: Budget alerts at 80% with SNS notification, Cost Anomaly Detection monitors per service, CloudWatch alarms on key application metrics, an incident runbook, and a tested rollback procedure.

I'd also verify the network is right: VPC with private subnets for data layer, public subnets only for the load balancer, NAT GWs in each AZ for outbound traffic, VPC Flow Logs enabled. And IAM posture: no wildcard permissions on task roles, no long-lived access keys for the application, Security Hub score above 85% before launch. A launch readiness checklist with all of these as sign-off items — no green, no launch — is the right process gate."

Principal"A production Lambda function started failing with TooManyRequestsException. How do you investigate and resolve?"▼

Strong answer: "TooManyRequestsException from Lambda is a throttling event — you've hit either the account-level concurrent execution quota (default 1,000) or a function-level reserved concurrency limit. First: check CloudWatch Metrics for Lambda → ConcurrentExecutions at the account level and for the specific function. If account-level ConcurrentExecutions is at 1,000, you've hit the account quota — submit a Service Quotas increase request immediately for Lambda concurrent executions. If the function has a reserved concurrency configured and it's hitting that limit, either increase the reservation or look at the upstream traffic pattern causing the spike.

Short-term mitigation: implement SQS in front of Lambda (Lambda event source mapping) to buffer requests — SQS absorbs the spike and Lambda processes at a controlled rate. The Lambda service auto-scales up to the concurrent execution limit; SQS decouples the producer's rate from the consumer's concurrency constraint. Long-term: request a concurrency increase, set a CloudWatch alarm at 80% of the concurrency limit so you see this coming next time, and review whether the spike was expected (legitimate traffic growth) or unexpected (a bug causing an event loop)."

Principal"An auditor from MAS is asking about your cloud security controls. Walk me through what you'd show them."▼

Strong answer: "I'd structure the walkthrough around the MAS TRM sections that cover cloud. For §7 (identity management): show IAM Identity Center with MFA enforcement, no root access keys, IAM password policy compliance from Config, and the credential report showing no long-lived keys. For §11 (data protection): show EBS default encryption, S3 Block Public Access at account level, KMS CMK usage for sensitive data, and the Config rule s3-default-encryption-kms showing all S3 buckets are encrypted. For §12 (audit trail): show the CloudTrail org trail configuration, log file validation enabled, KMS-encrypted logs, and a CloudWatch metric filter alerting on root login events. For §14 (BCM): show the DX+VPN redundancy architecture, the tested failover runbook, and annual failover test evidence.

Then I'd pull up Security Hub showing the CIS AWS Foundations Benchmark compliance score — that's the MAS TRM §12 evidence in visual form. And I'd show GuardDuty findings history with the investigation and resolution log for any HIGH/CRITICAL findings. The auditor wants to see three things: controls exist, controls are monitored, and exceptions are tracked and justified. Security Hub score + GuardDuty findings log + Config compliance history provides all three in one set of screenshots."

Principal"How do you handle a GuardDuty finding that indicates an EC2 instance is communicating with a known crypto-mining pool?"▼

Strong answer: "This is a confirmed compromise finding — unlike some GuardDuty findings that require further investigation, an EC2 instance actively communicating with a crypto-mining pool is as close to certainty as threat detection gets. The response is time-sensitive. First: isolate the instance immediately. Modify the instance's security group to deny all outbound traffic except to the investigation CIDR (your forensics workstation or IR tooling). Do NOT terminate yet — preserve evidence. Second: snapshot all EBS volumes attached to the instance before any remediation — legal and forensic hold. Third: pull CloudTrail logs for all API calls made from the instance's IAM role in the past 30 days — check for new IAM users, new access keys, new Lambda functions, new S3 buckets created by the compromised role.

Fourth: rotate all credentials the instance could have accessed — the instance role's assumed credentials, any long-lived secrets in environment variables or instance metadata. Fifth: determine the initial access vector — was it an exposed SSH port, a vulnerable application, an SSM session from an unknown principal? Fix the root cause before redeploying the workload. Sixth: notify your CISO and legal/compliance team — this may trigger MAS TRM §14 incident reporting requirements. The whole sequence is your IR playbook, which should be pre-written and tested before incidents occur, not improvised during one."
